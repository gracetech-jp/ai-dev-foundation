# 動作確認依頼テンプレートスキル

実装・テストが完了し、ユーザーに動作確認を依頼するタイミングで使う。
目的は「不要なコマンドを並べない」こと。今回の変更に**直接関係する操作だけ**を提示する。

> 各サービスの具体的な起動・反映手順（開発サーバの自動リロード有無、再ビルド、マイグレーション適用の
> コマンド等）は `SERVICE.md` を正とする。このスキルは**依頼メッセージの組み立て方**を定めるもので、
> 具体コマンドは `SERVICE.md` から引く。

## 前提
- このステップは「テスト作成・実行」完了後に行う。ビジネスロジック変更があればテスト合格が前提。

## 進め方

### 1. 今回の変更を種別に分類する
変更したファイルを見て、以下のどれに該当するか判定する（複数該当あり）。
**追加操作が必要なのは、そのランタイムに反映するために手動アクションが要る場合だけ**。

| 変更種別 | 追加で必要になるもの（例。実コマンドは`SERVICE.md`参照） |
|---|---|
| サーバ側コードのみ | 通常は不要（開発サーバの自動リロードで反映） |
| クライアント側コードのみ | 通常は不要（devサーバの自動反映） |
| 依存パッケージの追加・更新 | 再ビルド／再インストールが必要 |
| データモデルの変更 | マイグレーション内容を要約提示 ＋ 適用コマンドを提示 |
| 環境変数の追加 | ユーザー自身の環境ファイルにも同じキーを追記する必要がある旨を明示 |

該当しない項目は書かない。「念のため」で余計なコマンドを足さない。

### 2. 再ログイン要否を判定する
- **再ログインが必要**：認証・セッション・トークン有効期限・ログイン処理まわりの変更
- **リロードのみでよい**：UI・レスポンス形式・データのみの変更
- 迷う場合は「念のため再ログインを」と保守側に倒し、理由も添える

### 3. 依頼メッセージを組み立てる（該当項目のみ、この順で簡潔に）
1. 何を実装したかの一行要約
2. 動作確認に必要なコマンド（該当するものだけ、コードブロックで）
3. データモデル変更がある場合はマイグレーション内容の要約
4. 再ログインが必要かリロードのみでよいかを明示
5. 確認してほしい具体的な操作・画面（アクセスURLがあれば併記）

### 4. 完了の扱い
ユーザーの明示的な「OK」を待たず、次の実装依頼が来た時点で動作確認完了とみなしてよい
（各サービスの作業フロー定義に従う）。ただし**コミットは別途「コミットして」の明示を待つ**
（このスキルは依頼の体裁を整えるものであり、コミットタイミングのルールは変更しない）。
