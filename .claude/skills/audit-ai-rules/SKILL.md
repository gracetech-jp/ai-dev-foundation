# AI駆動開発ルール監査スキル

本プロジェクトのAI駆動開発ルール（CLAUDE.md・SERVICE.md・docs/rules/・.claude/settings.json）が、Web上の最新ベストプラクティスや実際のコードベースの状態からズレていないかを定期的に洗い出すためのスキル。

## 進め方

### 1. Web上のベストプラクティスを調べる

以下の観点でWebSearchを行う（日本語・英語の両方でクエリを打つと精度が上がる）。

- Claude Code / CLAUDE.md のベストプラクティス（記述量・構成・具体性）
- エージェント型コーディングのガードレール（破壊的操作の防止、hookでの機械的強制）
- AI駆動開発におけるルール運用・メンテナンスのプラクティス

**情報源の扱い方（重要）**：検索結果には「2026年版まとめ」のようなSEO目的のリライト記事が大量に混ざる。以下を優先する。

- 一次情報（Anthropic公式ドキュメント、`code.claude.com/docs`等）を最優先で採用する
- 二次情報（個人ブログ・アフィリエイト風メディア）は複数のソースで内容が一致した場合のみ採用し、単独の主張はそのまま鵜呑みにしない
- 具体的な数値（「200行以内」等）は出典が示す文脈（コミュニティ基準か公式基準か）を明記する

### 2. 現状のルール・実装を確認する

思い込みで比較しない。必ず以下を実際に読む。

| 対象 | 確認内容 |
|---|---|
| `CLAUDE.md` | 全体の構成・行数・MUSTルールの具体性 |
| `SERVICE.md` | 技術スタック表・ディレクトリ構成・環境変数表が実装と一致しているか |
| `docs/rules/*.md` | 各ルールの内容、他ファイルとの重複・矛盾の有無 |
| `.claude/settings.json` / `settings.local.json` | permissions.allow/deny/ask の内容。MUSTルールに書かれた禁止事項が実際にdenyされているか |
| `scripts/audit-consistency.sh` / `scripts/pre-push` | 整合性監査・テスト実行が実際にpush前などで強制されているか |
| 実際のコード（依存定義ファイル・モジュール構成） | ドキュメントに書かれていない新規モジュール・依存関係がないか |
| 各サービスリポの `SERVICE.md`・`docs/service-rules/` | 本スキルは基盤リポでのみ実施する（2026-07-23 にサービス配布を停止）。監査対象には、本リポの**親ディレクトリ配下にある各サービスリポ**（`.service-profile` ファイルの存在で機械判別。特定サービス名は前提にしない）の固有ルールも含め、サービス側の監査機会が失われないようにする。到達できないサービスリポは「未監査」と明記する |

### 3. ギャップを洗い出す

観点の例（すべてではなく、実際に見つかったものだけを報告する）：

- **ルール量・肥大化**：毎セッション自動ロードされる合計行数は適正か（目安：CLAUDE.md本体は200行以内）
- **ガードレールの実装ギャップ**：MUSTルールがプロンプト任せで、`.claude/settings.json`のdeny/allowと対応していない箇所はないか
- **ドキュメント整合性のドリフト**：SERVICE.mdの棚卸し対象外になっている項目、実装とドキュメントのズレ
- **テスト・監査の機械的強制の欠如**：「べき」がプロンプト記述のみで、hookやCIで担保されていないもの
- **ルールの重複・矛盾**：同じルールが複数ファイルに異なる表現で書かれていて、将来ズレるリスクがあるもの
- **メンテナンス運用の欠如**：ルールを継続的に更新する仕組みがあるか

### 4. 報告 → 合意 → 実装の順で進める（勝手に直さない）

- 洗い出した問題点は一覧化してユーザーに提示する。この時点では実装しない
- ユーザーが「全部直して」等で合意した場合のみ実装に進む
- 優先度や対応範囲が不明な場合は`AskUserQuestion`で確認する

### 5. 実装時の注意（このスキル固有の教訓）

- **新しいルール・deny設定を追加する前に、既存の他ファイル（特に`docs/rules/git.md`のようなフェーズ限定の例外規定）と矛盾しないか必ず確認する。** 過去に「mainへの直接pushを一律禁止」しようとして、`git.md`が定めるMVPフェーズ中の例外（現に直近のコミットもmain上で直接行われている）と矛盾しかけた実例がある。ルールを机上で正しそうに見えても、実際の運用実態（`git log`等）と食い違っていないか確認すること
- `.claude/settings.json`を編集した後は、Readツールで読み戻すかJSON構文チェックを行い、構文崩れがないか確認する
- `scripts/audit-consistency.sh`にチェックを追加した場合は、実際に`bash scripts/audit-consistency.sh`を実行して意図通り動くか確認してから完了とする
- CLAUDE.md本体・SERVICE.md・docs/rules/の間でルールを重複させない。既存のルールを補強する場合は該当ファイルを更新し、他ファイルには参照のみを残す
- コミット・プッシュは通常のプロジェクトルール通り、ユーザーの明示的な指示があるまで行わない
