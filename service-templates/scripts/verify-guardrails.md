# ガードレールの実測チェックリスト（第2層・第3層）

`.claude/settings.json` の `permissions.deny`（第2層）を変更したとき、および devcontainer を
Rebuild したときに1回流す。所要2分。**Claude Code のセッション内で、下の7項目を順に叩いて結果を見る。**

## なぜ機械化しないのか

`permissions.deny` は **Claude Code 本体が評価する**ため、テストランナーからは検証できない。
「ルールがそう書いてある」ことは `make audit-all` の検査(5)が常時見ているが、
**そのルールで実際にブロックされるか**は、ツール層を通さないと分からない。

ヘッドレス実行（`claude -p "…"`）で自動化する案は、モデルがそのコマンドを実行しようとするかに
依存して**非決定的**になるため採らない。CI に入れると理由の分からない赤を生む。

## 手順

| # | 叩くもの | 期待 | 何を確かめているか |
|---|---|---|---|
| 1 | `git reset --hard HEAD~1` | **ブロックされる** | フラグが後ろに来る形 |
| 2 | `git clean -fd` | **ブロックされる** | force 形 |
| 3 | `git checkout .` | **ブロックされる** | `--` を伴わない変更破棄 |
| 4 | `cat .env` | **ブロックされる** | 第3層（フック）の秘密読み取り遮断 |
| 5 | `cat .env.example` | **通る** | 例外が生きていること |
| 6 | `git clean -n` | **通る** | ドライランの例外が生きていること |
| 7 | `ls -la .env` | **ブロックされる**（フックのメッセージが出ない形で） | **第2層が生きていること** |

## 5・6 を必ず含める理由

**止まることだけを確認するチェックリストは、全部止める設定でも緑になる。**
過剰ブロックはガードの形骸化に直結する（正当な操作が止まると回避策が常用される）。
**通ることの確認と止まることの確認は対で意味を持つ。**

## 7 が必要な理由

1〜4 は**すべて第3層（フック）が先に止める**。したがってこれだけでは第2層が生きているか分からず、
**deny が全部消えていても 1〜4 は緑になる**——二重化の片側を検証できていない。

`ls` はフックの読み取りコマンド一覧に**入っていない**（`ls -la ~/.ssh/` のような正当な操作を
通すため意図的に除外されている）。したがって `ls -la .env` はフックを素通りし、
**止まるとすれば第2層の `Read(.env)` だけ**である。実測でも、この形だけはフックの日本語メッセージが
出ず「Permission to use Bash ... has been denied」で止まった。**層を切り分けられる唯一の項目**。

## 検証用ファイルの用意

`.env` / `.env.example` が無い状態で 4・5・7 を叩くと、**止まった理由がガードなのか
ファイル不在なのか区別できない**。無ければダミーを置き、検証後に削除すること
（`.env` の作成は bash 経由だとガードが止めるので、エディタで作る）。

## 結果が期待と違ったとき

| 症状 | 見るところ |
|---|---|
| 1〜3 が通ってしまう | `.claude/settings.json` の `permissions.deny`（第2層）と、共通側のフック（第3層）。`make audit-all` の検査(5)が両側の実在を見る |
| 4 が通ってしまう | フックが起動していない疑い。devcontainer が共通 `.claude` を `/home/node/.claude` へマウントしているか |
| 5・6 が止まる | 過剰ブロック。共通側の `guard-dangerous.sh` のサニタイズ・例外側を確認する |
| 7 が通ってしまう | 第2層が消えている。`.claude/settings.json` の `Read(.env)` を確認する |
