# ADR-017: 保守運用工程を定める — OTel 計装の規約と AI による一次トリアージ

- 日付: 2026-08-03
- ステータス: 採用

## 背景

棚卸しの結果、保守運用に関する記述は整合性監査（`docs/rules/consistency.md`）のみで、**監視・ログ設計・アラート・インシデント対応・オンコール・バックアップ・障害復旧のルールは全リポジトリ横断の grep でヒット 0** だった。

サービスは展開後の保守運用まで含めてサービスである。ここが空白のままでは、リリース後の運用が全て場当たりになる。

## 決定

### 1. OpenTelemetry を計装の標準とする

ただし位置づけを明確にする。**OTel はデータ標準であり、脱出計画ではない。**

基盤が配るのは計装の規約まで。監視バックエンド（SaaS）の選定はプロジェクト側の判断とし、本 ADR では決めない。

### 2. SLO から始める

順序を規定する。

```
1. 答えたい問いを決める（主要ユーザージャーニー 2〜4 本を選ぶ）
2. それらに SLI を定義する（レイテンシ / エラー率 / 可用性）
3. その後でテレメトリのカバレッジを広げる
```

先に大量のログを出すことを禁止する。

### 3. 相関可能性を必須要件とする

AI に運用の一次対応をさせる前提条件として、次を必須とする。

- ログに `trace_id` / `span_id` を含める
- `service.name` を一貫させる
- OTel の Resource 属性とセマンティック規約に従う
- 構造化ログとする（非構造化ログを禁止する）

これらは推奨ではなく**CI ゲートで検査する必須項目**とする。

### 4. エージェントによる一次トリアージ

アラート発火時に、エージェントが次を行うスキルを配布する。

コンテキスト収集 → ログ照会 → 関連デプロイの取得 → 過去の類似インシデントの取得 → トリアージ要約の作成 → 構造化されたブリーフィングの提示

**判断はしない。** 恒久対処の方針決定は人間の判断点として残す（ポストモーテムの再発防止策）。

### 5. ポストモーテムを仕組みに還元する

再発防止策は「気をつける」で終わらせず、**必ず CI ゲート・フック・ルールのいずれかとして実装する**。既存の `CLAUDE.md`「AI が同じ間違いを繰り返した場合、原因と理由をルールファイルに 1 行追記する」を、インシデント全般に拡張する。

### 6. 配布物

| 対象 | 内容 |
|---|---|
| 計装 | OTel 最小実装、構造化ログの規約 |
| SLO | 定義ファイルの雛形（値は空） |
| ランブック | 雛形と記載項目の規定 |
| ポストモーテム | 雛形 |
| スキル | 一次トリアージ手順 |
| CI ゲート | 構造化ログ・trace_id・service.name の検査 |

## 理由

### OTel の位置づけ

OTel は計装のロックインを減らすが、ダッシュボード・アラート・ランブック・運用習慣までは移してくれない。データ収集層での乗り換えは容易になるが、ワークフロー層では依然として高くつく。計装の可搬性は本物だが、ワークフローの可搬性は弱い。

したがって「OTel で計装しておけばバックエンドは後から選べる」は正しく、監視 SaaS の選定を後回しにできる。一方で「後から無痛で乗り換えられる」は誤りであり、選定を無期限に先送りしてよいわけではない。

### SLO を先に決める理由

まず答えたい問いを定義し、その後でどれだけのログをどこに送るかを決める。2〜4 の主要なユーザージャーニーを選んで SLI（レイテンシ、エラー率、可用性）を導入し、その後でテレメトリのカバレッジを広げる、というのが推奨順序である。

観測可能性の目的は「データを持つこと」ではなく、良質なシグナル・一貫したセマンティクス・相関・自動化されたワークフローによって MTTR を下げ信頼性を上げることである。

### 相関可能性を必須にする理由

2026 年の AIOps は、AI が魔法のようにインシデントを解決することではなく、良質なテレメトリの上に乗る相関・支援レイヤーとして機能する。アラートの重複排除とグルーピング、サービストポロジーと変更に基づく根本原因候補、トレース／ログ／メトリクスストアへの自動クエリとランブックの提案、異常検知がその内容である。

そして条件が明示されている。**AI は、一貫して命名され接続されていないものを相関できない。** だからこそ Resource 属性、ログ内の trace/span ID、一貫した `service.name`、セマンティック規約が鍵になる。

**運用を AI に任せたいなら、計装の規約こそが最重要**である。これが基盤の担当範囲となる。

### 一次トリアージの形

実務パターンは、アラートが発火するとエージェントがコンテキストを集め、ログを照会し、関連するデプロイを取得し、関連する過去のインシデントを引き、トリアージ要約を作成し、構造化されたブリーフィングとともにオンコールを呼び出す、というものである。

### 監視 SaaS を基盤で決めない理由

小規模チームでは、社内のエンジニアリング労力を完全に計算に入れると、マネージド SaaS が一貫してフリーソフトウェアを上回るとされる。一人法人では自前運用は選択肢に入らないが、コストは想定データ量で見積もる必要があり、観測可能性データは急速に増える。プロジェクトの規模が見えてから決めるべき判断である。

## 注意事項

- 監視 SaaS 未選定のため、ADR-016 の自動ロールバックトリガーは指標源が決まるまで雛形のみとなる
- サンプリング方針は SaaS 選定時に決める。head-based のベースサンプリングと、エラーおよび高レイテンシを保持する tail-based の組み合わせが 2026 年の標準とされる
- 「Observability as Code」——テレメトリの完全性をデプロイ前に検証するテスト——が新しい潮流として挙がっている。決定 3 の CI ゲートはこれにあたる
- ランブックの雛形は配るが、内容はプロジェクト固有である。基盤側に具体的な手順を書かない

## 結果

- `profiles/_base/docs/runbooks/` と雛形を配布する
- `profiles/_base/docs/postmortems/` と雛形を配布する
- `profiles/_base/docs/slo.yaml`（値は空）を配布する
- product-web に OTel 計装の最小実装を配布する
- 構造化ログ・`trace_id`・`service.name` の CI ゲートを実装する
- 一次トリアージのスキルを配布する
- `docs/rules/operations.md` を新設する

## 未解決

- 監視バックエンド（SaaS）の選定。本番プロダクトのリリース後、実データ量が見えてから判断する
