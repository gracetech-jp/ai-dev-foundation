# ADR-016: リリース工程を定める — デプロイとリリースの分離・自動ロールバック

- 日付: 2026-08-03
- ステータス: 採用

## 背景

棚卸しの結果、リリース工程はルール・雛形・機械ゲートのすべてがほぼゼロだった。存在するのは `docs/rules/git.md` の「MVP フェーズ中は main 直 push を許可」と `docs/rules/quality-gates.md` の一文（build / deploy は全ジョブの成功を前提にする）のみ。

バージョニング、タグ付け、変更履歴、リリースノート、ロールバック手順、デプロイワークフローのいずれも存在しない。

この欠落は AI 駆動開発では致命的になる。組織の 72% が AI 生成コード起因の本番インシデントを経験し、一方で開発者の出荷速度は 63% 向上した（Harness, 2025）とされる。速度が上がった分だけ事故も増えるため、**リリース後の回復速度が決定的**になる。

DORA 2025 では、エリートチームは低パフォーマンスチームより 24 倍速く障害から回復し、リリース管理の規律がその分岐点だとされている。

## 決定

### 1. デプロイとリリースを分離する

フィーチャーフラグを導入し、デプロイ（コードを本番に置く）とリリース（挙動をユーザーに露出する）を切り離す。

**フラグ極性の規約**: Off = 既存・レガシーの挙動、On = 新規・将来の挙動。例外を認めない。

### 2. バージョニングと変更履歴を自動化する

Conventional Commits から semver の採番と CHANGELOG 生成を自動で行う。`commit-msg` フックで Conventional Commits は既に機械強制されているため、そのまま接続する。

### 3. 自動ロールバックトリガーを定義する

エラー率の上昇、レイテンシのスパイク、主要指標の低下に閾値を設定し、**人間の介入なしにロールバックする**。

閾値は設定ファイルとして各プロジェクトが持ち、雛形のみ基盤が配る。

### 4. 段階的デプロイ

一度に全ユーザーへ切り替えない。カナリアまたはリング展開とし、自動ヘルスチェックで昇格を判断する。

### 5. DB マイグレーションは後方互換を必須とする

新旧のコードが同時に動く期間が必ず存在するため、後方互換でないマイグレーションを禁止する。CI ゲートで検査する。

### 6. 本番リリースは人間が承認する

**人間の判断点として残す。** カナリア通過による自動昇格は採用しない。

### 7. 配布物

| 対象 | 内容 |
|---|---|
| デプロイ | GitHub Actions の deploy ワークフロー雛形 |
| バージョニング | Conventional Commits → semver / CHANGELOG の自動化設定 |
| フラグ | フラグ評価の最小実装と命名規約 |
| ロールバック | 自動トリガー閾値の定義ファイル雛形（値は空） |
| マイグレーション | 後方互換規約と CI ゲート |
| リリースノート | コミットと PR から生成する設定 |

## 理由

### デプロイとリリースの分離

フラグはデプロイとリリースを切り離し、新しいコードが本番デプロイに存在しながら実行されない状態を作る。これにより、長命ブランチなしのトランクベース開発、トラフィックの部分集合への段階的露出、値を反転させるだけの即時ロールバックの 3 つが可能になる。

フラグ極性の規約は事故を 1 クラス防ぐ。Off = レガシー、On = 新規を徹底すると「フラグを Off にする」が常に「動いていた状態に戻る」を意味し、これは深夜に対応するオンコール担当者が推論できる必要がある性質である。

### 自動ロールバック

カナリアもブルーグリーンも、自動ヘルスチェックと事前定義されたロールバックトリガーを必要とする。エラー率の上昇、レイテンシのスパイク、コンバージョンの低下にトリガーを設定し、人間の介入なしにシステムが回復するようにする。

これが自動化の核である。**ロールバックを人間の判断点に含めない**のはこのためである。

### Conventional Commits からの自動化

ブランチ保護規則を設定し、マージ前に最低 1 つの承認と CI 通過を要求する。Conventional Commits（`feat:` / `fix:` / `chore:`）を用いて CHANGELOG と semver を自動化する、というのが標準構成である。

### 後方互換マイグレーション

継続的デプロイのベストプラクティスに、後方互換な DB マイグレーションが明示的に含まれる。

### 本番承認を残す理由

AI エージェントの実務パターンでも、エージェントがドラフト PR を開きテストを走らせるところまでを担い、**マージは人間に残す**形が最もレバレッジが高いとされる。品質ゲートの原則も「承認なくばデプロイなし」である。

## 注意事項

- `docs/rules/git.md` の「MVP フェーズ中は main 直 push を許可」は、本番相当環境への初回リリースを切替条件の 1 つとしている。本番プロダクトの初回リリースがその地点にあたるため、ブランチ保護へ移行する
- トランクベース開発を前提とする。短命ブランチ（1〜2 日）で PR を経て main にマージし、main は常にデプロイ可能に保つ
- 段階的ロールアウトの各フェーズにセキュリティ検証を組み込む。セキュリティを別工程にしない
- 監視 SaaS が未選定のため、自動ロールバックトリガーは実際の指標源が決まるまで雛形のみとする（ADR-017）

## 結果

- `profiles/_base/.github/workflows/deploy.yml` を配布する
- `CHANGELOG.md` と semver 自動化の設定を配布する
- フラグの最小実装と命名規約を配布する
- ロールバック閾値の定義ファイル雛形を配布する
- マイグレーション後方互換の CI ゲートを実装する
- `docs/rules/release.md` を新設する
- `docs/rules/git.md` のフェーズ規定を更新する
- ブランチ保護と必須ステータスチェックを設定する
