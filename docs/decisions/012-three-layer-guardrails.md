# ADR-012: ガードレールを3層防御へ再編する — 本物の境界はコンテナ隔離だけ

- 日付: 2026-08-03
- ステータス: 採用
- 置換: ADR-009 の一部（共通所有ファイルのロック方式は維持、防御の主軸のみ変更）

## 背景

これまで防御の主軸を PreToolUse フック（`guard-dangerous.sh`、239行・テスト154ケース）に置いてきた。しかしこの層には構造的な弱点がある。

サブディレクトリから `claude` を起動すると `CLAUDE_PROJECT_DIR` が起動ディレクトリを指し、フックスクリプトが見つからず**無警告で素通しする**。対策として `guard-shim.sh` が実装されテストも通っているが、配布経路が存在せず実プロジェクトで一度も動いていない。

つまり R-001（Tier S）が守るはずの防御が、この経路で機能していなかった。

さらに `CLAUDE.md` は脅威モデルを「不注意であって悪意ある実行者ではない」と規定していたが、この前提は AI エージェント環境では成立しない。プロンプトインジェクションで生成されたコードは不注意ではなく敵対的である。

## 決定

### 1. 3 層防御に再編する

```
第1層  コンテナ隔離        ← 唯一の本物の境界。爆発半径を決める
第2層  permissions.deny    ← 事故防止。防御とは呼ばない
第3層  PreToolUse フック    ← 事故防止。防御とは呼ばない
```

第 2 層・第 3 層は「不注意による事故を減らす」ためのものと位置づけ、敵対的コードに対する防御としては数えない。

### 2. 脅威モデルを更新する

「不注意」から「実行時に生成され、実行前にレビューも信頼もできない任意のコード」へ変更する。

### 3. `guard-shim.sh` を廃止する

フックが主防御でなくなれば、フックの欠落は補助層の欠落に格下がりする。脆い層を中間層で補強するのではなく、脆い層に依存しない構成にする。

### 4. deny で表現できる判定は `permissions.deny` へ**追加**し、フックにも残す（二重化）

**（2026-08-04 改訂。当初は「フックを縮小し、移した判定はフックから削除する」だった）**

deny ルールで表現できる判定（`git push --force` / `git reset --hard` / `git clean -f` /
`git checkout` による破棄）は `permissions.deny` に**追加**する。ただし**フック側の判定は削除しない**。

冗長化を正当化する根拠は「片方が漏れるから」ではなく、**2つの層が独立に失敗する**ことである。

- 多層防御における冗長性は、**層が独立に失敗する場合に**正当化される（NSA の整理では、ある層で
  攻撃が可能なら別の層に冗長性が存在すべきとされる。原子力分野の定義はより厳密で、
  複数の「**独立かつ**冗長な」保護層を要求する）
- 反対原則として simplicity-in-security があり、**同一機能を同一理由で壊れる形で重複させること**は
  避けるべきとされる。重複そのものが善なのではない
- 本件の2層は独立に失敗する。**`permissions.deny` は例外を書けずに失敗し**（決定4の下の理由節）、
  **PreToolUse フックは見つからずに失敗する**（`CLAUDE_PROJECT_DIR` が起動ディレクトリを指す経路。
  背景節の fail-open）。失敗の原因が共通していないため、冗長化は simplicity-in-security の
  例外にあたる

したがってフックに残すのは「deny で書けないもの」だけではない。**deny で書けるものも、
失敗の仕方が違う限り残す**。

### 5. フックは fail-closed とし、第3層のブロック時は原因と回復手順を出力する

**（2026-08-04 限定。当初は「ブロック時のメッセージに『何が見つからなかったか』『どう直すか』を必ず出力する」と層を限定せずに書いていた）**

信頼を確立できないなら操作を拒否する。そのうえで:

- **第3層（フック）のブロック時は、原因と回復手順を出力する。** ここは自前のスクリプトなので制御できる
  （例: `jq` 不在時に「devcontainer の Dockerfile が jq を導入しているか確認してください」を出す）
- **第2層（`permissions.deny`）のメッセージは Claude Code 本体の仕様であり、こちらから制御できない。**
  拒否理由の文面もルール名の提示有無も本体が決める
- したがって**回復手順を伴わせたい判定はフック側に置く**

限定した理由は R-001 の題を「機械的遮断」→「事故防止」に直したのと同じで、
**要件が実態より強いことを主張し続けるほうが危険**だからである。
当初の文言のままでは「全てのブロックに回復手順が付く」という達成不能な約束が残る。

## 理由

### フックは最下層である

2026 年の AI エージェントセキュリティの整理では、フックはローカルの床であり、残りはハーネスと OS にあるとされる。権限の優先順位は deny ルール → ask ルール → PreToolUse フック → allow ルール → モード → コールバックであり、フックはモードより強い。

Claude Code 自体は権限プロンプトとフックを使い OS レベルの隔離を持たないため、最大限のセキュリティを得るには上から Docker 等を被せる必要がある。

サンドボックス化されたエージェントは、ホストへの無制限アクセスを持つエージェントと比べてセキュリティインシデントを約 90% 減らすという報告がある。

### 第 2 層も主防御にできない — 決定的なのは「例外の書き口が無い」こと

**（2026-08-04 改訂。当初の根拠は回避経路の列挙だったが、実装前の調査で前提が誤っていたことが判明した。
下の「根拠の訂正」を参照）**

`permissions.deny` は Claude Code 本体が強制するためフックより堅牢である。それでも主防御に
できない理由は、**deny ルールには例外を書く手段が無い**という一点にある。deny は allow より
常に優先され、否定も書けない。広い deny は、その中の正当な一点を通す方法を持たない。

policy-as-code のガバナンスでは、「**例外はどう扱われるのか**」に答えられない仕組みは
秩序ではなく混沌を生むとされる。禁止の表現力ではなく、例外の受け皿があるかどうかが分かれ目になる。

**本リポジトリのガードは例外の集合で成立している。**

| 判定 | 通さなければならない例外 |
|---|---|
| `.env` の読み取り遮断 | `.env.example` / `.sample` / `.template` / `.dist`、`process.env` / `import.meta.env` / `Bun.env` / `Deno.env`（言語構文であってファイルではない） |
| 鍵ファイルの読み取り遮断 | `id_rsa.pub` 等の公開鍵、`row.key` のようなプロパティアクセス |
| 共通所有ファイルの書き込み遮断 | 第1引数が `profiles/_base/` の `cp` / `rsync` / `install`（骨格同期。唯一の正規更新手順） |

これらの例外は、いずれも**直後の文字種・引数の位置・語の意味**で判別しており、
パターンマッチの語彙では表現できない。**例外の居場所が手続き的な層（フック）にしかない**。

例外を諦めて広い deny を置けば、正当な操作が止まり、回避策が常用され、ガードは形骸化する。
これは仮定ではなく、この基盤で 2026-07-25 と 07-26 に実際に起きた（`process.env` の誤遮断、
`ls /home/node/.ssh/` の誤遮断）。

第 2 層は「例外を持たない禁止」しか表現できず、第 3 層は見つからなければ黙って素通しする。
どちらも主防御に据えられない以上、本物の境界はコンテナしかない。

#### 根拠の訂正（2026-08-04・実装前の調査で判明）

当初この節は、次の4点を「実証された回避経路」として根拠に置いていた。
**このうち少なくとも上2点は、現行の Claude Code の仕様に照らして誤りである。**

- ~~Bash の deny ルールは相対パスしかブロックせず、絶対パスは完全に迂回する~~
  → Bash ルールは `*` を**任意の位置**で使える（先頭・中間・末尾）。「先頭一致のみ」ではない
- ~~`find` / `grep` のような間接的コマンドで迂回される~~
  → `find` の `-exec` / `-delete` が prefix ルールの対象外なのは事実だが、これは deny 固有の欠陥ではなく
  **どの層でも捕捉していない**（フック側にも `find` の判定は無い）。第2層を否定する根拠にはならない
- `Read()` の deny が設定されていても代替のツール経路（bash の `cat` 等）で読まれる
  → 事実。ただしこれは「`Read()` ルールが Bash に及ばない」という**適用範囲**の話であり、
  第2層そのものの限界ではない
- `echo` 経由のコマンドインジェクションが allowlist と権限プロンプトを迂回する（CVE-2025-54795）
  → 事実。ただし第3層も文字列検査であり同種の細工に弱い。**層の選択の根拠にならない**

あわせて、`permissions.deny` はシェル演算子（`&&` `||` `;` `|` `|&` `&` 改行）を解釈して
**各サブコマンドを独立に照合し**、先頭の環境変数代入も跨いで一致する。
したがって「`&&` 連結で deny をすり抜ける」も成立しない。

（出典: Claude Code 公式ドキュメント `code.claude.com/docs/en/permissions`。2026-08-04 に実物を取得して確認。
調査記録: `docs/audit/adr012-phase1-investigation-20260804.md`）

### 脅威モデルの更新根拠

AI エージェントのサンドボックス化が従来と異なるのは、実行されるコードが LLM によって実行時に生成され、実行前にレビューも信頼もできない点にある。これは脅威モデルを「バグから守る」から「任意の敵対的コードから守る」へ移す。

### 回復手順を必須にする理由

回復手順が文書化されていない fail-secure 制御はシャドー IT を生む。公式の経路が長く止まっていると、ユーザーは安全でない回避策を見つける。原則を適用した結果として制御が外されることを防ぐ。

## 注意事項

- 第 2 層・第 3 層を撤去するわけではない。位置づけを「防御」から「事故防止」に変えるだけである
- `permissions.deny` と PreToolUse フックは bypassPermissions 下でも有効。明示的な ask ルールはプロンプトを出し、`rm -rf /` と `rm -rf ~` はプロンプトを出し、あらゆるレベルの deny はブロックし、フックは終了コード 2 でブロックできる
- ADR-009 の共通所有ファイルロック自体は維持する。変更するのは防御の主軸のみ
- **検証手段そのものが「作動していない」ことがある。**（2026-08-04・実施して判明）
  二重化した判定を実測するチェックリストを作り、初回に流したところ、
  **項目1〜4 がすべて第3層（フック）で止まった**。フックの判定が先に走るため、
  **第2層の deny が全部消えていてもチェックリストは緑になる**——二重化の片側を
  一度も検証していなかった。層を切り分けられたのは、フックの読み取りコマンド一覧に
  `ls` が入っていない（`ls -la ~/.ssh/` を通すための意図的な除外）ことを利用した
  `ls -la .env` だけで、これはフックを素通りし第2層だけが止める。
  **検証手段の設計が本体だと決めた ADR で、その検証手段自体に穴があった。**
  教訓は「止まることの確認だけでは、どの層が止めたかを検証したことにならない」。
  チェックリストには**層を切り分ける項目**と**通ることの確認**を必ず含める
  （`scripts/verify-guardrails.md` の項目5〜7）

## 結果

- `guard-shim.sh` を削除する
- `tests/resolve-common.bats` の該当 6 ケースを削除する
- `.claude/settings.json` の `permissions.deny` を拡充する（`git reset --hard` はフラグ位置に依存しない形へ、
  `git clean` は全面 deny へ、`git checkout .` を追加、`rm` の主要な表記ゆれを追加）
- **`guard-dangerous.sh` の該当判定は削除せず残す**（決定4の二重化。当初の「縮小する」から改訂）
- R-001 の要件文を書き直す（防御の所在が変わるため）
- `CLAUDE.md` の脅威モデル記述を書き直す
- `docs/rules/security.md` の「静的検査の防御ライン」節を書き直す
- テスト 154 ケースを再編する
- 隔離境界の具体は ADR-013 で定める

### 実装前の調査で判明した、あわせて直すもの（2026-08-04 追記）

- **`CLAUDE.md` 30行目と `guard-dangerous.sh` のヘッダコメント（2〜6行目）の記述が不正確である。**
  「`permissions.deny` はコマンド先頭の文字列一致のみのため、`&&` 連結・変数プレフィックス・
  フラグの順序違いをすり抜ける」と書かれているが、現行仕様では Bash ルールは `*` を任意位置で使え、
  サブコマンド単位で照合し、先頭の環境変数代入も跨ぐ。**脅威モデルの書き直しとは別件として直す。**
  誤った前提のまま残すと、フックに残すべきものの判断を誤らせる
- **`git checkout` による破棄（判定 A6）を検証するテストが1件も無い。** 判定はフックに実装されているが、
  `tests/guard-dangerous.bats` の154ケース中に該当が0件だった。再編時に追加する
- **テスト再編の中心は「削除」ではなく「検証手段の設計」である。** deny ルールは Claude Code 本体が
  評価するため bats から検証できない。移管対象を直接検証している既存ケースは154中3件しかなく、
  削るものはほとんど無い。むしろ「deny に書いてあること」をどう機械検証するか
  （監査の検査層を足すか）が論点になる
- 詳細な判定ごとの可否・影響範囲は `docs/audit/adr012-phase1-investigation-20260804.md` に記録した

### 配布側への展開（2026-08-04 実施）

- **二重化の突合を配布する。** `profiles/_base/scripts/audit-consistency.sh` に検査(5)を実装した
  （基盤の検査(14)に相当）。基盤だけ検査があっても、生成プロジェクト側で deny が片側だけ消えれば
  誰も気づけない——**基盤だけ守られて配布先が守られない**状態は本 ADR の目的に反する。
  検査は「deny の実在」「フック定義・複製の再発」「共通 `.claude` のマウント」を常に見て、
  共通側フックとの突合はマーカーを解決できたときだけ行う（解決できないときは**理由を1行出す**。
  無言のスキップは作動していないゲートになる）
- **実測チェックリストを配布する。** `profiles/_base/scripts/verify-guardrails.md`（項目7 を含む）
- 配布された検査が実際に動くことは `tests/dist-guardrails.bats`（11ケース）が、
  **生成物に対して監査を走らせて**検証する（雛形を直接読むのではなく配布経路を通ったものを見る）
