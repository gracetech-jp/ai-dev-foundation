# ADR-012: ガードレールを3層防御へ再編する — 本物の境界はコンテナ隔離だけ

- 日付: 2026-08-03
- ステータス: 採用
- 置換: ADR-009 の一部（共通所有ファイルのロック方式は維持、防御の主軸のみ変更）

## 背景

これまで防御の主軸を PreToolUse フック（`guard-dangerous.sh`、239行・テスト154ケース）に置いてきた。しかしこの層には構造的な弱点がある。

サブディレクトリから `claude` を起動すると `CLAUDE_PROJECT_DIR` が起動ディレクトリを指し、フックスクリプトが見つからず**無警告で素通しする**。対策として `guard-shim.sh` が実装されテストも通っているが、配布経路が存在せず実プロジェクトで一度も動いていない。

つまり R-001（Tier S）が守るはずの防御が、この経路で機能していなかった。

さらに `CLAUDE.md` は脅威モデルを「不注意であって悪意ある実行者ではない」と規定していたが、この前提は AI エージェント環境では成立しない。プロンプトインジェクションで生成されたコードは不注意ではなく敵対的である。

## 決定

### 1. 3 層防御に再編する

```
第1層  コンテナ隔離        ← 唯一の本物の境界。爆発半径を決める
第2層  permissions.deny    ← 事故防止。防御とは呼ばない
第3層  PreToolUse フック    ← 事故防止。防御とは呼ばない
```

第 2 層・第 3 層は「不注意による事故を減らす」ためのものと位置づけ、敵対的コードに対する防御としては数えない。

### 2. 脅威モデルを更新する

「不注意」から「実行時に生成され、実行前にレビューも信頼もできない任意のコード」へ変更する。

### 3. `guard-shim.sh` を廃止する

フックが主防御でなくなれば、フックの欠落は補助層の欠落に格下がりする。脆い層を中間層で補強するのではなく、脆い層に依存しない構成にする。

### 4. `guard-dangerous.sh` を縮小する

deny ルールで表現できる判定は `permissions.deny` へ移す。フックには deny で書けないもの（引数の組み合わせ、パイプを跨いだ共起判定）だけを残す。

### 5. フックは fail-closed とし、回復手順を必須にする

信頼を確立できないなら操作を拒否する。ただしブロック時のメッセージに「何が見つからなかったか」「どう直すか」を必ず出力する。

## 理由

### フックは最下層である

2026 年の AI エージェントセキュリティの整理では、フックはローカルの床であり、残りはハーネスと OS にあるとされる。権限の優先順位は deny ルール → ask ルール → PreToolUse フック → allow ルール → モード → コールバックであり、フックはモードより強い。

Claude Code 自体は権限プロンプトとフックを使い OS レベルの隔離を持たないため、最大限のセキュリティを得るには上から Docker 等を被せる必要がある。

サンドボックス化されたエージェントは、ホストへの無制限アクセスを持つエージェントと比べてセキュリティインシデントを約 90% 減らすという報告がある。

### 第 2 層も主防御にできない

`permissions.deny` は Claude Code 本体が強制するためフックより堅牢だが、既知の回避経路が実証されている。

- Bash の deny ルールは相対パスしかブロックせず、絶対パスは完全に迂回する
- `find` / `grep` のような、拒否対象のファイル名パターンを含まない間接的コマンドで迂回される
- `Read()` の deny が設定されていても代替のツール経路で読まれる
- `echo` 経由のコマンドインジェクションが allowlist の正規表現と権限プロンプトを迂回する（CVE-2025-54795）

第 2 層も第 3 層も穴が実証されている以上、本物の境界はコンテナしかない。

### 脅威モデルの更新根拠

AI エージェントのサンドボックス化が従来と異なるのは、実行されるコードが LLM によって実行時に生成され、実行前にレビューも信頼もできない点にある。これは脅威モデルを「バグから守る」から「任意の敵対的コードから守る」へ移す。

### 回復手順を必須にする理由

回復手順が文書化されていない fail-secure 制御はシャドー IT を生む。公式の経路が長く止まっていると、ユーザーは安全でない回避策を見つける。原則を適用した結果として制御が外されることを防ぐ。

## 注意事項

- 第 2 層・第 3 層を撤去するわけではない。位置づけを「防御」から「事故防止」に変えるだけである
- `permissions.deny` と PreToolUse フックは bypassPermissions 下でも有効。明示的な ask ルールはプロンプトを出し、`rm -rf /` と `rm -rf ~` はプロンプトを出し、あらゆるレベルの deny はブロックし、フックは終了コード 2 でブロックできる
- ADR-009 の共通所有ファイルロック自体は維持する。変更するのは防御の主軸のみ

## 結果

- `guard-shim.sh` を削除する
- `tests/resolve-common.bats` の該当 6 ケースを削除する
- `guard-dangerous.sh` を縮小し、deny ルールへ移管する
- `.claude/settings.json` の `permissions.deny` を拡充する
- R-001 の要件文を書き直す（防御の所在が変わるため）
- `CLAUDE.md` の脅威モデル記述を書き直す
- `docs/rules/security.md` の「静的検査の防御ライン」節を書き直す
- テスト 154 ケースを再編する
- 隔離境界の具体は ADR-013 で定める
