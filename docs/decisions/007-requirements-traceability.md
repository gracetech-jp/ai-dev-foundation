# ADR-007: 要件トレーサビリティ基盤（人間批准・LLM封鎖・機械ゲート）

## 日付
2026-07-16（意思決定の記録日。Notion 上の記録を 2026-07-22 に本リポへ ADR-007 として転記。
作成順の連番であり、時系列では ADR-006 より前の意思決定）

## ステータス
採用済み・実装完了（本番CI緑）

## 背景
発端は「Opus で設計 → Sonnet で実装 → 全体レビュー、というパイプラインで、CIは緑なのに要件を
満たさない実装が当たり前に出る」という体感。

原因はモデルの性能ではなく構造にあった。**要件がLLMの生成ループの中で毎回作り直され、実装も
テストも同じ理解から作られるため、間違った理解に対して設計・実装・テスト・レビューの全員が
仲良く整合してしまう**。エンドポイント単位のテストが100%緑でも、それは「エンドポイントの
カバレッジ」であって「要件のカバレッジ」ではない。この2つは直交する。

## 決定
**要件を「LLMが毎回生成し直す派生物」から「人間が批准する永続・ID付きの一次成果物」に変え、
テスト・Tier・コードをそこに機械追跡させる。** 既存の作法（fail-closed・一方向ラチェット・
配布/逆輸入）をそのまま要件層へ横展開し、新しい思想は増やさない。quality-gates の「善意ではなく
機械ゲートで担保」という原則を、これまで抜けていた要件層にも延長しただけ。

核心は一貫して**「LLMの自己申告を単独で信頼するゲートを作らない」**。自己申告している箇所は、
人間批准かコード実態からの裏取りで閉じる。

## 記録すべき重要な設計判断

### 1. 共通リポは「機構のみ・固有ドメイン語ゼロ」が不変条件
ai-dev-foundation はアプリ実装を持たない共通基盤。特定サービスの制約語を、配布される実体
（既定値・テンプレ本文・スクリプト）に一語も焼き込まない。焼き込むと、その制約に該当しない
新規サービスを生成したときにゴミとして残存するため。具体の禁止事象は各サービスが
`docs/requirements/` と `SERVICE.md` に自分のドメイン語で書く。共通側は空欄フォーマットと
ルールと照合エンジンだけを配る。この純度は grep で機械的に検査可能な一線として維持する。

### 2. 自己申告点は三重に潰した
- **マーカー**（実装LLMがハッピーパスにも貼れる）→ Tier S/A は `tests_ratified_by`（人間の妥当性批准）を必須化。
- **Tier**（低く申告すれば全ゲート蒸発）→ human-ratified フィールド化＋トリップワイヤでコード実態から裏取り。
- **ベースライン**（最重要のS/Aを初日に恒久免除）→ S/A はベースライン登録不可（登録で exit 2）。
- **時間軸の穴**（批准後にテストを骨抜き）→ `tests_ratified_sha` のハッシュ照合で再批准を要求。

これらは front-matter の `tier` / `tests_ratified_by` を deny 対象ディレクトリ内に置くことで、
「昇格は人間の commit でしか起きない」を物理的に担保している。

### 3. G3の主防壁は CODEOWNERS＋サーバ側ブランチ保護
`settings.json` deny と `guard-dangerous.sh` は「穴の残る補助的多層防御」にすぎない
（interpreter の `open('w')` 等ですり抜けうる）。真の防壁は CODEOWNERS＋GitHub ブランチ保護だが、
これはファイル化できず手動設定。この位置づけを guard 自体のコメントと `docs/rules/git.md` に
明記し、過信を防いでいる。

### 4. この基盤自身が原則をドッグフーディングしている
基盤の破壊的操作ガードを R-001 として要件化し、bats テストに req マーカーで紐づけ、
人間（大澤将平）が批准してコミットした。基盤の「機微面なし」も人間が `.tier-tripwire-none` で
宣言。要件ディレクトリの中身は全て人間名義のコミットで揃えており、Co-Authored-By（LLM関与の
証跡）は付けていない。

## 検証（記録時点: 2026-07-16）
bats 33 green（本番CI含む）。全負例が回帰テストとして恒久登録済み（S/Aベースライン登録→exit 2、
機微シンボル混入→赤、削除による骨抜き→赤、批准後テスト改変→ハッシュ不一致で赤、機微fixture
骨抜き→再批准要求で赤 等）。最終検証で実バグ1件（配布テンプレ `R-000-template.md` の tier
プレースホルダ誤検出）を捕捉し、fail-closed を緩めない形（固定名除外＋回帰テスト）で修正済み。
本番CI 6ジョブ全緑（audit / lint / req-coverage / secret-scan / test / tier-tripwire）。

## 効いた考え方（再利用可能な教訓）
- 「モデルが信用できない」と感じたら、モデルを替えるのではなく「要件が生成ループの外側に
  アンカーされているか」を疑う。
- 検証で「動いた」（手動実証）と「壊れたら気づける」（回帰テスト恒久登録）は別物。後者にする。
- 除外ロジックは fail-closed を緩める方向に働きやすい。除外を足すときは「除外が効く」テストと
  「fail-closedが壊れていない」テストを必ずセットで登録する。
- 厚いスクリプトは要約でなく実物（cat）で照合する。この方針が実際に複数の実バグ
  （ハッシュ非決定・R_FILE暗黙前提・テンプレ誤検出）を捕まえた。
