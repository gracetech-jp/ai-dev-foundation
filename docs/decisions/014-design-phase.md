# ADR-014: 設計工程を定める — design.md 6節構成と CI ゲート

- 日付: 2026-08-03
- ステータス: 採用

## 背景

棚卸しの結果、設計工程には ADR の運用ルールしか存在せず、**機械ゲートがゼロ**だった。設計メモの雛形もない。

要件定義（`docs/requirements/`）と実装・テスト（req-coverage / tier-tripwire）は作り込まれているが、その間が欠落している。要件から直接実装に入ると、AI は構造の判断を暗黙に行い、記録に残さない。

記録がないことの実害は具体的である。あるエージェントが冗長に見えたミドルウェアをリファクタしたが、それは 2 年前の障害（90 分間に 4,200 人へ二重課金）の後に書かれた冪等性レイヤだった。PR はグリーン、レビュアーは若手、本番は 9 日間持ちこたえた後に同じ障害が再発した。

**「なぜこうなっているか」が書かれていないと、AI は善意で壊す。**

## 決定

### 1. 入力と出力

```
入力   requirements.md（要件定義から渡される）
出力   docs/design/<束>.md   束ごとに1本
       docs/adr/*.md          恒久的な判断（人間承認）
       AGENTS.md              守らせる制約（人間承認）
```

### 2. 要件を束ねてから設計する

設計の第一歩は、フラットな要件を実装可能なまとまりに束ねることである。

**主軸**: 一緒に変更されるものを同じ束に入れる
**補助**: 同じデータを読み書きするか（テーブルを共有するなら同じ束）
**大きさ**: 上限を設けない。大きめの束から始め、割る理由ができたら割る

「割る理由」とは、束の中で独立して変更される部分が実際に現れたときを指す。予測で先に割らない。

### 3. design.md は 6 節構成

1. **対象要件** — この束が満たす要件 ID（`R-xxx`）の列挙。受け入れ基準のサブ ID（`R-xxx-N`）ではない
2. **構成** — コンポーネントと責務
3. **データ** — スキーマ、型、状態遷移。他束との共有テーブルがあれば明記
4. **インターフェース** — エンドポイント、リクエスト／レスポンス、エラー応答
5. **主要な流れ** — 正常系のシーケンス。異常系は分岐点のみ
6. **判断と理由** — なぜこの構成か。**捨てた案も書く**

### 4. 書き分けの基準

| 内容 | 場所 |
|---|---|
| この束の中で閉じる判断 | design.md 第6節 |
| 他の束にも影響する判断 | `docs/adr/` |
| 恒久的に守らせたい制約 | `AGENTS.md` |

### 5. AI とのやり取り

```
【設計案】確定分のみ
【確認】判断が必要な分岐点
【保留】回答待ちで書けていない節
```

終了条件は確認と保留が両方空。設計は要件定義より確認が多くなるのが正常である。確認が少ない場合、AI が勝手に決めている。

### 6. 承認の所在

**design.md は CI 自動通過とする。人間が承認するのは ADR と AGENTS.md のみ。**

### 7. CI ゲート

| # | 内容 | 種別 |
|---|---|---|
| 1 | **前方向**: 全要件 ID がいずれかの design.md 第1節に現れる（網羅） | 形式 |
| 2 | **逆方向**: 各 design.md 第1節が空でなく、実在する要件 ID だけを参照する。空・不在 ID は**赤** | 形式 |
| 3 | 第6節が空でない。案A/案B の形式を満たす | 形式 |
| 4 | 別セッションの AI が「設計は第1節の要件を満たすか」を検証。要件IDごとに Yes/No/不明、1つでも No なら赤 | 内容 |
| 5 | 第3節に他束との共有テーブルがある / 要件1件だけの束 / 同じ要件 ID が複数の束の第1節に現れる → 警告 | 束の妥当性 |

ゲート 1・2 は**要件 ID（`R-xxx`）の粒度**で判定する（受け入れ基準のサブ ID ではない。後述）。

## 理由

### design.md を分割しない

実務では設計成果物を分割していない。Kiro は spec ごとに requirements.md / design.md / tasks.md の 3 ファイルを生成し、設計工程の出力は design.md 1 つである。その中身にデータフロー図、インターフェース定義、DB スキーマ、API エンドポイント定義に加えて主要な判断の理由（なぜセッションではなく JWT か等）が含まれる。

判断の記録・機械可読仕様・構造記述を分けると参照が分散し、AI が一部しか読まない。

### ADR を別レイヤーに置く

ADR は安定した ID を持たせて `/docs/adr/` に置くのが標準構成である。ADR は「次の読み手に経緯を伝える手段」であり、2026 年時点でその読み手はますます人間でなくなっている。

### AGENTS.md を成果物に含める

ADR は受動的な成果物であり、存在を思い出し、更新し、変更前に読むと自分で決めなければならなかった。AGENTS.md 系が違うのは能動的である点で、すべての AI 支援セッションが参照し、すべてのエージェント生成 PR に反映される。読むかもしれない文書ではなく、強制されるルールになっている。

設計で決めた「守らせたい制約」は AGENTS.md に落とす。

### 束ね方の根拠

「一緒に変わるコードは一緒に置く」は古典的な凝集度の原則であり、単一責任原則（モジュールは変更理由を 1 つだけ持つ）と結びつく。モジュール設計のゴールは、他を壊さずに 1 つのものを変更できることである。

大きさに上限を設けないのは、割りすぎの害が実証されているためである。コンテキストが多すぎることはアンチパターンであり、各コンテキストにはオーバーヘッド（別データストア、統合イベント、マッピング）があるため、少数の大きなコンテキストから始めて必要になったら割るべきとされる。分割を誤ると「分散モノリス」——物理的に分離されているが論理的には密結合——になり、変更のたびに複数箇所の協調更新が必要になる。

件数で機械的に割る基準には「一緒に変わるか」という判断が含まれないため採用しない。

### 要件の重複は「束ね方」の問題であって、トレーサビリティ違反ではない（2026-08-07 訂正）

当初この表には「同じ要件 ID が複数の design.md に現れない（重複なし）」を**形式ゲート**として置いていた。
**これは誤りだったので外す。** 根拠なく足した記述である。

RTM（要件トレーサビリティマトリクス）の標準では、**1つの要件が複数の設計要素にマップされることは正常**で
ある。正常な形をトレーサビリティ違反として赤にすると、赤が常態化して誰も見なくなる。

ただし観測そのものには意味がある。正しい理屈は「1要件が2束にまたがるなら、**その2束は一緒に変更される
はずであり、束ね方が間違っている**」——§2 の主軸（一緒に変更されるものを同じ束に入れる）に照らした
**束の妥当性**の問題である。したがってゲート5へ移し、警告として扱う。赤にしないのは、束を割るべきでない
のに割ってしまった疑いを示すだけで、割った結果が正当な場合もあるためである。

### 逆方向トレーサビリティをゲートに入れる（2026-08-07 追加）

双方向トレーサビリティが標準であり、**要件・テスト・実装成果物の間の双方向の対応を維持すること**が
トレーサビリティの本質的な構成要素とされる。当初のゲートは前方向（要件 → 設計）しか見ておらず、
**どの要件にも紐づかない設計を素通し**していた。

どの要件にも紐づかない設計は、AI が勝手に足したものである。§5 の「確認が少ない場合、AI が勝手に
決めている」と同じ失敗が、やり取りではなく成果物の側に現れた形にすぎない。

警告ではなく赤にするのは、**前方向のゲート1が赤である以上、逆方向だけ警告にすると片側しか強制されない**
ためである。網羅（要件に設計が付いているか）と根拠（設計に要件が付いているか）は同じ強度で見る。

### 要件 ID の粒度 — EARS 化の影響（2026-08-07 確認）

requirements.md が EARS 記法（`While〈前提条件〉, when〈トリガー〉, the〈システム名〉shall〈システム応答〉`）
に変わり、受け入れ基準に `R-001-3` のような**サブ ID** が付くようになった
（実例: `docs/requirements/R-001-guardrail-enforcement.md`）。

**要件 ID そのものは `R-<連番>` のまま不変**であり（`docs/rules/requirements.md` §1）、第1節の参照方法は
変わらない。ただし**サブ ID で書いてはならない**点が新たに効くので明記する。理由は機械照合の粒度である——
`check-requirements-coverage.sh` はマーカーから `R-[0-9]+` を抜き出すため、`R-001-3` は `R-001` に
丸められる。サブ ID で書いても検査は区別しないのに、書いた側は「受け入れ基準の単位で網羅した」と読める。
**記述と検査がずれるのが害**であって、粒度が細かいこと自体が害なのではない。

束が要件の一部の受け入れ基準しか担わない場合は、第1節には要件 ID を書き、どの基準を担うかを同節に
注記する。ゲート 1・2・5 はいずれも要件 ID の粒度で判定する。

### 適応的な厳密さ

すべての変更を同じ重量級の工程に通さない。AWS の AI-DLC も適応的な厳密さを原則とし、単純なバグ修正は計画を飛ばして直接コード生成へ、複雑な機能は要件分析・アーキテクチャ設計・テスト設計を通す。既存の Tier 分類（S/A/B/C）をこの振り分けに用いる。

### design.md を人間承認にしない理由

人間が読めない量のものを承認ゲートに置くと、形だけの承認になり仕組みが死ぬ。ADR は量が少なく（1 案件で数本）、影響が恒久的で、判断そのものであるため人間が握る。

## 注意事項

- ゲート 4（AI レビュー）は、実装したセッションと別セッションで行う。同じセッションの AI は自分の設計を甘く評価する
- 第 6 節に「捨てた案」がない場合、それは検討していないことを意味する。後から AI が「もっと良い方法がある」と作り替える事故はここが空だから起きる
- 要件定義では「機能でグルーピングしない」と決めている。設計の束は機能ではなく「一緒に変更されるもの」で切るため、この原則と矛盾しない

## 結果

- `profiles/_base/docs/design/` と README、`design.md` の雛形を配布する
- `profiles/_base/AGENTS.md` の雛形を配布する（`CLAUDE.md` から `@AGENTS.md` でインポートする形とする）
- 設計工程のスキル／スラッシュコマンドを配布する
- CI ゲート 5 種を実装し、reusable workflow に組み込む（ADR-011）
- 要件 ID と design.md の対応検証は既存の req-coverage の仕組みを拡張して実装する
