# ADR-013: devcontainer を隔離境界として再設計し、その内側で bypassPermissions を既定にする

- 日付: 2026-08-03
- ステータス: 採用
- 関連: ADR-012（3層防御の第1層にあたる）

## 背景

ADR-012 で、本物の境界はコンテナのみと結論した。しかし現在の devcontainer は「開発環境」として設計されており、隔離境界としては設計されていない。

素の devcontainer で隔離されるもの・されないものは次の通り。

| | 状態 |
|---|---|
| ファイルシステム | 隔離される（ホストのファイルにアクセス不可） |
| プロセス | 隔離される |
| パッケージインストール | 隔離される（コンテナ内に留まる） |
| **ネットワーク** | **隔離されない（既定で外向き全開放）** |
| git identity | `~/.gitconfig` を読み取り専用マウント |
| SSH エージェント | ソケット転送。鍵はホストに残る |
| Docker ソケット | 既定ではマウントしない |

最大の穴はネットワークである。認証情報の窃取は、環境内で読めるもの（`~/.aws/credentials`、Stripe キー入りの `.env`、GitHub トークン）が cat 一発で外へ出るコンテキストに載ることで成立する。

## 決定

devcontainer を隔離境界として再設計し、その内側で `bypassPermissions` を既定とする。

### 構成

| 項目 | 設定 |
|---|---|
| 外向きネットワーク | 既定拒否 + 許可リスト（Anthropic API、必要なパッケージレジストリ） |
| 本番のクラウド認証情報 | コンテナに入れない。短命トークンまたは外部で解決 |
| SSH 秘密鍵 | ホストに残す |
| ホームディレクトリ | マウントしない |
| 他プロジェクト | マウントしない |
| Docker ソケット | マウントしない |
| 実行ユーザー | 非 root |
| 権限モード | `permissions.defaultMode: bypassPermissions` |
| MCP サーバー | `mcp__*` を `ask` に登録し、未知のサーバーを既定で確認対象とする。禁止すべきサーバーが現れた時点で個別に `deny` を追加する（2026-08-04 実装時に確定） |

### ファイル構成

```
.devcontainer/
  devcontainer.json    マウント・拡張・設定
  Dockerfile           イメージとツール
  init-firewall.sh     起動時のネットワーク規則
```

## 理由

### 隔離は自動化の前提条件である

Anthropic の devcontainer ドキュメントは、コンテナの強化されたセキュリティ対策により無人運用のために `--dangerously-skip-permissions` を安全に実行できると明記している。

因果は逆である。隔離するから手作業が増えるのではなく、**隔離するから権限確認を全て飛ばせる**。

Anthropic の Safeguards チームの研究者は、2026 年 2 月に Rust ベースの C コンパイラを構築する 16 並列エージェントを `--dangerously-skip-permissions` で動かしている。付記は「これは実際のマシンではなくコンテナで実行すること」。

bypass モードの正当な使用ケースの共通点は、人間の確認ループが、人間がいないため不可能であるか、環境が既に封じ込めを担っているため冗長であるか、のいずれかとされる。本構成は後者にあたる。

### ネットワーク既定拒否

推奨は、外向き既定拒否とし Anthropic API と実際に必要なパッケージレジストリだけを許可リストに入れること。Anthropic の参照実装も、許可ドメインのみへの外向き接続に制限し、DNS と SSH は許可、それ以外は既定拒否、コンテナ初期化時にファイアウォール規則を検証する構成である。

### 認証情報の渡し方

推奨は、非 root ユーザーで実行し、意図したワークスペースだけをマウントし、クラウド認証情報はホストの認証情報ファイルをマウントするのではなくワークロードアイデンティティ、Codespaces シークレット、短命の環境変数で渡すこと。

### 隔離ティア

リポジトリごとに隔離ティアを選ぶ。低リスクは既定権限とサンドボックス、本番・規制対象は devcontainer / VM / クラウド実行。本番の顧客データを扱うプロダクトは後者に該当する。

## 注意事項

- **限界がある。** devcontainer は相当な保護を提供するが完全ではない。`--dangerously-skip-permissions` で実行した場合、悪意あるプロジェクトがコンテナ内でアクセス可能なもの（Claude Code の認証情報を含む）を持ち出すことは防げない
- バインドマウントされたワークスペースはホスト上に直接現れる。コンテナ境界は正確なマウントモデルを軸に設計する
- **MCP ツール呼び出しは bypass モードで自動承認される。** MCP サーバーがデータベース、デプロイシステム、外部 API に触れる場合、それらが無人で実行される。`ask` の `mcp__*` で捕まえるか、コンテナ内でのみ動かす。**`deny` を先に書くことはしない**（2026-08-04 実装時に確定）。現時点で禁止すべきサーバーが存在せず、空のルールを置いても実効性が無いためである。効いているのは「未知のサーバーを既定で確認対象にする」側であり、禁止すべきサーバーが現れた時点で個別に `deny` を足す
- パッケージマネージャを一括許可しない。`uv run` は後続を何でも実行し、`npm install <pkg>` はインストールスクリプトを走らせる。内側のコマンドまで固定する（既存の `ask` 設定の方針を維持する）
- ロールバック手段は git 履歴である。通常は権限システムが担う安全網を git が引き受ける
- Claude Code は認識済みサンドボックス環境内では root チェックを自動的にスキップする。`sudo claude` ラッパーで回避してはならない

## 人間の作業量への影響

| 項目 | 増減 |
|---|---|
| push をホストから実行 | 増分なし（既に人間実施） |
| 許可ドメインの追加判断 | 新規依存導入時のみ |
| ネットワーク遮断の切り分け | 初期構築時に集中 |
| **権限確認のクリック** | **消滅（減少）** |
| **git fetch / pull をホストから実行** | **増加**（2026-08-04 追記・同日修正。`github.com` を許可リストに入れないため、コンテナ内から SSH のリモート操作ができない） |
| **MCP ツール呼び出しの確認** | **増加**（2026-08-04 追記。`ask` の `mcp__*` は bypass 下でも発火する） |

**結論（2026-08-04 改訂）: 「差し引きで減る」は言い過ぎだった。**

当初はこの表を「権限確認のクリックが消える分、差し引きで減る」とまとめたが、実装時に前提が2つ変わった。

- **git のリモート操作がコンテナ内でできなくなる**ことを数えていなかった。`origin` が SSH の
  リポジトリでは `git fetch` / `git pull` がホストへ移る。push は元々ホスト実施なので増分ゼロと
  見ていたが、fetch/pull は日常操作であり、ここは明確に増える。

  **原因の訂正（2026-08-04・手順10 の裏取りで判明）**: 当初これを「`~/.ssh` を貼らないため」と
  書いたが、実測すると失敗は認証エラーではなく `No route to host`——**ファイアウォールの
  REJECT が先に効いている**。`github.com:22` への TCP 接続そのものが落ちる。したがって
  仮に鍵を貼っても、`github.com` が許可リストに無い限り fetch は通らない。原因は
  「鍵が無い」ではなく「宛先が許可されていない」（両方が重なっている）。
  運用上の結論は変わらない——**リモート操作はホストで行う**。
- **MCP の扱いが決まった**（2026-08-04）。`bypassPermissions` は明示的な `ask` ルールだけは
  素通りしないため、`ask` に `mcp__*` を置くことで未知の MCP サーバーにも実行時の歯止めが掛かる。
  これは意図した設計だが、**MCP に関しては「権限確認のクリックの消滅」が成立しない**。

正しい要約は「**Bash・ファイル編集の権限確認は消え、その代わりに git のリモート操作と MCP 呼び出しが
人間の手に残る**」である。総量が減るか増えるかは作業の内訳によって変わる。
それでもこの構成を採るのは、作業量ではなく**爆発半径**が判断軸だからである（ADR-012）。

## 結果

- `profiles/_base/.devcontainer/` に `init-firewall.sh` を追加する
- `devcontainer.json` のマウントをプロジェクトディレクトリのみに絞る
- `.claude/settings.json` に `permissions.defaultMode: bypassPermissions` を設定する
- MCP サーバーの `ask` ルール（`mcp__*`）を追加する
- `common/docker/Dockerfile.base` を非 root 前提で見直す
- 許可ドメインリストを要件として管理する（変更時に監査対象とする）

## 未解決

2026-08-04 の実装（手順1〜10）完了時点で残っているもの。優先度順。

- **【最優先】ホストの Docker ソケットを共有している構成（第1波完了後に対応する）。**
  ここだけは「未着手」ではなく**第1層が成立していない**状態であり、他の3件とは重みが違う。
  **ソケットを渡した時点で、本 ADR のネットワーク遮断もマウント制限も意味を失う**——
  ソケットが使えるならコンテナの設定を任意に上書きして起動できるため、隔離の前提そのものが崩れる。
  これはホスト root 相当の権限を与えることと同じであり、`docker-outside-of-docker` のような
  「開発の便利さ」のために有効化される機能が、そのまま第1層の無効化になる。
  **したがって隔離境界を主張するプロジェクトでは、ソケット共有を選択肢に入れない。**
  ただし既にソケット前提で組まれたビルド・テストの導線がある場合、外すと `make` の多くの
  ターゲットが動かなくなるため、docker-in-docker への移行を含めて別途設計が要る。
  該当構成の追跡は非公開の運用記録で行う（本 ADR には具体を書かない。ADR は公開資産であり、
  未修正の弱点の所在を記すと「どこを狙えばよいか」を示すことになるため）。
- **既存プロジェクトへの伝播（第1波完了後に対応する）。**
  今回の実装は基盤リポ自身と雛形（`profiles/`）のみを対象とした。
  雛形が正しい形になったので、伝播は雛形との差分を当てる作業になる。
  どのプロジェクトが未適用かは非公開の運用記録で追跡する。

- **生成物（product-web / product-static）での許可ドメイン実測は未実施。**
  許可リストの実測は基盤リポの devcontainer でのみ行った（2026-08-04・記録は
  `docs/audit/adr013-egress-verification-20260804.md`）。生成物は `uv` / `pnpm` を使うため
  `pypi.org` / `registry.npmjs.org` が実行時に要る可能性が高いが、**現在の許可リストでは
  どちらも遮断される**（実測で確認済み）。コンテナ内で依存追加を行う運用にするなら、
  実測のうえ許可リストへの追加が要る。ビルド時（`docker build`）は遮断前なので影響しない。

- **VS Code 拡張の取得先は許可しない（現状維持の判断。2026-08-04・未着手ではない）。**
  `marketplace.visualstudio.com` / `vscode.blob.core.windows.net` /
  `update.code.visualstudio.com` は参照実装には入っているが、こちらの構成で必要になった実測が
  無いため入れていない。拡張の追加・更新で詰まった時点で、失敗したエラーを根拠に1行足して
  Rebuild する。**「今は要らない」の記録であって、対応待ちの課題ではない。**
