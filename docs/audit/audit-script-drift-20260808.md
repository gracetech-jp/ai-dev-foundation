# audit-consistency.sh のテンプレートドリフト — 調査と提案（2026-08-08）

基盤に検査を足しても既存プロジェクトへ届かない問題の整理。**提案のみ。実装はしていない。**

結論を先に書く。

- **ドリフトは「2件溜まっている」ではなく、リポジトリごとに性質が違う。** grace-tech-hp は
  **5件欠落**、sumai-desk は**そもそもテンプレ由来ではない**（同期という枠組みが当てはまらない）
- **「分離はあと一歩」という見立ては、雛形については概ね正しく、実在プロジェクトについては
  当てはまらない。** 雛形の共通検査5本のうち4本は既に共通スクリプトの薄いラッパだが、
  1本（ガードレール二重化）は未抽出で、しかも基盤側と**二重実装**になっている
- **集約は「届く先を作る」作業ではない。** 集約しても、一度は各プロジェクトを触る必要がある。
  集約が効くのは**その後の追加**に対してである
- 選択肢のうち ADR-010 と整合するのは**集約＋ドリフト検出**のみ。同期ボットとサブモジュールは
  どちらも「複製を前提にした延命」で、ADR-010 の決定と逆を向く

## 2. 見立ての検証 — 「あと一歩」はどこまで正しいか

**正しい部分。** 雛形の検査6・7・8・9 は、共通スクリプトを呼ぶだけの薄いラッパである
（解決ボイラープレート＋読めるかの分岐＋1行の呼び出し）。判定ロジックは既に共通側にあり、
複製されているのは確かに**呼び出し側だけ**である。

**足りない部分は3つある。**

**(a) 検査5 が未抽出で、しかも二重実装になっている。**
雛形の検査5 と基盤の検査14 は**同じ概念の別実装**で、判定の正本である `DUAL_LAYER` 配列
（`A2:Bash(git push:*)` など）を**両方が持っている**。基盤の検査14 自身が
「新しい正本ファイルは作らない。作ると4箇所目の重複になる」と書いているのに、
配布側にもう1つ実装が生えている。集約の前に、これを
`common/scripts/check-guardrail-duplication.sh` として1本に抽出する必要がある。

**(b) 解決ボイラープレートが呼び出し側に残る。**
マーカー `.ai-dev-foundation-root` の上方探索と「見つからない／読めない」の分岐は、
どのプロジェクトにも約12行のまま残る。これ自体は避けられない（プロジェクトは共通側の位置を
自力で知る必要がある）が、**検査を足すたびに増えない形**にはできる。現状は共通検査ごとに
`xx_script=...` の分岐が並ぶので、検査を足すと呼び出し側も伸びる。

**(c) 実在プロジェクト2本は、集約しても自動では届かない。**
grace-tech-hp は共通ラッパを4本とも欠いており、sumai-desk は1本も持たない。
**集約は「届く先」を作らない。** 一度は各プロジェクトを触って呼び出しを入れる必要がある。
集約が効くのは**それ以降の追加**に対してである。

> したがって見立ては「**雛形については概ね正しい。実在プロジェクトについては当てはまらない**」。
> 「あと一歩」で完成するのは配布経路の設計であって、配布された結果ではない。

## 3. 検討1 — 共通検査の呼び出しを集約できるか

**できる。** 形は既存の `run-gates.sh`（ゲートを列挙して soft/hard を判定する共通スクリプト）
と同じで、先例がある。

### 3-1. 提案する形

新設: `common/scripts/run-common-audits.sh <project-root>`

- 共通検査を**このファイルの中で列挙**して順に実行し、結果をまとめて返す
- プロジェクト側の `audit-consistency.sh` は、**解決ボイラープレート＋1行の呼び出し**だけを持つ
- 新しい共通検査を足すときは `run-common-audits.sh` に1行足す。
  **呼び出しを持つ全プロジェクトへその場で届く**（複製の更新が要らない）

前提として、次の1件を先に片付ける。

- `check-guardrail-duplication.sh` の抽出（雛形の検査5 と基盤の検査14 を1本に統合）。
  これをやらないと「共通検査の集約」に穴が1つ空いたままになる

### 3-2. 障害になり得るもの（実測で確認した）

| 障害 | 実態 | 影響 |
|---|---|---|
| CI で共通側が見えるか | **reusable workflow は基盤を `path: .` に checkout する**ので見える | reusable 利用時は CI でも共通検査が走る |
| 実在2本の CI | **どちらも reusable 未使用**。composite action（`@v1`）だけを使っており、基盤リポの木は checkout されない | **この2本では共通検査が CI で ℹ スキップされる**。ローカル（pre-push）でしか働かない |
| 番号体系の衝突 | 共通も固有も同じ `(N)` 空間を使っている | 共通側に検査を足すと固有側の番号とぶつかる（後述） |

**CI 到達性の非対称は集約では解けない。** これは ADR-011 の reusable 移行が済むまで残る問題で、
本件とは別軸である。集約の価値は「新しい検査が届くようになる」ことで、
「CI でも走る」は reusable 移行が引き受ける。**混ぜて語らないこと。**

## 4. 検討2 — プロジェクト固有の検査をどう残すか

固有検査は**そのまま残す**。触る必要はない。構造だけを2部構成に固定する。

```
scripts/audit-consistency.sh
  [前半] 共通基盤の解決 → run-common-audits.sh を1行で呼ぶ
  [後半] このプロジェクト固有の検査（sumai-desk の【1】〜【14】がそのまま入る）
```

**番号体系を分けることが要点である。** 現状は共通も固有も `(N)` を共有しているため、
共通側に検査を1本足すと固有側の番号が全部ずれるか、衝突する。
共通側は共通側で採番し（例 `C1..Cn`）、固有側はプロジェクトが自由に採番する。
sumai-desk が `【N】` を使っているのは偶然だが、結果的にこの衝突を避けている。

**sumai-desk の【15】（git フック）は削除して共通側へ寄せる。** 独自実装を残すと、
共通側の `check-git-hooks.sh` を直しても sumai-desk には反映されない——
まさに本件と同じ構造の問題を、検査1本の粒度で再生産することになる。

## 5. 検討3 — ドリフト検出

集約しても「古い呼び出しのままのプロジェクト」は残る。検出は**2段構えが要る**。

### 5-1. 呼び出しの実在を見る（プロジェクト側）

`run-common-audits.sh` が**自分が呼ばれたこと**を前提にできないため、
プロジェクト側の監査が共通呼び出しを含むかは、プロジェクト側からは検証できない
（呼ばれていなければ何も走らない＝無音）。

**したがって「呼ばれているか」は CI 側の契約で見る。** `required-checks.txt` と同じ発想で、
プロジェクトが「共通監査を通した」と宣言し、その宣言と実装の一致を見る。

### 5-2. 版のずれを見る（共通側）

`run-common-audits.sh` に**契約番号**（検査の集合を表す整数）を持たせ、
プロジェクト側の呼び出しが期待する番号を渡す形にすると、
「共通側が進んだのにプロジェクト側が古い」を機械で検出できる。
`foundation-ref` の二重記述検査（基盤の検査17）と同じ手口である。

### 5-3. 基盤側から一括で見る案 — **成立しない**

「基盤の監査が `projects/*/scripts/audit-consistency.sh` を読んでドリフトを検出する」案を
検討したが、**採れない**。

`projects/` は基盤リポの `.gitignore` に入っており（`.gitignore:21` の `/projects/`）、
**追跡ファイルは0件**である。基盤の CI checkout には `projects/` が存在しないため、
この検査は**開発者のローカルでしか動かない**。
ローカルでしか動かない検査を「機械で守っている」と数えないこと——
本基盤が繰り返し潰してきた「作動していないゲート」の一形態である。

補助的な気付き役としてなら価値はある（ローカルの `make audit-all` で警告を出す）。
その場合は**警告に留め、赤にしない**。CI で再現できない赤は運用を止める。

## 6. 検討4 — 選択肢の比較

| 選択肢 | ADR-010 との整合 | 判断 |
|---|---|---|
| **集約＋ドリフト検出** | **整合する。** 判定の実体は共通側に1つ、プロジェクトは参照するだけ | **推奨** |
| 同期ボット（PR 経由で伝播） | **逆行する。** 複製の存在を前提に、複製の更新を自動化する仕組みである。ADR-010 は「複製を持たない」と決めた | 採らない |
| サブモジュール | **見かけ上は参照だが実質は複製。** 各リポジトリが pin した commit を持つため、**複製と同じ更新遅延**が発生する。加えて `projects/` が基盤配下という現在の配置と経路が二重になる | 採らない |
| 手動更新を運用として明記 | 整合はするが、**単独では機能しない実績がある**。検査8・9 が届かないまま溜まった | 単独では不可 |

**同期ボットについて補足する。** 呼び出し側の1行（解決ボイラープレート）だけは、
どうしてもプロジェクト側に置くしかない。この1行の伝播にボットを使う案はありうるが、
**1行のためにボットを持つのは割に合わない**。1行は変わらない設計にできる（3-1）ので、
変わらないものに同期機構は要らない。

## 7. 進め方の案（段階）

実装は別途判断する。順序だけ示す。

| 段階 | 内容 | 効果 |
|---|---|---|
| 1 | `check-guardrail-duplication.sh` を抽出（雛形5 と 基盤14 の二重実装を解消） | 共通検査が全部スクリプト化される |
| 2 | `run-common-audits.sh` を新設し、雛形と基盤の呼び出しを差し替え | 以後の追加が雛形へ自動で届く |
| 3 | grace-tech-hp に呼び出しを入れる（欠落5件が一度に埋まる） | 実在プロジェクトへ届く |
| 4 | sumai-desk に呼び出しを入れ、【15】を削除 | 独自実装の再生産を止める |
| 5 | ドリフト検出（契約番号）を入れる | 次のずれを無音にしない |

段階3・4は**別リポジトリなので基盤からは実施できない**。各プロジェクトのセッションで行う
（`check-internal-reachability.sh` のステップ2 と同じ制約）。手順は §9・§10。

**段階1・2 は 2026-08-08 に実装済み。** 以下が入った。

- `common/scripts/check-guardrail-duplication.sh`（抽出。基盤(14)と雛形(5)を1本化）
- `common/scripts/run-common-audits.sh`（集約。契約番号 `COMMON_AUDIT_CONTRACT=1`）
- 基盤と雛形の `audit-consistency.sh` を2部構成へ（共通は番号を持たない／固有は `(P1..)`）

### 7-1. 抽出で1点だけ挙動が変わった（承知のうえ）

以前、雛形の検査(5)は**共通基盤が解決できない状況でも第2層（deny の実在）だけは検証していた**。
判定が雛形にインライン複製されていたからである。共通側へ抽出した結果、
**共通基盤が解決できないときは共通監査そのものが走らない**（スクリプトが共通側にあるため）。

検査 6〜9 は元からこの挙動だったので、抽出によって5も揃った形になる。
通常の CI では問題にならない——雛形の `ci.yml` は reusable workflow を使い、
それが共通基盤を `path: .` へ checkout する。ここに来るのは単独チェックアウトのときだけである。
**黙って飛ばさず理由を1行出す**点は維持した（`tests/dist-guardrails.bats` が固定している）。

これを取り戻すには共通監査を composite action として同梱する必要があり、
それは「参照にできない複製」（基盤の検査(10) `MIGRATION_PAIRS`）を1つ増やす判断になる。
**今回は採らない。** 必要になるのは reusable を使わない CI を持つリポジトリだけで、
それは §10 の移行で解消される。

## 9. 段階3 — grace-tech-hp（雛形由来・5件欠落）への適用手順

**性質: 差分適用。** 雛形から生成された構造を保っているので、雛形の前半部分をそのまま移植できる。

1. `scripts/audit-consistency.sh` の先頭（`report()` 定義の直後）へ、雛形と**同じ前半ブロック**を入れる
   （マーカーの上方探索 → `run-common-audits.sh` を `"$ROOT" 1` で呼ぶ → 解決できないときは ℹ）。
   雛形 `profiles/_base/scripts/audit-consistency.sh` からそのまま写す
2. 既存の検査 (1)〜(4) を `(P1)`〜`(P4)` へ改番する。共通側と番号空間を分けるため
3. `make audit-all` を回す。**5件の欠落が一度に埋まるので、最初は赤になる可能性が高い**。
   とくに次を確認する
   - ガードレール二重化: `.claude/settings.json` の deny が9本そろっているか
   - git フック: `make install-hooks` で相対リンクに張り直したか（絶対リンクなら赤）
   - identity: `.git/config` に `user.*` のローカル上書きが無いか
4. 緑になったらコミットする

**注意**: このリポジトリの CI は composite action だけを使っており共通基盤を checkout しない。
したがって共通監査は**ローカル（pre-push）でのみ走る**。CI でも走らせるには §10 の reusable 移行が要る。

## 10. 段階4 — sumai-desk（最初から別物）への適用手順

**性質: 移植。** 雛形由来ではなく番号体系も `【N】` で、共通検査を1本も持たない。
差分を当てるのではなく、前半を**新設**して固有部分を後半へ残す。

1. `scripts/audit-consistency.sh` の先頭へ、雛形と同じ前半ブロックを**新設**する
   （既存の `【1】`〜`【14】` はそのまま。番号体系が違うので改番は不要——
   `【N】` と共通監査は最初から衝突しない）
2. **`【15】` git フックの独自実装を削除する。** これは共通 `check-git-hooks.sh` と同じ判定を
   別実装で持っており、共通側を直しても反映されない。**本件と同じ構造の問題を検査1本の粒度で
   再生産している。** 共通監査に含まれるので消してよい
3. `make audit` を回して緑を確認する。新たに走り始めるのは次の5件
   - ガードレール二重化 / 必須チェック宣言 / ref 一致 / git フック / identity
4. **`.github/required-checks.txt` が無い**ため、必須チェック宣言の検査は
   「宣言ファイルが無い」で赤になる可能性がある。先に宣言を用意するか、
   検査の出力を見てから判断する（ブランチ保護はプラン制約で設定できないが、
   宣言と実装の一致は宣言だけで検証できる）
5. 緑になったらコミットする

**注意**: §9 と同じく、このリポジトリの CI も共通基盤を checkout しない。共通監査はローカルのみ。

## 11. 契約番号の運用

`run-common-audits.sh` の `COMMON_AUDIT_CONTRACT` は**共通検査の集合の版**である。

- 共通検査を追加・削除したら**必ず上げる**。上げ忘れると、呼ぶ側は古い宣言のまま緑になり、
  ドリフト検出が空回りする（検査を足したのに誰も気づかない、という本件と同じ形に戻る）
- 上げると、宣言が古いリポジトリは**赤になる**。これは意図した挙動である。
  新しい共通検査はプロジェクト側の準備（宣言ファイル等）を要することがあり、
  **黙って未判定になるほうが害が大きい**
- 直し方は「新しい検査を確認して呼び出しの数字を上げる」だけで、その場で閉じられる。
  外部要因の赤（依存の脆弱性 DB など）とは性質が違う

- 固有検査の中身の妥当性は見ていない。触るのは構造だけ
- 実装は行っていない
