# 公開前セキュリティ確認（`ai-dev-foundation` を public にするにあたって）

作成日: 2026-08-04 ／ 対象: 全78コミット・全ブランチ（`main` / `feature/adr-013-devcontainer-isolation` /
`worktree-review-fixes-adr008-009`）・タグ `v1`・未コミットの作業ツリー
**公開操作は行っていない。** 本書は確認結果と提案のみ。

## 0. 検査手段の制約（先に明示する）

**gitleaks は実行できなかった。** この devcontainer には `docker` も `gitleaks` バイナリも無く
（ADR-013 で Docker ソケットを渡さない決定をしたため）、`ghcr.io` も許可ドメイン外で取得できない。

代わりに **git 履歴全体（`git log --all -p`）に対する正規表現スキャン**を実施した。
対象パターン: AWS アクセスキー / GitHub トークン（`ghp_` `github_pat_`）/ Slack / Stripe /
Anthropic API キー / Google API キー / PEM・OpenSSH 秘密鍵ヘッダ / JWT / `password=` `secret=`
`api_key=` `token=` の代入形 / 通知サービスのトピック / ECR レジストリ URL。

**gitleaks 相当の網羅性は保証できない。** 公開直前にホスト側で下記を実行して裏を取ること。

```bash
docker run --rm -v "$PWD:/repo" ghcr.io/gitleaks/gitleaks:v8.18.4 detect --source=/repo --redact --no-banner
#                                                            ↑ --no-git を付けない＝全履歴が対象
```

## 1. 公開前に対処すべきもの（優先度順）

### ✅ P1（解消済み）: 通知トピックが履歴に残っていた（実際の秘密）

| 項目 | 内容 |
|---|---|
| 値 | （伏せる。通知サービスのトピック名1件。実値はコミット `2f56676` の diff にある） |
| 所在 | コミット `2f56676`（2026-07-12 導入）〜 `0a885f2`（同日、環境変数参照へ切り出し） |
| 現在の HEAD・作業ツリー | **残っていない**（除去済み） |
| なぜ秘密か | このサービスのトピック名は**事実上のパスワード**。知っている者は誰でも購読でき（＝通知内容をすべて読める）、publish もできる（＝偽の通知を送れる）。本リポジトリの運用ルールでも秘密扱いとし `settings.local.json` の env で各自管理と決めている |
| 公開時の影響 | 承認待ち・タスク完了の通知内容が第三者に読まれ、通知を偽装される。**通知が来ない／偽の通知が来る**状態は、承認フローの信頼性を直接損なう |

**解消（2026-08-04・実施済み）: 提案1・2 のいずれでもなく、機能ごと廃止した。**

`bypassPermissions` を既定にした結果、**承認待ち通知（Notification フック）が鳴る場面が消えた**。
残るのは完了通知だけで、そのために ①外向きの宛先を1つ開け続け ②トピック名を秘密として管理し続ける
のは割に合わない。したがって通知フックを削除し、許可ドメインからも外した。

**購読先が存在しなくなるため、履歴に残った値は無意味になる**（ローテーションと同じ効果を、
管理対象そのものを消す形で得た）。実施内容:

- `.claude/settings.json` の `Notification` / `Stop` フックを削除（配布側には元から無い）
- `.claude/settings.local.json` から通知トピックの環境変数を削除
- `.devcontainer/extra-allowed-domains.txt` から当該ドメインを削除（追加ドメインは0件になった）
- R-003 に「不要になった宛先は外す」を明記（許可リストを増える一方にしない）

**したがって公開前チェックリストの ① は「ローテーション」ではなく「機能の廃止」で解消した。**

以下は当初の提案（記録として残す）。

1. **トピックをローテーションする。** `settings.local.json` の当該環境変数を新しい値に変え、
   古いトピックの購読をやめる。**履歴に残った値は無意味になる**ので履歴書き換えが不要になる。
   所要1分。影響範囲ゼロ（他人のクローンにも既存タグにも影響しない）。
2. 履歴を書き換える（`git filter-repo` 等）。**影響範囲が大きい**ので推奨しない:
   - 全コミットハッシュが変わる → `v1` タグの指すコミットが消える／作り直しになる
   - 既存2プロジェクトが `@v1` で参照している composite action の解決先が変わる
   - 他の作業ツリー・別セッションのクローンが全て不整合になる（sumai-desk 側で並行作業中）
   - `main` への force push が必要（`CLAUDE.md` で禁止している操作）

**1 を採れば公開前の残作業はトピック変更のみ。**

### ✅ P2（解消済み）: 「未修正の弱点」の公開範囲

ADR-013「未解決」の1件目は、当初**別リポジトリの未修正の構成上の穴**を、対象プロジェクト名・
設定ファイルのパス・**再現コマンド**つきで書いていた。公開すると「どのプロジェクトの／どこに／
どんな穴があり／どう突けるか」が揃った状態で外へ出る。当該リポジトリ自体は private のため
直ちに悪用できるわけではないが、部分的なアクセスを得た攻撃者に狙いどころを教えることになる。

**解消（2026-08-04・実施済み）: 案 B（表現を変えて公開）を採った。**

- ADR-013「未解決」1件目を**一般的な設計上の注意**へ書き換えた。残したのは
  「ソケットを渡した時点でネットワーク遮断もマウント制限も意味を失う」「ホスト root 相当の権限を
  与えることと同じ」「隔離境界を主張するプロジェクトでは選択肢に入れない」という**設計判断の根拠**。
  落としたのは**プロジェクト名・ファイルパス・再現コマンド**
- 同種の記述を同時に修正: `docs/requirements/R-003`（対象外節）/
  `docs/audit/adr013-egress-verification-20260804.md`（判定の射程）/
  ADR-013 の伝播の項（「外向き通信は全開放のまま」という現状開示を削除）
- **具体の追跡は git 管理外の運用記録へ移した。移した先は公開文書に書いていない**
  （書けば「どこを見れば穴の詳細が分かるか」を教えることになり、伏せた意味が消えるため）

**残る判断事項（弱点ではないが固有情報）**

- ADR-013「理由/隔離ティア」節に、あるプロダクトが**本番の顧客データを扱う**という記述がある。
  弱点の開示ではなく事業情報であり、P5 と同じ扱い（経営判断）。generalize するかは未決
- `docs/audit/adr011-phase1-investigation-20260804.md` のデプロイ構成の要約は、
  ベンダー名（ECR / EC2）を一般語（コンテナレジストリ / 本番ホスト）へ置き換えた（2026-08-04）。
  具体値（アカウントID・ホスト・鍵）は元から含まない

### 🟡 P3: コミットメタデータに個人のメールアドレスが含まれる

| 著者 | 件数 | 種別 |
|---|---|---|
| `Osawa Shohei <osawa_shohei@grace-tech.co.jp>` | 57 | 会社アドレス |
| `Showithwgy <lov.m.f.s@gmail.com>` | 20 | **個人の Gmail** |
| `Showithwgy <あなたã…@gmail.com>` | 1 | 同上（文字化けした著者名。1コミットのみ） |

公開すると**個人の Gmail が全世界から参照可能**になり、GitHub の commit 一覧に恒久的に残る
（スパム収集の対象になる）。加えて著者名が2系統に割れており、文字化けしたものが1件ある。

**提案**: 公開そのものを止める要因ではない。**判断事項**として挙げる。

1. 許容する（何もしない）
2. GitHub の `noreply` アドレス（`<id>+<user>@users.noreply.github.com`）へ統一し、**今後の**コミットだけ変える
   （過去は履歴書き換えが必要なので P1 と同じ理由で推奨しない）
3. 今後のために `git config user.email` を会社アドレスへ固定する（1分・影響なし）

**あわせて**: コミットメッセージ44件に `claude.ai/code/session_...` のセッションURLが入っている。
第三者がアクセスできる URL ではないが、セッション識別子が公開される。**許容範囲と判断するが、
今後付与するかは方針として決めておくとよい。**

### 🟡 P4: 弱点の「一般的な」記述は公開してよい — ただし理解のうえで

次のファイル群が、ガードレールの**限界と迂回方法**を具体例つきで記述している。

`CLAUDE.md` / `docs/rules/security.md` / `docs/decisions/012` / `013` /
`docs/requirements/R-001` / `tests/guard-dangerous.bats`（「既知の限界」節に**動く迂回コマンドが6例**）/
`guard-dangerous.sh` と各複製 / `init-firewall.sh` と各複製

**これは公開して問題ない**と判断する。根拠は3つ。

1. **脅威モデル上、そもそも防御として数えていない。** ADR-012 で第2層・第3層は「事故防止」であり
   敵対的コードに耐えるのは第1層（コンテナ隔離）だけと明記済み。
   隠して強くなる層ではない（security by obscurity に依存していない）。
2. 記述されている迂回（難読化・ファイル実行・`npm run` 経由・`find -delete`・絶対パス起動）は
   **正規表現による静的検査一般の限界**であり、この基盤固有の脆弱性ではない。
3. **限界を明記していること自体が本リポジトリの価値**であり、伏せると
   「ガードがあるから安全」という誤った前提を読者に与える。

**ただし公開後は「この基盤を使っている＝この限界がある」ことが第三者に既知になる。**
第1層（コンテナ隔離・ネットワーク遮断）が実際に効いていることの担保が、これまで以上に重要になる
（`scripts/verify-isolation.sh` を Rebuild のたびに流す運用を継続すること）。

## 3. 公開後に変わる運用

### 3-1. ブランチ保護

| 項目 | 現在（private・Free 想定） | public 後 |
|---|---|---|
| ブランチ保護ルール | **有料プランでないと使えない** | **無料で使える**（public リポジトリは Free でもブランチ保護が可能） |
| 必須ステータスチェック | 同上 | 同上 |

→ **ADR-011 の「未解決」（ブランチ保護が未設定なら CI が赤でもマージを止められない）が、公開によって解消可能になる。**
公開後にやること: `main` に保護ルールを作り、必須チェックに **`ci`**（reusable 呼び出しジョブ名）を指定する。
`display-green` の廃止（ADR-011 判断2）とセットで実施する。

### 3-2. GitHub App は不要になるか → **側置きチェックアウトの用途では不要になる**

| 用途 | private のとき | public 後 |
|---|---|---|
| 基盤リポジトリの checkout（側置き） | **トークンが要る**（App） | **不要**。public リポジトリは未認証で clone できる |
| reusable workflow の参照 | 組織アクセス設定が必要 | **public なら誰でも参照可能**（設定不要） |
| composite action の参照 | 同上 | 同上 |

**ADR-011 の設計変更（フェーズ2で反映する差分）**

- `service-ci.yml` の `secrets: app-id / private-key` は**任意のまま残す**が、既定は未設定でよい。
  すでに「App 未設定なら token を渡さない」分岐を実装済み（`if: secrets.app-id != ''`）なので、
  **YAML の変更は不要**。組織シークレットの登録作業が消えるだけ。
- §4「GitHub App の作成手順」は**実施不要**になる。ただし**将来 private のプロジェクトから
  private の基盤を参照する構成に戻る可能性**があるため、手順は計画書に残す（削除しない）。
- **結果として公開前にやるべき作業が減る**。App 作成（ホスト側の手作業）が公開の前提から外れる。

### 3-3. 組織シークレット

- `APP_ID` / `APP_PRIVATE_KEY` の登録が**不要**になる（3-2）。
- **重要**: public リポジトリでは、**fork からの pull_request でシークレットが渡らない**
  （`pull_request` イベントの fork PR は secrets にアクセスできない）。
  現在の CI は secrets を使っていないため**影響なし**だが、
  今後 CI にシークレットを要する処理（デプロイ・外部 API）を足すときは
  `pull_request_target` の危険性とあわせて設計が必要になる。
- **Actions の実行分**: public リポジトリの GitHub Actions は**無料枠が無制限**（private は月2000分等の上限）。
  CI を頻繁に回す構成にとっては実質的な緩和になる。

### 3-4. その他、公開で変わること

| 項目 | 影響 |
|---|---|
| Issue / PR | 誰でも作成できるようになる。**テンプレートと運用方針を決めるまで放置すると荒れる** |
| `CODEOWNERS` | ADR-008 で廃止済み。公開後にレビュー必須化を再導入するかは別判断 |
| Dependabot / Code scanning | public なら **CodeQL などが無料**で使える（現在は gitleaks のみ） |
| ライセンス | **`LICENSE` ファイルが無い**。公開すると「著作権表示なし」の状態になり、第三者が利用可否を判断できない。公開前に決めるべき（MIT / Apache-2.0 / 明示的に「無許諾」等） |
| `SECURITY.md` | 脆弱性報告の窓口が無い。公開リポジトリでは慣例として求められる |
| 秘密の再混入リスク | **公開後に秘密を1度でもコミットしたら即座に露出する**。現在の CI は `--no-git`（HEAD のみ）なので、**push 前フックまたは CI に全履歴スキャンを足すか**を検討する |
