## 0. 設計の骨格

```
プロジェクトの .github/workflows/ci.yml（3行）
  └ uses: gracetech-jp/ai-dev-foundation/.github/workflows/service-ci.yml@v1
       ├ [1] GitHub App トークン取得
       ├ [2] 側置きチェックアウト（基盤 → . / プロジェクト → projects/<name>）
       ├ [3] 共通ゲート  … projects/<name> で make req-coverage / tier-tripwire / audit-all
       ├ [4] スタック層  … projects/<name> で make lint / test / coverage / audit-deps / build
       └ [5] secret-scan … gitleaks（基盤に依存しない）
```

**環境一致は「同じ make ターゲットを呼ぶ」ことで担保する**（devcontainer は使わない）。
2026-07-23 に8ジョブ→3ジョブへ統合した理由（devcontainer ビルドが毎 push × N 回走る）はそのまま残り、
かつ既存2プロジェクトは実際に devcontainer を CI から外している（フェーズ1 §4）。

## 1. `service-ci.yml`（reusable workflow）の設計

### 1-1. ファイルの位置と呼び出し形

配置: `.github/workflows/service-ci.yml`（基盤リポジトリ）。`on: workflow_call`。

呼び出し側（各プロジェクト）の `ci.yml` はこれだけになる。

```yaml
name: CI
on: [push, pull_request]
jobs:
  ci:
    uses: gracetech-jp/ai-dev-foundation/.github/workflows/service-ci.yml@v1
    with:
      project-name: <静的サイト側のリポジトリ名>
      runtime: node
      node-version: "24"
    secrets: inherit
```

**ジョブ名は `ci` に統一する**（判断2）。ブランチ保護の必須チェックはこの1本
（reusable workflow の場合、チェック名は `ci / <reusable 側のジョブ名>` の形で出るため、
**必須チェックに指定する文字列は実測で確定させる**。→ §8）。

### 1-2. inputs / secrets

```yaml
on:
  workflow_call:
    inputs:
      project-name:     {type: string,  required: true}   # 側置き先のディレクトリ名（projects/<これ>）
      profile:          {type: string,  required: false, default: ""}      # 記録・分岐用（product-web / product-static）
      runtime:          {type: string,  required: false, default: "none"}  # none | node | python | both
      node-version:     {type: string,  required: false, default: "24"}
      python-version:   {type: string,  required: false, default: "3.12"}
      package-manager:  {type: string,  required: false, default: ""}      # pnpm | npm | uv | poetry（空なら導入しない）
      db:               {type: string,  required: false, default: "none"}  # none | postgres（§1-4）
      db-image:         {type: string,  required: false, default: "postgres:16-alpine"}
      stack-gates:      {type: string,  required: false, default: "lint test coverage audit-deps"}  # 呼ぶ make ターゲット
      common-gates:     {type: string,  required: false, default: "audit-all req-coverage tier-tripwire"}
      foundation-ref:   {type: string,  required: false, default: ""}      # 空なら §1-3 の自動解決
      runs-on:          {type: string,  required: false, default: "ubuntu-latest"}
    secrets:
      app-id:           {required: true}
      private-key:      {required: true}
```

**`stack-gates` / `common-gates` を文字列リストにする理由**: プロファイル差（product-static だけ `build` を持つ）を
**基盤側の分岐で持たない**ため。呼び出し側が並びを渡す＝ゴールデンパスの「カスタマイズ可能」を満たす
（ADR-011 の理由節）。既定値は現在の `_base` の並びと一致させる。

**secrets**: GitHub App の `app-id` / `private-key` の2つのみ（§4）。
`secrets: inherit` を推奨（組織シークレットを各プロジェクトで再定義しない）。

### 1-3. 側置きチェックアウトの手順と、パス解決が成立する根拠

```yaml
steps:
  - uses: actions/create-github-app-token@v2
    id: app-token
    with:
      app-id: ${{ secrets.app-id }}
      private-key: ${{ secrets.private-key }}
      owner: ${{ github.repository_owner }}
      repositories: ai-dev-foundation        # 最小権限: この1リポジトリにスコープ

  # 1本目: 共通基盤を GITHUB_WORKSPACE 直下へ
  - uses: actions/checkout@v4
    with:
      repository: gracetech-jp/ai-dev-foundation
      ref: ${{ inputs.foundation-ref || github.job_workflow_sha }}
      token: ${{ steps.app-token.outputs.token }}
      path: .

  # 2本目: 呼び出し元プロジェクトを projects/<name> へ
  - uses: actions/checkout@v4
    with:
      fetch-depth: 0                          # tier-tripwire の差分基準（origin/main）に必須
      path: projects/${{ inputs.project-name }}
```

**成立の根拠（実ファイルで確認済み）**

| 仕組み | 実装 | 側置き後に何が起きるか |
|---|---|---|
| マーカー上方探索 | 各プロファイル Makefile が `PROJECT_ROOT` から `while [ "$d" != "/" ]` で `.ai-dev-foundation-root` を探す | `$GITHUB_WORKSPACE/projects/<name>` から1つ上がると `$GITHUB_WORKSPACE/.ai-dev-foundation-root` に当たる → **`COMMON_ROOT` が解決する** |
| fail-closed ガード | `ifeq ($(COMMON_ROOT),) $(error ...)` | 解決するので**発火しない**（現状 CI で発火していたのがこれ） |
| ゲート実装の参照 | `gates.mk` が `bash "$(COMMON_ROOT)/common/scripts/check-*.sh" "$(PROJECT_ROOT)"` | `common/scripts/` の**実体**が同じワークスペースにある → composite action の同梱複製が不要になる（§2） |
| 差分基準 | `check-tier-tripwire.sh` が `git -C "$ROOT" rev-parse origin/main` | プロジェクト側 checkout に `fetch-depth: 0` が要る（上記） |

**注意点3つ**

1. **`path: .` への checkout は既存ファイルを消さない**。1本目→2本目の順序を守れば
   `projects/<name>` は2本目が作る。逆順にすると1本目が `projects/` を含むワークスペースへ展開されるため、
   **順序は固定する**（実装時にコメントで理由を残す）。
2. **基盤リポの `.gitignore` は `/projects/` を無視している**。CI 上で `projects/<name>` に別リポジトリを
   置いても基盤側の git は関知しない（ネストしたリポジトリとして扱われる）。**基盤側で `git status` を
   叩くゲートは無い**ので影響しない（実測: `audit-consistency.sh` は git を使わない／
   `check-tier-tripwire.sh` は `git -C "$PROJECT_ROOT"` で明示的にプロジェクト側を見る）。
3. **`github.job_workflow_sha`** は「reusable workflow ファイルのコミット SHA」を指す。
   これで**呼び出された reusable と同じコミットの基盤**をチェックアウトでき、
   `@v1` のタグ移動と実体のズレが原理的に起きない。**ただしこの挙動はこの環境から検証できない**
   （§8 のホスト側コマンドで確認する）。確認が取れるまでは `foundation-ref` を明示指定できる口を残す。

### 1-4. `services:`（DB）を渡す口 — GitHub Actions の制約と回避

**`services:` ブロックは式で組み立てられない**（`jobs.<id>.services` はジョブ定義の静的キー。
`image:` の値に式は書けるが、**サービスの有無そのものを入力で切り替えることはできない**）。

したがって取れる形は次の3つ。

| 案 | 形 | 長所 | 短所 |
|---|---|---|---|
| **A（採用）** | reusable 内に **`gates`（DB無し）と `gates-db`（postgres 付き）の2ジョブ**を置き、`if: inputs.db == 'none'` / `== 'postgres'` で排他起動。共通ステップは**内部 composite action** `./.github/actions/service-gates` に切り出して重複を避ける | 後から DB 種別を足せる（`gates-mysql` を追加するだけ）／ステップ本体は1箇所 | ジョブ定義が2つ並ぶ（YAML の見た目の重複） |
| B | サービスを常時起動（`postgres` を必ず立てる） | 分岐不要 | 使わないプロジェクトでも毎回コンテナが起動する。無駄と起動失敗リスク |
| C | DB はプロジェクト側のステップで `docker run` する | reusable が単純 | ヘルスチェック・ポート待ちを各プロジェクトが書く＝伝播しない |

**採用案 A の骨子**

```yaml
jobs:
  gates:
    if: inputs.db == 'none'
    runs-on: ${{ inputs.runs-on }}
    steps: [...共通ステップ（composite action 1呼び出し）...]

  gates-db:
    if: inputs.db == 'postgres'
    runs-on: ${{ inputs.runs-on }}
    services:
      postgres:
        image: ${{ inputs.db-image }}
        env: {POSTGRES_PASSWORD: postgres, POSTGRES_DB: ci_test}
        ports: ["5432:5432"]
        options: >-
          --health-cmd pg_isready --health-interval 10s --health-timeout 5s --health-retries 5
    steps: [...同じ composite action...]
```

これにより **ADR-016（deploy 系）で `migration-check` 相当を移してくる際、
`db: postgres` を渡すだけで済む**（後から作り直しにならない、という判断3の要求を満たす）。

### 1-5. soft/hard 判定のシェルブロックの持ち方

フェーズ1 §3-2 のとおり、判定は**静的な `with:` に落ちない**（make の出力文字列と `.coverage-floor` の内容に依存）。
**シェルブロックごと基盤が持つ**。持ち方は2案。

| 案 | 形 | 判定 |
|---|---|---|
| **A（採用）** | **`common/scripts/run-gates.sh` として実体化**し、reusable workflow の step から `bash "$COMMON_ROOT/common/scripts/run-gates.sh" <targets...>` で呼ぶ | ローカル（`make` 経由）でも CI でも**同じスクリプト**が走る。bats で直接テストできる（現在の `runCmd` 直書きはテスト不能） |
| B | reusable workflow の `run:` に現在のシェルをそのまま貼る | 差分は小さいが、**YAML 内のシェルは bats で検証できない**。現状の弱点をそのまま持ち越す |

**案 A の仕様（現在の `runCmd` の挙動を保存する）**

```
run-gates.sh <mode: hard|softable> <target> [<mode> <target> ...]
  - 各ターゲットを make で実行し、出力を保持したまま次へ進む
  - softable かつ 出力に `make: *** [...] Error 3`（TODO 契約）→ ::warning:: へ落として続行
  - hard で失敗 → fail=1 を立てて続行
  - coverage は呼び出し側が .coverage-floor を読んで mode を決める（下記）
  - 最後に exit $fail
```

`coverage` の floor 切替はスクリプト内に閉じる:
`floor="$(cat "$PROJECT_ROOT/.coverage-floor" 2>/dev/null || echo 0)"` → `0` なら softable、それ以外は hard。

**この切り出しは MIGRATION_PAIRS を増やさない**（`common/scripts/` の実体を側置きで直接読むため。§2）。

### 1-6. ジョブ構成（reusable 内部）

| ジョブ | 内容 | soft/hard |
|---|---|---|
| `gates` / `gates-db` | 側置きチェックアウト → ランタイム導入（`runtime` 入力）→ `run-gates.sh` で common-gates + stack-gates | スクリプトが判定 |
| `secret-scan` | gitleaks（プロジェクトのみ checkout。基盤も App トークンも不要） | hard |

**集約ジョブは作らない**（判断2）。呼び出し側のジョブ名 `ci` が1本の必須チェックになる。
`gates` / `gates-db` の排他起動により**片方は必ず skip** になるが、
skip は失敗ではないため必須チェックの扱いに影響しない——**ただしこれは §8 で実測して確認する**
（静的サイト側が `display-green` で `skipped` を許容していたのは、まさにこの挙動を懸念してのもの）。

## 2. composite action の扱い（MIGRATION_PAIRS の二重管理は減らせるか）

**判定: 減らせる。ただし段階を踏む。**

| 論点 | 事実 |
|---|---|
| 複製の存在理由 | action.yml のコメント「`$GITHUB_ACTION_PATH` から実行するため同梱が必須」＝**単独 checkout で共通リポが無い**ことが前提 |
| 側置きチェックアウト後 | `common/scripts/check-*.sh` の**実体がワークスペースにある**。`$GITHUB_ACTION_PATH` から読む必要が消える |
| 現在の利用者 | `service-templates/`（ADR-011 で削除）と既存2プロジェクト（どちらも §5 で移行） |
| 移行後の利用者 | **ゼロになる** |

**結論**: 両プロジェクトの移行完了後、`.github/actions/{req-coverage,tier-tripwire,coverage-floor}` を削除できる。
削除すると `MIGRATION_PAIRS` の**6対中3対が消える**（残るのは Dockerfile と init-firewall.sh の3対）。

**ただし削除は最後に行う**（§7 の順序）。理由は2つ。

- `@v1` を指す外部利用者がいないことを**確認できない**（リモート未確認。§8）
- 移行の途中で片方のプロジェクトが旧方式のまま残る期間があり、その間は action が要る

**内部 composite action（§1-4 の `./.github/actions/service-gates`）は新設する。**
これは**基盤内部からの相対参照（`./.github/actions/...`）専用**で、外部公開しない。
ADR-011 注意事項の「基盤内部から composite action を参照する場合は相対パス構文を使う」に従う。
**スクリプトの同梱は不要**（側置きで `common/scripts/` が見えるため）＝ MIGRATION_PAIRS を増やさない。

## 3. 検査(8)（基盤 CI の6ジョブ名の機械検証）の改訂

### 3-1. 現状と問題

```bash
for job in audit lint test req-coverage tier-tripwire secret-scan; do
  grep -qE "^[[:space:]]{2}${job}:[[:space:]]*$" "$CI_YML" || report "…必須ジョブ '${job}' がありません"
done
```

**ジョブ名の直値一致**であり、次のどちらでも壊れる。

- 基盤自身が reusable を呼ぶ形に変わる（ジョブ名が `ci` 1本になる）
- ジョブを分割・改名する

一方でこの検査が守っている本質は「**CI と pre-push の二重化が崩れていないこと**」＝
**6つのゲートが CI のどこかで実行されること**であって、ジョブ名ではない。

### 3-2. 改訂案（ジョブ名ではなく「ゲートの実行」を見る）

`REQUIRED_GATES` を「ゲート名: そのゲートが実行されたと判定できる正規表現」の対にする。

| ゲート | 判定に使う正規表現（`ci.yml` 全体に対して） |
|---|---|
| audit-all | `make audit-all` または `service-ci\.yml@` の呼び出しで `common-gates` に `audit-all` を含む |
| lint | `make lint` または `stack-gates` に `lint` |
| test | `make test` または `stack-gates` に `test` |
| req-coverage | `make req-coverage` または `common-gates` に `req-coverage` |
| tier-tripwire | `make tier-tripwire` または `common-gates` に `tier-tripwire` |
| secret-scan | `gitleaks` |

**基盤自身は reusable を呼ばない方針を推奨する**（下記）ため、実際には現行の `make X` 一致で緑のままだが、
**検査が「呼び出し形」も許容する形になっていれば、将来の移行でゲートが落ちない**。

### 3-3. 基盤自身を reusable 化するか — 推奨は「しない」

| 案 | 評価 |
|---|---|
| **基盤は現行6ジョブのまま（推奨）** | 基盤には側置きチェックアウトが不要（自分が基盤）。`runtime` も `db` も不要。**reusable を通す意味が無く、通すと自己参照で ref 解決が複雑になる**（`job_workflow_sha` が自分自身を指す） |
| 基盤も reusable を呼ぶ | 「基盤が自分の作った経路を通る」dogfood 効果はあるが、上記の複雑さに見合わない |

**代わりに dogfood は別の形で担保する**（§6 のテスト）: `new-service.sh` で生成した雛形に対して
`run-gates.sh` を実際に走らせる bats を追加する。**reusable workflow の YAML 自体は
GitHub 上でしか実行できない**ため、そこは §8 の実測に委ねる。

## 4. GitHub App の作成手順と必要な権限

**すべてホスト側（ブラウザ／`gh`）で行う。この環境からは実行できない。**

### 4-1. 作成手順

1. 組織 `gracetech-jp` の Settings → Developer settings → **GitHub Apps** → New GitHub App
2. 名前: `ai-dev-foundation-ci`（任意）／ Homepage URL: リポジトリ URL
3. **Webhook: Active のチェックを外す**（イベント受信は不要）
4. **Repository permissions を次の2つだけにする（最小権限）**

   | 権限 | 値 | 理由 |
   |---|---|---|
   | **Contents** | **Read-only** | 基盤リポジトリを checkout するため |
   | Metadata | Read-only（自動付与・変更不可） | GitHub が必須とする |

   **その他はすべて No access**。とくに Actions / Workflows / Packages / Administration は**不要**
   （トークンは checkout にしか使わない）。書き込み権限は一切与えない。
5. Where can this GitHub App be installed? → **Only on this account**
6. 作成後、**Private key を生成**して `.pem` をダウンロード
7. 組織の Settings → GitHub Apps → Install → **`ai-dev-foundation` リポジトリのみを選択**して Install
   （`Only select repositories`。All repositories にしない）
8. **App ID** を控える

### 4-2. シークレットの配置

| 名前 | 値 | 置き場所 |
|---|---|---|
| `APP_ID` | 手順8 の App ID | **組織シークレット**（Settings → Secrets and variables → Actions → New organization secret）。Repository access は該当プロジェクトに限定 |
| `APP_PRIVATE_KEY` | 手順6 の `.pem` の中身（全文・改行込み） | 同上 |

各プロジェクトの `ci.yml` は `secrets: inherit` で渡す。**プロジェクトごとに秘密を複製しない。**

### 4-3. なぜ PAT ではないか（判断1の根拠を記録）

- PAT は個人アカウントに紐づく＝**担当者が抜けると CI が止まる**
- 期限切れの手動更新が必要＝「極力人間に手を使わない」前提に反する
- App のインストールトークンは**1時間で失効し自動ローテーション**される
- 権限はリポジトリ単位・API 単位で絞れる（上表の2つだけ）
- 監査ログに App 名で記録される（誰の PAT かではなく何が動いたかが残る）

### 4-4. 未確認事項

**基盤リポジトリが private か public かをこの環境から確認できない。**
public であれば checkout にトークンは不要で、GitHub App 自体が不要になる（§8 で確認）。
private 前提で設計しておき、public と判明したら App の導入を省略できる形にする
（`app-id` / `private-key` を `required: false` にし、未指定なら `token` を渡さない分岐）。

## 5. 既存2プロジェクトへの適用差分

### 5-1. 静的サイト側（現 138行・6ジョブ → 約10行・1ジョブ）

```yaml
jobs:
  ci:
    uses: gracetech-jp/ai-dev-foundation/.github/workflows/service-ci.yml@v1
    with:
      project-name: <静的サイト側のリポジトリ名>
      profile: product-static
      runtime: node
      node-version: "24"
      package-manager: pnpm
      stack-gates: "lint test coverage audit-deps build"
      foundation-ref: v1    # uses: のタグと同じ値。省くと main が使われる（§8-5）
    secrets: inherit
```

| 現在のジョブ | 移行後 |
|---|---|
| `stack-gates`（pnpm + setup-node + coverage-floor action + lint/test/audit） | reusable の `gates` に吸収。`make lint` / `make test` 経由になる（**現在は `pnpm run lint` を直接呼んでいる**ため、Makefile 側の実装確認が要る） |
| `req-coverage` / `tier-tripwire`（composite action） | reusable の `gates` 内の `make req-coverage` / `make tier-tripwire` に統合。**設定値は Makefile が持つ**（現在は ci.yml に直書き）→ **Makefile と ci.yml の二重管理が解消する** |
| `audit` | 同上（`make audit-all`） |
| `secret-scan` | reusable の `secret-scan` |
| **`display-green`** | **廃止**（判断2）。必須チェックは `ci` 1本 |

**移行前に確認が要る点**: `tier-tripwire` の設定（機微パス / 機微シンボル /
`self-re: '^Makefile$'`）が**プロジェクトの Makefile 側にも同じ値で入っているか**。
入っていなければ CI 経路を切り替えた瞬間に**設定が空になって exit 2（fail-closed）**になる。

## 7. 実行順序と各段階の検証方法

**原則**: 壊れても戻せる順に。**基盤内で完結する変更を先に、GitHub 側の設定変更を後に。**

| # | 作業 | 検証 | 戻せるか |
|---|---|---|---|
| 1 | `common/scripts/run-gates.sh` 新設 + bats（6-2 の1） | `make test` / `make lint` | git |
| 2 | 検査(8) の改訂 + bats（6-2 の2） | `make audit-all` / `make test` | git |
| 3 | 側置き配置の bats 追加（6-2 の3） | `make test` | git |
| 4 | `.github/workflows/service-ci.yml` 新設（内部 composite action 含む）。**まだ誰も呼ばない** | `make audit-all`（構文は actionlint が入っていれば） | git |
| 5 | **GitHub App の作成・インストール・組織シークレット登録**（§4） | §8 のコマンドで疎通確認 | App を削除すれば戻る |
| 6 | 基盤リポに**検証用の呼び出し**を一時的に置く（`.github/workflows/service-ci-selftest.yml`、`workflow_dispatch` 限定）→ 実行して緑を確認 | GitHub 上で実行 | ファイル削除 |
| 7 | 静的サイト側の `ci.yml` を置換 → push して緑を確認 | GitHub 上で実行 | git revert |
| 8 | 静的サイト側のブランチ保護を `display-green` → `ci / gates` へ張替 | §8 | 設定を戻す |
| 9 | 動的アプリ側の `ci.yml` を置換 → 緑を確認 → ブランチ保護張替 | 同上 | 同上 |
| 10 | `profiles/_base/.github/workflows/ci.yml` を reusable 呼び出しへ置換 + `new-service.sh` の生成物確認 | `make audit-all` / 生成して目視 | git |
| 11 | `service-templates/` を削除（23ファイル）+ 検査(10)後半の削除 | `make audit-all` / `make test` | git |
| 12 | `.github/actions/` 3本を削除 + `MIGRATION_PAIRS` 3対を削除 | `make audit-all` / `make test` | git |
| 13 | `v1` タグを新しいコミットへ移動（または `v2` を切る） | §8 | タグを戻す |

**11・12 を最後にする理由**: どちらも「旧経路の撤去」であり、7〜9 が緑になるまで旧経路が要る。
**12 は 7・9 の完了が前提**（両プロジェクトが composite action を参照しなくなるまで消せない）。

**13 の判断 → `v2` を新設する（2026-08-06 決定）。** 根拠は3つで、いずれも実測に基づく。

1. **`v1` はそもそも使えない。** `v1` = `0906ac0`（2026-07-26）の tree を確認したところ、
   `.github/workflows/service-ci.yml` も `common/scripts/run-gates.sh` も**存在しない**。
   `uses: ...@v1` はワークフローが見つからず即エラーになり、仮に `foundation-ref: v1` を渡せば
   composite action が読む `run-gates.sh` が無くて落ちる。**移行先として成立していない。**
2. **`v1` を動かすと、いま動いているものが壊れる。** 既存2プロジェクトは composite action を
   `@v1` で参照している。タグを進めると**参照先の中身が黙って変わる**——
   バージョン付けの目的（壊さずに旧版を非推奨にする。ADR-011 注意事項）と正面から矛盾する。
3. **§8-5 でピン止めの意味が重くなった。** `foundation-ref` を明示する運用では、
   タグは「reusable の定義」と「checkout する共通基盤のコード」の**両方**を決める。
   動くタグは、その両方を同時に予告なく動かすということになる。

したがって **`v1` は凍結**（既存の composite action 利用者のために残す）、
**`v2` を現在の main で切り**、サービス側は `uses: ...@v2` + `foundation-ref: v2` で移行する。
タグが増えるコストは受け入れる——**「増やさない」ために動かすと、壊れ方が静かになる。**

**v2 を切る前に済ませること**: 手順10（`profiles/_base` の CI を reusable 呼び出しへ）。
配布雛形が古い形のまま v2 に含まれると、生成物と v2 の中身が食い違う。

### 8-2. selftest 第1回（2026-08-06・run 31068031762）— **配布前に不具合を1件検出した**

結果: `selftest / gates` が **失敗**、`selftest / secret-scan` 成功、`selftest / gates-db` skip。

**原因**: 1本目の checkout が `Input required and not supplied: token` で落ちた。
`token: ${{ steps.app-token.outputs.token }}` は、App 未設定で当該ステップが skip されると
**空文字**になる。`actions/checkout` の `token` は既定値を持つが、**既定値は入力を省いたときにしか
効かない**——空文字は「未指定」ではなく「不正な指定」として扱われる。

**これは selftest 固有の問題ではない。** App を作らない前提（public 化により手順5は不要と判断済み）で
サービス側が移行すれば、**最初の1本目の checkout で必ず同じ形で落ちる**。
配る前に踏めたことが手順6の値である。

**修正**: `token: ${{ steps.app-token.outputs.token || github.token }}`。
App 未設定なら呼び出し元の `GITHUB_TOKEN` へ落ちる。共通基盤が public ならこれで読め、
private へ戻したときだけ App（secrets）が要る、という分岐が1行に閉じる。

### 8-3. selftest 第2回（2026-08-06・run 31068359593）— **全ジョブ緑**

`selftest / gates` success ／ `selftest / secret-scan` success ／ `selftest / gates-db` skipped（23秒）。
`gates` の全ステップが緑で、§8-2 の修正（`|| github.token`）が効いたことを確認した。

| 確認項目 | 実測 |
|---|---|
| 1本目の checkout（共通基盤を workspace 直下へ） | success |
| 2本目の checkout（呼び出し元を `projects/<name>` へ） | success |
| `service-runtime` / `service-gates` | success（`$GITHUB_WORKSPACE/common/scripts/run-gates.sh` が実行され、`make -C projects/<name> lint` が緑） |
| 側置きの配置 | **成立**。composite action が workspace 直下の `common/scripts/` を読めている＝共通側が直下、プロジェクトが `projects/<name>` に置かれている |
| `referenced_workflows[].sha` | `fa24bdc2bb3e47f63d5d2286fe64ef2ce9dc99b3`（= dispatch 時の main の HEAD）。`@main` の解決先が確定 |

**側置きについて過大に読まないこと。** この selftest は
**プロジェクト側 Makefile のマーカー上方探索（COMMON_ROOT 解決）を踏んでいない**——
呼び出し元が基盤自身なので `projects/<name>` に入るのも基盤で、そこにマーカーが同梱されており
探索は外へ出ずに自分自身で止まる。実サービス（マーカーを持たない）が外側を解決する経路は
`tests/side-by-side-layout.bats` がローカルで固定している。

**`job_workflow_sha` のリテラル値だけ未観測。** 値を出すステップは緑で通ったが、
**実行ログ本体は隔離コンテナから読めない**（下記）。そこで第3回以降で直接読めるよう、
記録ステップを `::notice::`（＝ check run の annotation。`api.github.com` で読める）へ変えた。
あわせて、**空なら落とす判定**を入れた——空だと checkout が既定ブランチへ落ち、
**ゲートを定義したコミットと実行するコミットがずれる**。黙って別の版で回るのが最悪なので
fail-closed にする（`inputs.foundation-ref` を明示している場合は対象外）。

### 8-5. selftest 第3回（run 31070611524）— **`job_workflow_sha` は空だった**

annotation（`::notice::`）の実測値:

```
共通基盤: job_workflow_sha=（空） / checkout HEAD=ed6d731c39ecd6d1ca77557e584dee1b50b75735 / foundation-ref=
```

同じ run の API 側:

```
referenced_workflows: [{ path: ".../service-ci.yml@main", ref: "refs/heads/main",
                         sha: "ed6d731c39ecd6d1ca77557e584dee1b50b75735" }]
```

**checkout された HEAD と `referenced_workflows[].sha` は一致しているが、これは偶然である。**
`ref:` に空文字が入った結果 checkout が**既定ブランチ（main）へ落ち**、その HEAD が
たまたま dispatch 元と同じコミットだっただけ。第1回・第2回が緑（または token で落ちた）ときも、
実際には**この空振りが起きていた**——第3回で入れた fail-closed 判定が、それを初めて可視化した。

**これは設計の前提が崩れているということ。** ADR-011 §1-3 は
「`foundation-ref` 未指定なら `job_workflow_sha`＝呼ばれた reusable と同じコミットを指す」
を前提に、**呼び出し側に ref を二重に書かせない**設計にしていた。実際には空になるため、

- `uses: ...@v1` でピン止めしても、**チェックアウトされる共通基盤は `main`** になる
- つまり**バージョン固定が無効化される**。`v1` を残す意味（ADR-011 結果節・段階的移行）が消える
- しかも**症状が出ない**。ゲートは走り緑になる。ずれていることに誰も気づけない

**当面の対処（実施済み）**: `foundation-ref` を明示する。selftest は `foundation-ref: main` を渡す。
サービス側は `uses: ...@v1` と `foundation-ref: v1` を**同じ ref で**書く。
二重記述だが、黙って別の版で回るよりはよい。**未指定のまま空になる経路は fail-closed で落とす**
（既に実装済み。第3回の失敗はこの判定が正しく発火したもの）。

### 8-6. 代替文脈の測定（第4回・run 31073015470）— **代替は無い。明示で確定**

```
job_workflow_sha=（空） / job_workflow_ref=（空） /
workflow_ref=gracetech-jp/ai-dev-foundation/.github/workflows/service-ci-selftest.yml@refs/heads/main /
checkout HEAD=0238b2d8… / foundation-ref=main
```

| 文脈 | 値 | 使えるか |
|---|---|---|
| `github.job_workflow_sha` | **空** | ✗ |
| `github.job_workflow_ref` | **空** | ✗ |
| `github.workflow_ref` | `…/service-ci-selftest.yml@refs/heads/main` | ✗ — **呼び出し側の**ワークフローと ref であって、共通基盤の版ではない。サービスから呼べば `service-repo/.github/workflows/ci.yml@refs/heads/feature-x` になり、共通基盤の ref は何も分からない |

**したがって `foundation-ref` の明示を確定とする。** 二重記述は消せない。
消せない以上ずれるので、**一致を監査で機械強制する**（検査(17)・`common/scripts/check-foundation-ref.sh`）。
`uses: ...@X` と `foundation-ref: Y` が食い違えば赤。未指定でも赤。

`workflow_ref` が正しく埋まっている＝文脈の仕組み自体は動いているのに `job_workflow_*` だけ
空である点から、**同一リポジトリの reusable を参照しているため（self-reference）**という仮説が有力。
もう一つの仮説は `workflow_dispatch` 起点であること。**切り分けの決定的な測定は
「サービスリポジトリから PR 契機で呼んだときの値」**で、移行時に必ず通る。
ただし**どちらであっても運用は変わらない**——明示すれば正しく動き、省けば fail-closed で落ちる。
移行時に値が入っていることが分かったら、そのとき二重記述をやめるか判断すればよい。

### 8-4. 隔離コンテナから CI ログをどう読むか（2026-08-06 実測・両回に共通）

実行ログの本体は**コンテナからは読めない**（許可リストは `api.github.com` / `github.com` のみ。ADR-013）。

| 経路 | 宛先 | 結果 |
|---|---|---|
| `gh run view --log` / `--log-failed` | `results-receiver.actions.githubusercontent.com` | `no route to host` |
| `gh api .../actions/jobs/<id>/logs` | `*.blob.core.windows.net`（署名付き URL へリダイレクト） | 同上 |
| **`gh api .../check-runs/<id>/annotations`** | `api.github.com` | **読める** |
| **`gh api .../actions/runs/<id>`**（`referenced_workflows`） | `api.github.com` | **読める** |

**したがって、CI から持ち帰りたい値は `::notice::` / `::error::` で annotation に出す。**
ログへ `echo` しただけの値は、この環境からは永久に読めない。
§8-2 の失敗原因（`Input required and not supplied: token`）も annotation 経由で特定した。
**隔離を緩めずに原因まで辿れる**ので、許可リストへ宛先を足す前に、この経路で足りないかを
先に確認すること（R-003「推測で足さない」）。

なお §4（GitHub App の作成手順）は**実施しないが削除しない**——
将来 private の基盤を private のプロジェクトから参照する構成に戻る可能性があるため
（`pre-public-security-review-20260804.md` §3-2 の判断）。

## 9. 実装前に判断が要る点

1. ~~**`v1` を動かすか `v2` を切るか**~~（§7 の 13）→ **決着（2026-08-06）: `v2` を新設する。**
   `v1` は `service-ci.yml` も `run-gates.sh` も含まず移行先にならない／動かすと既存の
   composite action 参照が黙って変わる／`foundation-ref` 明示運用ではタグが定義とコードの
   両方を決めるため、動くタグの危険が増した。根拠の詳細は §7 の 13。
2. **静的サイト側の Makefile がスタックゲートを実装しているか**（§5-1）。
   実装が無いまま CI を `make lint` 経由へ切り替えると、TODO 契約（exit 3）で soft 化されて
   **今まで hard だった lint/test が soft に落ちる**。移行前に Makefile を確認する必要がある。
3. **`stack-gates: ""`（動的アプリ側）を許容するか**（§5-2）。
   空だとスタック層が CI で一切走らない。現状（deploy.yml が持つ）の追認だが、
   ADR-016 までの間「ci.yml だけ見るとスタックゲートが無い」状態が続く。
4. **基盤自身を reusable 化しない方針**（§3-3）の是非。
