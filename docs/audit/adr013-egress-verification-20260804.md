# ADR-013 手順10: 許可ドメインの裏取り（実測記録）

対象: `ai-dev-foundation` の devcontainer（Rebuild 済み・`verify-isolation.sh` 9/9 ✅ 通過後）
日付: 2026-08-04

手順9までで許可リストは「公式の必須ホスト ∩ tcpdump による DNS 観測」で確定させた（手順A）。
本書はその**逆側からの確認**（計画 §2-3 手順B）である。遮断した状態で実作業を流し、
**失敗したものからしか宛先を足さない**。

---

## 1. 判定基準（実行前に確定させたもの）

「通ったから裏が取れた」は成立させない。次の4条件が**同時に**成立したときにのみ
「裏が取れた」と判定する。1つでも欠けたら未成立として報告する。

### 条件1: 網羅

下の §2 に事前列挙した作業をすべて実行し、各作業を次の3分類のいずれかに確定させる。
未分類が1件でも残れば不成立。

- **成功**（期待どおり通った）
- **設計どおりの失敗**（遮断以外の理由で落ちることが事前に分かっているもの）
- **未実施**（理由と、どこへ持ち越すかを明記したもの）

### 条件2: 失敗の帰属

失敗した作業について、原因が**ファイアウォールによる遮断か否か**を、
宛先を特定できる証拠（エラーメッセージ、または該当宛先への到達確認の結果）で切り分ける。
切り分けられない失敗が1件でも残れば不成立。「たぶん通った／たぶん別の理由」を成立と呼ばない。

### 条件3: 追加の根拠

許可リストへ追加する場合、**1件ごとに「どの作業のどのエラーが根拠か」**が対応していること。
根拠のない追加（予防的に広げる、まとめて足す）はしない。
遮断由来の失敗が0件だった場合は「**追加なしで確定**」を結論とする。

### 条件4: 陰性対照（空撃ち検出）

計測が**遮断の効いている状態で行われた**ことを、同一セッション内で確認する。
具体的には、許可リストに無い宛先への通信が実際に失敗することを測る。
これが取れないなら、全部通ったという結果は「遮断が効いていないから通った」と区別できず、
測定そのものが無意味になる。

### 判定の限界（事前に宣言しておくこと）

- 本書が確認できるのは**この devcontainer（基盤リポ）で行う作業の範囲**に限る。
  生成物（product-web / product-static）は別イメージ・別依存であり、ここでは測れない。
- 「1回流して通った」ことは「今後も通る」を意味しない。CDN の IP ローテーションで
  許可済みドメインが到達不能になりうる（`init-firewall.sh` 冒頭の既知の限界）。

## 3. 実測結果

計測環境のスタンプ: `status=ok / at=2026-08-04T02:03:59+00:00 / detail=policy=DROP domains=10`

### 3-1. 条件4（陰性対照）— 遮断が効いている状態で測ったか

| 宛先 | 結果 |
|---|---|
| `https://example.com` | 不達（curl exit=7 接続不能） |
| `https://pypi.org` | 不達（exit=7） |
| `https://registry.npmjs.org` | 不達（exit=7） |
| `https://github.com` | 不達（exit=7） |
| `https://api.github.com` | 不達（exit=7） |
| `https://sentry.io` | 不達（exit=7） |
| `https://statsig.anthropic.com` | 不達（exit=6 名前解決不能） |

**条件4 成立。** 許可外7件がすべて落ちているため、以降の「通った」は遮断が効いた状態での結果である。
参照実装が挙げていた sentry / statsig を入れなかった判断も、実際に使われていないことが裏付けられた
（これらが不達でも Claude Code の動作に支障が出ていない）。

### 3-2. 許可リスト内の到達性（作業5）

`BASE_DOMAINS` 9件 + `extra-allowed-domains.txt` 1件（通知サービス）＝**10件すべて到達**。
> **追記（2026-08-04・同日）**: この追加1件は、通知フックの廃止にあわせて許可リストから外した。
> bypassPermissions を既定にしたことで承認待ち通知が鳴る場面が消え、完了通知だけのために
> 外向きの宛先を1つ開ける理由が無くなったため。**以後の許可は `BASE_DOMAINS` 9件のみ**。
到達不能なものは無い。＝**死んだ許可行（もう要らないのに残っている行）の疑いは、この計測では出ていない**。
逆に言えば「使われていないから消してよい行」も特定できていない（到達性は必要性の証明ではない）。

### 3-3. 作業ごとの分類（条件1）

| # | 作業 | 結果 | 分類 |
|---|---|---|---|
| 1 | `make audit-all` / `test` / `lint` / `req-coverage` / `tier-tripwire` | 全て緑（bats 257ケース） | 成功 |
| 2 | Claude Code の応答1往復（本セッション） | 成功（本記録の作成自体が証拠） | 成功 |
| 3 | `git fetch origin` | 失敗（`ssh: connect to host github.com port 22: No route to host`） | 設計どおりの失敗（→ 3-4） |
| 4 | 許可外への通信 | すべて失敗 | 期待どおり（陰性対照） |
| 5 | 許可10件への到達確認 | すべて到達 | 成功 |

| 7 | `uv sync` / `pnpm install` | 実施せず | 未実施（基盤イメージに `uv`/`pnpm` 無し。生成物での実測へ持ち越し） |

未分類は0件。**条件1 成立。**

### 3-4. 失敗の帰属（条件2）— `git fetch` は「鍵が無いから」ではなかった

失敗は作業3のみ。エラーは `No route to host`（= iptables の `REJECT --reject-with
icmp-admin-prohibited`）であり、**認証エラーではない**。切り分けの実測:

- `/home/node/.ssh` は存在するが**空**（秘密鍵は無い。マウント解消済み）
- `github.com:22`（140.82.121.4）への TCP 接続も `No route to host` で落ちる

つまり原因は**2つ重なっている**。firewall が先に落としており、仮に鍵を貼っても
`github.com` が許可リストに無い以上 fetch は通らない。

**ADR-013 の作業量の表の記述（「`~/.ssh` を貼らないため、コンテナ内から SSH のリモート操作が
できない」）は、原因として不完全である。** 遮断だけでも同じ結果になる。
運用上の結論（リモート操作はホストで行う）は変わらないため、本記録で補足するに留める。

**条件2 成立**（切り分けられない失敗は0件）。

### 3-5. 追加の要否（条件3）

**追加なしで確定。** 遮断由来の失敗のうち、許可リストへの追加で解決すべきものは0件だった。

`github.com` を**足さない**理由: git のリモート操作はホストで行うという決定（ADR-013）に基づき、
コンテナ内から必要な操作ではない。ここを開けると「ホストへ移した操作」がコンテナへ戻り、
境界を広げた分の見返りが無い。

---

## 4. 判定

**条件1〜4すべて成立。許可ドメインの裏取りは成立した（追加0件）。**

ただし判定の射程は §1「判定の限界」のとおり、**基盤リポの devcontainer 内で行う作業に限る**。
次は未消化として残る。

- **生成物（product-web / product-static）での実測は未実施。** これらは `uv` / `pnpm` を使い、
  `pypi.org` / `registry.npmjs.org` が実行時に要る可能性が高い（本計測ではどちらも遮断されている）。
  依存追加をコンテナ内で行う運用にするなら許可リストへの追加が要る。ADR-013「未解決」に既記載。
- **既存プロジェクトへの伝播は今回のスコープ外。**
- **ホストの Docker ソケットを共有している構成では、そもそも第1層が成立しない**（ADR-013「未解決」）。
  該当の有無は非公開の運用記録で追跡する。
