## 0. 最初の判断点 — 配布側フックの委譲先

### 0-1. ADR-013 で基盤 root 側はどう解決されたか

| 要素 | 基盤 root の現状 |
|---|---|
| マウント | `.devcontainer/devcontainer.json` が `${localWorkspaceFolder}/.claude` → **`/home/node/.claude`**（＝ユーザースコープ）へ bind |
| フック定義 | `.claude/settings.json` の `PreToolUse` が **絶対パス** `bash /home/node/.claude/scripts/guard-dangerous.sh` |
| 効き方 | ユーザースコープの設定は**起動ディレクトリに関係なく効く**。`CLAUDE_PROJECT_DIR` に依存しない |

つまり root 側は「フックの定義もスクリプト実体もユーザースコープに置く」ことで解決している。
サブディレクトリから起動しても、参照先が固定なので見失わない。

### 0-2. 配布側に同じ形を適用できるか

**できる。しかも配布側は root より条件が良い。** ADR-013 で雛形の `devcontainer.json` は
共通の `.claude` を**同じ位置（`/home/node/.claude`）へマウント**する形に揃っている
（`profiles/_base/.devcontainer/devcontainer.json` の mounts 1本目。コメントに
「共通 deny・フック・agents・skills の配布経路」と明記）。

**したがって、生成プロジェクトの devcontainer 内では、共通側の `settings.json`（＝基盤 root の
`.claude/settings.json`）がユーザースコープとして既に読まれており、絶対パスのフックが効いている。**

公式ドキュメントで確認した事実（`code.claude.com/docs/en/hooks`、2026-08-04 取得):

- **フックは設定スコープ間で「マージ」される。** user / project / local のフックは互いを置換せず、
  一致するものが**すべて走る**。同一のコマンド文字列は自動的に重複排除される
- `CLAUDE_PROJECT_DIR` はプロジェクトルートに解決される（起動ディレクトリ依存の問題は
  この基盤が実測で掴んだ挙動であり、ドキュメントは相対/絶対の警告を明示していない）
- フックのスクリプトが存在しない場合の挙動はドキュメントに**明示が無い**。
  「exit 2 以外は非ブロッキングエラー」という一般則から素通しになる
  （この基盤は `guard-shim.sh` のコメントに**実測で fail-open を確認**と記録している）

**root との違いは1点だけ**: 配布側にはプロジェクト同梱の複製
（`.claude/scripts/guard-dangerous.sh`、`new-service.sh` が `cp` する）が存在する。
root にはこの複製が無い（root 自身が実体）。

### 0-3. 選択肢

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| **A（推奨）** | 配布側の `settings.json` から `PreToolUse` / `SessionStart` の**フック定義を削除**し、`new-service.sh` が配る `.claude/scripts/*.sh` の**複製も廃止**。ユーザースコープ1本に集約 | 複製が消え ADR-010 の参照方式に一致／`CLAUDE_PROJECT_DIR` 依存が構造的に消える／検査(6)の diff 対象が2本減る | コンテナ外（ホストで直接 `claude`）ではフックが**無い**。プロジェクトのリポジトリを見てもガードの実体が見えなくなる（透明性の低下） |
| **B** | フック定義は残し、コマンドだけ絶対パス `/home/node/.claude/scripts/guard-dangerous.sh` に書き換え。複製は残す | 差分が小さい／プロジェクト側に「ガードが効いている」記述が残る | コンテナ内のパスをテンプレートに焼き込む（環境依存）／複製が残り ADR-010 に反したまま／user 側と同一文字列なら重複排除されるが、**違う文字列だと二重起動**する |
| **C** | 何もしない（`$CLAUDE_PROJECT_DIR` のまま）。実効はユーザースコープが担う | 差分ゼロ | **効いていないフック定義が残る**。サブディレクトリ起動時に project 側だけ黙って失敗し、「フックが2つ定義されているのに1つは常に無言で死んでいる」状態を仕様として残すことになる。この基盤が繰り返し潰してきた「作動していないゲート」そのもの |

**推奨は A。** ただし A は「コンテナのマウントが唯一の配布経路になる」ことを意味する。
マウントが無ければ**フックもルールも無いまま起動する**（fail-open）。
これは設定層では閉じられない——閉じるのは第1層（コンテナ定義）である。したがって A を採るなら
**検査(13) に「配布 `devcontainer.json` が共通 `.claude` をユーザースコープへマウントしていること」を
追加する**のが条件になる（下の 7-1 に含める）。

なお A を採っても、コンテナ外で起動したときに `CLAUDE.md` も `docs/rules/` も見えない
（どちらもマウント由来）。**ガードだけが特別に脆くなるわけではない**。

## 1. deny へ追加する4判定の具体的なルール記述

### 1-1. ルール

| 判定 | 現在の deny | **変更後** | 理由 |
|---|---|---|---|
| A2 `git push --force` | `Bash(git push:*)` | **変更なし** | push 全体を deny 済み。`--force` 系も覆えている |
| A3 `git reset --hard` | `Bash(git reset --hard:*)` | `Bash(git reset *--hard*)` へ**置換** | 現状は `--hard` が直後の形しか見ておらず `git reset HEAD~1 --hard` を取り逃がす |
| A4 `git clean -f` | `Bash(git clean -f*)` | `Bash(git clean *)` へ**拡大** | フラグ位置に依存しない。`git clean` は消える方向にしか働かず、全面 deny の損失が小さい |
| A6 `git checkout` 破棄 | `Bash(git checkout -- *)` | 左記に加え `Bash(git checkout .)` を**追加** | `git checkout .`（`--` 無し）が現状素通し |
| （A1 の補強） | `Bash(rm -rf:*)` `Bash(sudo rm:*)` | `Bash(rm *-rf *)` `Bash(rm *-fr *)` `Bash(rm *-Rf *)` `Bash(rm *-fR *)` を**追加**（既存は残す） | 主要な表記ゆれを第2層でも拾う。結合フラグ全域は覆えないためフック側が本体（フェーズ1 2-1） |

**A1 を「追加」に留める理由**: `Bash(rm *)` まで広げると `rm` が日常操作として使えなくなる。
deny には例外が書けない（ADR-012 の根拠そのもの）ため、広げ過ぎは回避策の常用を招く。

**A5（`git branch -D`）は deny を触らない**。結合フラグ `-fD` / `-Df` を覆おうとすると
`*D*` まで広げることになりブランチ名を巻き込む。フック側が担当（フェーズ1 2-5）。

### 1-3. 検査(6) の正規化比較への影響

- 検査(6) は **root ↔ `_base` の `permissions` が、共通所有ロック `Edit(...)` を差し引いて同値**であることを要求する。
  → **1本だけ更新すると即赤**。これは狙いどおりの動作であり、変更は不要。
- 検査(6) はプロファイル2本について「`ask` 以外は `_base` と完全一致」を要求する。
  → こちらも1本漏れれば赤。**追加の検査は要らない**。
- 正規化は「配列の値だけをソート」に修正済み（ADR-013 実装時）。deny 配列が増える分にはこの穴は再発しない。
- **`deny` の中身が正しいか（必要なルールが揃っているか）は検査(6)では見ていない。**
  4本が「揃って間違っている」状態は検出できない。ここを埋めるのが 7-1 の DENY_CORE。

## 4. R-001 の改訂案（EARS 記法）

記法は `While〈前提条件〉, when〈トリガー〉, the〈システム名〉shall〈システム応答〉`。
分割基準はトリガーと前提条件（同一トリガー・同一前提からの複数応答は1要件にまとめる）。

### 4-1. front-matter の変更

| 欄 | 現在 | 改訂案 |
|---|---|---|
| `title` | 破壊的操作・秘密読取の機械的遮断 | **破壊的操作・秘密読取の事故防止（第2層・第3層）** ※「遮断」は第1層の語 |
| `tier` | S | 維持 |
| `paths` | 6件 | **+2件**: `profiles/*/files/.claude/settings.json`（4ファイル同時更新の対象）。案 A を採るなら `profiles/_base/.claude/scripts/guard-dangerous.sh` と `service-templates/claude/scripts/guard-dangerous.sh` は**消える**ので削除 |
| `negative_space` | 2件 | 下記 4-3 |

### 4-2. 受け入れ基準（EARS）

**層の責務**

> **R-001-1**: When Bash ツールの呼び出しが発生したとき、**ガードレール第3層（PreToolUse フック）は**、
> 再帰強制削除・履歴/ブランチ破壊・force push・`git clean -f` 系・`git checkout` による変更破棄を含む
> コマンドを **deny しなければならない**。

> **R-001-2**: When Bash ツールの呼び出しが発生したとき、**ガードレール第3層は**、
> 秘密ファイルのパスが平文で現れる読み取り（外部コマンド・インタプリタのインラインコード・
> ヒアドキュメント・パイプ経由の流し込みを含む）を **deny しなければならない**。

> **R-001-3**: While 対象リポジトリが基盤リポジトリでない間（プロジェクトルートに `profiles/_base/` が無い間）、
> when 共通所有ファイルへの書き込みを伴う Bash 呼び出しが発生したとき、**ガードレール第3層は**、
> その呼び出しを **deny しなければならない**。

**二重化（ADR-012 決定4）**

> **R-001-4**: `git push --force` 系・`git reset --hard`・`git clean -f` 系・`git checkout` による変更破棄に対して、
> **ガードレール第2層（`permissions.deny`）は**、第3層と**独立に**当該コマンドを拒否する
> ルールを**保持しなければならない**。

**例外（通すこと。ここが deny へ移管できない理由そのもの）**

> **R-001-5**: When `.env.example` / `.env.sample` / `.env.template` / `.env.dist` の読み取り、
> 言語の環境変数構文（`process.env` / `import.meta.env` / `Bun.env` / `Deno.env`）、
> 公開鍵（`id_*.pub`）、プロパティアクセス（`row.key` 等）を含む Bash 呼び出しが発生したとき、
> **ガードレール第3層は**、その呼び出しを **deny してはならない**。

> **R-001-6**: While 対象リポジトリが基盤リポジトリでない間、
> when 第1引数が `profiles/_base/` で始まる `cp` / `rsync` / `install`（骨格同期）が発生したとき、
> **ガードレール第3層は**、その呼び出しを **deny してはならない**。

**fail-closed**

> **R-001-7**: If フックが判定に必要な前提（`jq` の実在）を満たさない場合、
> then **ガードレール第3層は**、Bash 実行自体を **exit 2 でブロックしなければならない**。

**退化検出**

> **R-001-8**: When 第2層または第3層のいずれか一方から上記の判定が失われたとき、
> **整合性監査は** 失敗（非ゼロ終了）**しなければならない**。

### 4-3. `negative_space` の改訂

| 現在 | 問題 | 改訂案 |
|---|---|---|
| 「破壊的コマンドが、表記ゆれを用いても**実行できてはならない**」 | 達成できていない絶対要求。`find . -delete`、`-rvf` のような結合フラグ、コンテナ外での起動で成立する | 「**第2層と第3層の双方から同時に**、破壊的コマンドの判定が失われてはならない」（＝独立性の喪失を禁じる） |
| 「秘密情報ファイルのパスが平文で現れる読み取りが bash 経由で成立してはならない」 | 妥当（2026-07-25 に達成可能な範囲へ限定済み） | **維持** |
| （新規） | — | 「ガードが**正当な操作を止める**ことで、回避策の常用を招いてはならない」（例外の集合＝ R-001-5 / R-001-6 の裏返し。誤遮断が2回起きている実績に基づく） |

### 4-4. 「対象外」節への追記

- `find . -delete` / `find . -exec rm …`（**第2層・第3層のどちらも捕捉していない**。第1層が受ける）
- コンテナ外での起動（マウントが無ければフックもルールも無い。第1層が前提）
- 既存の4項目（難読化・ファイル実行・間接実行・ライブラリ経由）は維持

### 4-5. 既存要件を EARS へ一括移行すべきかの見立て

**結論: 一括移行は不要。R-001 のみ今回書き直し、R-002 / R-003 は次に触るときに移行するのが妥当。**

| 要件 | 現在の書き方 | EARS 化の効き目 | 判断 |
|---|---|---|---|
| R-001 | 箇条書きの「〜を deny する」 | **大きい**。層が2つに増え、「どの層が何を約束するか」を主語で書き分ける必要が出た。EARS の〈システム名〉がそのまま層になる | **今回移行**（ADR-012 の変更対象そのもの） |
| R-002 | 「サービス側は共通所有ファイルを編集・複製しない」 | 中程度。前提条件（基盤リポか否か）とトリガー（編集操作）が明確なので EARS に素直に乗る。ただし内容は変わらない | 次に触るとき（ADR-009 のフェーズ5で共通所有ロック撤去を検討する際） |
| R-003 | 受け入れ基準が「決め方」と「スクリプトが満たすこと」の2種混在 | **中〜大**。「許可宛先の決め方」は手続きであって EARS の応答に落ちにくい。分割が必要になる（手続きは `docs/rules/security.md` 側へ、システム応答だけ要件に残す） | 次に触るとき（生成物での実測を行う際） |

**一括移行を今やらない理由**: 移行そのものは意味の変更を伴わないが、
`check-requirements-coverage.sh` は本文の書式を検査していない（front-matter のみ検査）ため、
**書き直しても機械的な裏付けが増えない**。表記統一のためだけに Tier-S 要件3本を同時に触ると、
tier-tripwire の差分が膨らみレビューの焦点がぼやける。**触る理由があるものから移行する**のが安全。

## 5. 脅威モデル記述の改訂案

### 5-1. `docs/rules/security.md` §43-46「### 脅威モデル」

現在:

> このガードが想定するのは **「LLM の不注意な選択」と「人間の操作ミス」** である。
> **「悪意ある実行者」は想定していない**。悪意ある実行者は下記のいずれかで自明に回避できる。

改訂案:

> このガードが想定するのは **「実行時に生成され、実行前にレビューも信頼もできない任意のコード」** である
> （2026-08-03・ADR-012 で更新。旧: 「不注意であって悪意ある実行者ではない」）。
> プロンプトインジェクションで生成されたコードは不注意ではなく敵対的であり、
> AI エージェント環境では旧前提が成立しない。
>
> ただし**この層（静的検査）がその脅威に耐えるという意味ではない**。防御は3層に分かれ、
> 敵対的コードに耐えるのは第1層だけである。
>
> | 層 | 位置づけ | 何に耐えるか |
> |---|---|---|
> | 第1層 コンテナ隔離 | **唯一の本物の境界** | 敵対的コード。爆発半径を決める |
> | 第2層 `permissions.deny` | 事故防止 | 不注意。例外が書けないため主防御にできない |
> | 第3層 PreToolUse フック | 事故防止 | 不注意。見つからなければ素通しするため主防御にできない |
>
> 第2層・第3層を撤去はしない。**位置づけを「防御」から「事故防止」へ変えるだけ**である。

### 5-2. `docs/rules/security.md` §74-82「### 悪意ある実行者を想定する場合」

節ごと**「### 想定する脅威にどの層で対処するか」**へ改題し、
「想定する場合」という条件付きの書き方をやめる（既定で想定するため）。中身の3項目
（ファイル権限・秘密の非ファイル化・ネットワーク遮断）は維持し、ネットワーク遮断が
ADR-013 で実装済みであることへの導線も維持する。

### 5-3. `docs/rules/security.md` §58-72「### 守れないこと」

**追記2件**: `find . -delete` / `find . -exec`（どの層も見ていない）、コンテナ外での起動。

### 5-4. `CLAUDE.md` 30行目

長い引用ブロックのうち、脅威モデルの文（「脅威モデルは『不注意』であって『悪意ある実行者』ではなく…」）を
次に置き換える。**CLAUDE.md 側は1〜2行に圧縮し、詳細は `docs/rules/security.md` に置く**
（「要点＝守るべき結論を1行／詳細＝理由・手順・例外」の分担）。

> **脅威モデルは「実行時に生成され、レビューも信頼もできない任意のコード」である（ADR-012）。
> これに耐えるのはコンテナ隔離（第1層）だけで、`permissions.deny`（第2層）と
> PreToolUse フック（第3層）は事故防止であって防御ではない**（詳細: `docs/rules/security.md`）。

## 7. 検証手段の設計 ← 本体

**問題**: deny ルールは Claude Code 本体が評価するため、bats からは検証できない。
二重化した瞬間、「deny 側が生きているか」を確認する手段が無いまま層が1つ増える。
これは ADR-012 が正そうとしている「作動していないゲート」を自分で作ることになる。

**設計方針**: ADR-013 で確立した二本立て——**「設定がそう書いてあること＝監査（機械・常時）」と
「実際にそう振る舞うこと＝実測（節目で1回）」**——をそのまま適用する。
そのうえで、**機械で担保できない範囲を明示する**。

### 7-1. 監査層: 検査(14)「二重化の突合」（機械・常時・CI と pre-push で走る）

**何を検査するか**: 二重化した4判定（A2/A3/A4/A6）が**両層に存在すること**。

実装方式は検査(7)（共通所有ロックの `COMMON_OWNED` ↔ 配布 deny の突合）と同型にする。
**新しい正本ファイルは作らない**——4箇所目の重複を増やすため。両側から抜き出して突合する。

| 側 | 抜き出し方 |
|---|---|
| 第3層（フック） | `guard-dangerous.sh` の各判定に機械可読なマーカーを1行入れる。例: `# @dual-layer: A3 git reset --hard`。検査はこのマーカー集合を `grep` で抽出 |
| 第2層（deny） | 4ファイルの `.permissions.deny` を `jq` で抽出 |
| 対応表 | 検査スクリプト内に `DUAL_LAYER=( "A3:Bash(git reset *--hard*)" … )` として**1箇所だけ**持つ |

検査が赤にする条件:

1. マーカーがフックから消えた（第3層の退化）
2. 対応する deny ルールが4ファイルのいずれかに無い（第2層の退化・同期漏れ）
3. 対応表にある判定 ID がフックのマーカーに無い（対応表だけ更新して実装を忘れた）

**あわせて `DENY_CORE` を追加する**（検査(7) の `LOCK_CORE` と同型）。
「1件でもあれば緑」では大半が消えても素通りするため、**これが消えたら意味を失う**ルールを個別に要求する:
`Bash(git push:*)` / `Bash(git reset *--hard*)` / `Bash(git clean *)` / `Bash(git checkout -- *)` /
`Bash(rm -rf:*)` と、Read deny のコア（`Read(**/.env)` / `Read(**/.ssh/**)` / `Read(**/.aws/**)`）。

**あわせて検査(13) に1項目追加**（0-3 の案 A の条件）:
配布 `devcontainer.json` が共通 `.claude` を `/home/node/.claude` へマウントしていること。
これが消えると**フックもルールも無いまま起動する**。

**この検査が証明すること/しないこと**:
- ✅ 両層に判定が「書いてある」こと、片側だけ消えていないこと
- ❌ deny ルールが**実際に発火する**こと（Claude Code の挙動そのもの）

### 7-2. 挙動テスト: bats（機械・常時）— 第3層のみ

第3層はスクリプトなので従来どおり bats で検証できる。**A6 のテスト0件を埋める**（7-3）。
第2層は bats の射程外——ここは 7-1（書いてあること）と 7-4（実測）で分担する。

### 7-3. A6（`git checkout` による破棄）の穴埋め

判定はフックにあるがテストが1件も無い。追加する4ケース:

| # | コマンド | 期待 |
|---|---|---|
| 1 | `git checkout -- .` | deny |
| 2 | `git checkout .` | deny |
| 3 | `cd src && git checkout -- .`（チェイン） | deny |
| 4 | `git checkout -- src/app.py`（特定ファイル） | **deny**（現在の正規表現は `-- .` と `.` のみ一致するため**素通しする**。仕様として固定するか、判定を広げるかの判断が要る） |
| 5 | `git checkout feature/foo`（ブランチ切替） | 素通し（誤検知しない） |

**4 は判断が要る**。`git checkout -- <file>` は個別ファイルの変更破棄であり、
「`git checkout -- .` は危険だが `git checkout -- file` は許す」という現在の線引きに
明文の根拠が無い（`CLAUDE.md` の禁止リストは `git checkout -- .` のみ）。
フェーズ2の実装時に、**現状維持（素通しをテストで固定）か、判定を広げるか**を決める。

### 7-4. 実測: deny が実際に発火するか（半自動・節目で1回）

**機械で常時検証する手段は現時点で無い**（Claude Code に「このルールが発火するか」を問い合わせる
CLI は無い）。取り得る手段は3つ。

| 案 | 方法 | 決定性 | コスト | 評価 |
|---|---|---|---|---|
| ア | `claude -p "…"` のヘッドレス実行で deny 対象コマンドを試させ、ブロックされることを確認 | **低**（モデルがそのコマンドを実行しようとするかに依存する） | 中（API 呼び出し） | 単体では不採用。CI に入れると非決定的な赤を生む |
| イ | **手動チェックリスト**。`settings.json` の deny を変更したとき／Rebuild したときに、セッション内で数件叩いて確認する | 高（人間が直接叩く） | 低 | **採用**。`verify-isolation.sh` と同じ位置づけ（設定の正しさ＝監査、振る舞い＝実測） |
| ウ | 検証しない（書いてあることだけ担保） | — | ゼロ | 不採用。二重化の片側が「書いてあるだけ」になる |

**採用案（イ）の具体**: `scripts/verify-guardrails.md`（チェックリスト）を追加し、
`docs/rules/security.md` から導線を張る。項目は5件程度に絞る:

1. `git reset --hard HEAD~1` → deny される（A3・フラグ位置が後ろの形）
2. `git clean -nd` → deny される（A4・全面 deny の副作用の確認も兼ねる）
3. `git checkout .` → deny される（A6・新規追加分）
4. `cat .env` → deny される（B7・フック側）
5. `cat .env.example` → **通る**（例外が生きている＝過剰ブロックの回帰）

**5 を入れるのが要点**。「止まること」だけを確認するチェックリストは、
全部止める設定でも緑になる（ADR-013 の `verify-isolation.sh` で
「許可側に到達できること」を必ず測るのと同じ理由）。

### 7-5. 「両層とも生きている」ことの確認は3点セットで成立する

| 問い | 担保する仕組み | 頻度 |
|---|---|---|
| 両層に判定が書いてあるか | 検査(14) + `DENY_CORE` | 常時（CI・pre-push） |
| 第3層が期待どおり振る舞うか | bats（A6 追加後 158ケース想定） | 常時 |
| 第2層が実際に発火するか | 手動チェックリスト（5項目） | deny 変更時・Rebuild 時 |
| マウントが生きているか（フックの前提） | 検査(13) の追加項目 | 常時 |

**この4行のうち1つでも欠けると、二重化は「片側が書いてあるだけ」に退化する。**
