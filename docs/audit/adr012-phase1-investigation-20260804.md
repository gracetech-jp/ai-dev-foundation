## 0. 先に報告すべき前提の訂正

**ADR-012 の「第2層も主防御にできない」の根拠のうち、`permissions.deny` の表現力に関する前提が、
現行の公式ドキュメントと食い違っている。** ここが 2. の判定を左右するので先に置く。

公式ドキュメント（`code.claude.com/docs/en/permissions`、2026-08-04 取得。許可リストに入っているため実物を読めた）で確認した事実:

| # | 事実 | 出典の要旨 |
|---|---|---|
| 1 | Bash ルールは `*` を**任意の位置**で使える（先頭・中間・末尾） | 「Wildcards can appear at any position」`Bash(* install)` / `Bash(git * main)` が例示 |
| 2 | **シェル演算子を解釈し、各サブコマンドを独立に照合する** | 区切りは `&&` `\|\|` `;` `\|` `\|&` `&` 改行。「A rule must match each subcommand independently」 |
| 3 | deny / ask は**先頭の環境変数代入を跨いで**一致する | 「`Bash(rm *)` in deny still matches `FOO=bar rm -rf tmp/`」 |
| 4 | ラッパは剥がしてから照合する | `timeout` `time` `nice` `nohup` `stdbuf` `command` `builtin` `noglob`、**フラグ無しの `xargs`** |
| 5 | **deny には否定・例外が書けない** | 「a deny rule can't carry allowlist exceptions」。広い deny は狭い allow を常に上書きする |
| 6 | フックが exit 2 で止めた場合、**権限ルール評価前に停止**する。逆にフックが allow を返しても deny/ask は評価される | 「A hook that exits with code 2 stops the tool call before permission rules are evaluated」 |
| 7 | `ls` `cat` `echo` `head` `tail` `grep` `find` `diff` `stat` 等は**組み込みの読み取り専用扱い**で全モードでプロンプトが出ない | 「to require a prompt for one of these commands, add an `ask` or `deny` rule」 |
| 8 | `find` の `-exec` / `-delete` は prefix ルールの対象外。`watch` `setsid` `ionice` `flock` も同様 | 「a `Bash(find *)` rule doesn't cover these forms」 |

**帰結が2方向にある。**

- **移管できる範囲は ADR 執筆時の想定より広い。** 「deny はコマンド先頭の文字列一致のみだから
  `&&` 連結・フラグ順序違いをすり抜ける」という前提（`CLAUDE.md` 30行目、
  `guard-dangerous.sh` 2〜6行目のヘッダコメント）は、現行仕様では**不正確**である。
  チェイン実行はサブコマンド単位で照合されるため素通りしない。
- **一方で「例外が書けない」（#5）が決定的な制約になる。** 本リポジトリのガードは
  `.env.example` を通す・`process.env` を通す・`id_rsa.pub` を通す・骨格同期の `cp` だけ通す、という
  **例外の集合**で成り立っている。deny 側には例外を書く手段が無いため、これらは移管すると
  「正当な操作が止まる → 回避策が常用される → ガードが形骸化する」に直結する。

**したがって「deny に移せるものは移す」の対象は、例外を持たない判定に限られる。**
これが 2. の判定基準である。

> 未実測（フェーズ2で確認する）: #2 のサブコマンド単位照合が **deny でも**同じに効くか。
> ドキュメントの記述は allow 文脈で書かれており、deny について明示された文は #3 だけである。
> 実測しないまま「チェインは deny で止まる」と書くと、ADR-012 が正そうとしている
> 「作動していないゲート」を自分で作ることになる。

## 2. 各判定は `permissions.deny` で表現できるか

判定基準は 0. のとおり、**例外を持たない判定だけが移管候補**。

| 判定 | 移管可否 | 根拠 |
|---|---|---|
| A1 `rm` 再帰強制 | **部分的（フックに残す）** | 下記 2-1 |
| A2 `git push --force` | **移管可能（実質すでに移管済み）** | 2-2 |
| A3 `git reset --hard` | **移管可能** | 2-3 |
| A4 `git clean -f` | **移管可能** | 2-4 |
| A5 `git branch -D` | **部分的（フックに残す）** | 2-5 |
| A6 `git checkout` 破棄 | **移管可能（すでに deny 済み）** | 2-6 |
| B7 `.env` 読み取り | **表現できない** | 2-7 |
| B8 鍵・認証情報 | **表現できない（強い指標の一部のみ可）** | 2-8 |
| C 共通所有への書き込み | **表現できない（Edit 側はすでに移管済み）** | 2-9 |

### 2-1. A1 `rm` 再帰強制 — 部分的

書ける形:

```
"Bash(rm *-rf *)", "Bash(rm *-fr *)", "Bash(rm *-Rf *)", "Bash(rm *-fR *)",
"Bash(rm *--recursive *)", "Bash(rm *--force *)"
```

**表現しきれない理由**: この判定の本体は「再帰フラグ **かつ** 強制フラグ」という AND であり、
1つのパターンに2つのワイルドカード条件を AND で書く手段が無い。`-rvf` `-fvr` `-r -v -f` のような
**他フラグを挟んだ結合**は組み合わせが閉じないため、列挙では覆えない。
`Bash(rm *)`（全 `rm` を deny）まで広げれば覆えるが、`rm` は日常操作であり
0.#5 のとおり例外が書けないため、実質的に `rm` が使えなくなる。

**さらに絶対パス（`/bin/rm -rf x`）は deny 側では覆えない**が、フック側は覆える
（正規表現の前方境界が `[^[:alnum:]_.-]` であり `/` に一致するため）。この非対称が
「A1 をフックに残す」決め手になる。

### 2-2. A2 `git push --force` — 移管可能

現在すでに `Bash(git push:*)` で **push 全体を deny** している（`CLAUDE.md`「push は自ら実行しない」の機械化）。
これで `--force` 系も含めて覆えており、**フック側の A2 は現状すでに重複**である。

### 2-3. A3 `git reset --hard` — 移管可能

`Bash(git reset *--hard*)` で、位置に依存せず一致する（0.#1）。
現在の `Bash(git reset --hard:*)` は「`--hard` が直後に来る形」しか見ておらず、
`git reset HEAD~1 --hard` を取り逃がす。**移管というより deny 側の書き方を直す話**である。

### 2-4. A4 `git clean -f` — 移管可能

`Bash(git clean *)`（`git clean` 全面 deny）が最も素直。`git clean` は
「消える方向にしか働かない」コマンドで、正当な用途を deny で潰す損失が小さい。
フラグ単位で絞る（`*-f*`）と、パス引数に `-f` を含むケース（`git clean -n src/my-file`）を
巻き込むため、かえって精度が落ちる。

### 2-5. A5 `git branch -D` — 部分的

`Bash(git branch *-D *)` と `Bash(git branch *-D)` で主要形は覆える。
覆えないのは**結合フラグ** `-fD` / `-Df`（文字列として `-D` を含まない）。
ここを覆おうとすると `*D*` まで広げることになり、ブランチ名に `D` を含む全操作を巻き込む。
フック側は「`-[A-Za-z]*D`」で結合形を正確に取れるため、**フックに残す価値がある**。
ただし A1 と比べれば実害は小さい（削除対象は1ブランチ）。

### 2-6. A6 `git checkout` による破棄 — 移管可能

`Bash(git checkout -- *)` はすでに deny にある。`git checkout .` は
`Bash(git checkout .)` の完全一致で足りる（引数を取らない固定形のため）。

### 2-7. B7 `.env` 読み取り — 表現できない

3つの理由が独立に効く。

1. **例外が書けない（0.#5）。** この判定は `.env.example` / `.sample` / `.template` / `.dist` を
   通し、`process.env` / `import.meta.env` / `Bun.env` / `Deno.env` を通すことで成立している。
   `Bash(*.env*)` と書くと `grep -r process.env src/` や `cat .env.example` が止まる。
   実測済みの経緯として、この誤遮断は 2026-07-25 に**実際に起きて是正した**類型である
   （`guard-dangerous.sh` 98-101 行のコメント）。
2. **共起がサブコマンドを跨ぐ。** `echo .env | xargs cat` は、パスを持つ側（`echo .env`）と
   読み取る側（`xargs cat`）が別サブコマンドに分かれる。0.#2 のとおり照合はサブコマンド単位なので、
   **どちらのサブコマンドも単独では危険に見えない**。フックはコマンド全体の共起で見るため捕捉できる。
   なお 0.#4 により裸の `xargs` は剥がされて `cat` として照合されるが、その `cat` の引数に `.env` は無い。
3. **組み込み読み取り専用（0.#7）。** `cat` `head` `tail` `grep` は全モードでプロンプトが出ない。
   つまり deny を書かない限り**何も止まらない**。第2層に置くなら広い deny が必要になり、1 と衝突する。

### 2-8. B8 鍵・認証情報 — 表現できない（一部のみ可）

- **強い指標の一部は書ける**: `Bash(*.ssh/*)` `Bash(*.aws/*)` `Bash(*secrets/*)` `Bash(*.netrc*)` など。
  ただし B7 と同じ共起・組み込み読み取り専用の問題は残る（パスだけ一致させると
  `ls -la /home/node/.ssh/` のような**正当な操作まで止まる**。これも 2026-07-26 に実際に起きた誤遮断）。
- **`id_rsa` は書けない**。`id_*.pub`（公開鍵）を通す例外が必要で、deny には書けない。
- **`.key` / `.pem` / `.p12` / `.pfx` は書けない**。`row.key`（プロパティアクセス）と字面が同じで、
  フック側は「直後が引用符・空白・行末か」で判別している。deny のワイルドカードには
  **直後の文字種を条件にする手段が無い**。

### 2-9. C 共通所有ファイルへの書き込み — 表現できない（Edit 側はすでに移管済み）

- **ツール経路（Edit/Write）はすでに第2層にある**: `_base` の `Edit(CLAUDE.md)` 等13件。
  検査(7)① がこの deny とフックの `COMMON_OWNED` 正規表現の一致を機械強制している。
- **bash 経路は移管できない**。理由は2つ。
  1. `Bash(* CLAUDE.md*)` のような形にすると、`cat CLAUDE.md` / `diff CLAUDE.md`（正当な読み取り）まで止まる。
     フックは「書き込み系コマンドとの共起」で読み書きを区別している。
  2. **骨格同期の例外**（第1引数が `profiles/_base/` の `cp`/`rsync`/`install` だけ通す）が deny に書けない。
     これは `docs/rules/common-assets.md` が定める唯一の正規更新手順であり、塞ぐと運用が止まる。
- 発動条件（`profiles/_base/` の有無で基盤リポと配布先を切り替える）も deny では表現できない。
  同じ `settings.json` が両方に配られるため、**実行時にどちらのリポジトリかを判定する必要がある**。

### 移管対象の確定

| 分類 | 判定 |
|---|---|
| **deny へ移管（フックから削除可能）** | A2 / A3 / A4 / A6 |
| **フックに残す（deny では覆えない部分がある）** | A1 / A5 / B7 / B8 / C |

**A2〜A6 を移管しても、フックの行数はほとんど減らない**（該当は 53-81 行の29行）。
239行の大半は B7 / B8 / C とその例外処理であり、そこは移管できない。
「フックを縮小する」という ADR-012 決定4の効果は、**行数ではなく責務の明確化**に出る。

## 3. 既知の回避経路4つは、移管対象の判定に当てはまるか

| # | 回避経路 | 移管対象（A2/A3/A4/A6）への影響 | 判断 |
|---|---|---|---|
| 1 | **絶対パス** | **当てはまる。** `/usr/bin/git push --force` は `Bash(git push *)` に一致しない。フック側は前方境界が `/` を許すため捕捉する | **移管しても第3層に同じ判定を残す**（二重化の維持）。移管＝フックから削除、ではない |
| 2 | **`find` / `grep` 経由** | 当てはまらない。`find` から `git reset` は起こらない。ただし A1 には当てはまる（`find . -delete` は**現状フックも deny も捕捉しない**。0.#8） | A1 の穴として記録。フェーズ2の判断事項（フックに `find` を足すか、第1層に委ねるか） |
| 3 | **`Read()` deny を代替ツール経路で迂回** | 当てはまらない（A系はファイル読み取りではない） | B7/B8 をフックに残す根拠そのもの。移管したら穴が開く |
| 4 | **`echo` 経由のコマンドインジェクション（CVE-2025-54795）** | どちらの層でも決定打にならない。フックはコマンド文字列全体を見るため同型の迂回には強いが、フック自身も文字列検査であり同種の細工には弱い | 第1層（コンテナ）に委ねる。ADR-012 の結論と一致 |

**要点**: 回避経路1が全ての A 系判定に当てはまるため、**「deny に移す＝フックから消す」ではない**。
移すのは「第2層で拾えるようにする」ことであり、フック側の判定は二重化として残す方が防御は強い。
ADR-012 決定4の「フックには deny で書けないものだけを残す」を文字どおり実行すると、
**絶対パス経由の破壊的コマンドが両層から抜ける**。ここはフェーズ2で明示的に判断が要る。

### 4-2. 移管後に変わる箇所（2. の判定の帰結。実装案ではなく、変更が要る箇所の特定）

| ルール | 現状 | 移管後 | 理由 |
|---|---|---|---|
| `Bash(git reset --hard:*)` | フラグ直後の形のみ | `Bash(git reset *--hard*)` へ**書き換え** | `git reset HEAD~1 --hard` を現状取り逃がす |
| `Bash(git clean -f*)` | `-f` で始まる形のみ | `Bash(git clean *)` へ**拡大** | フラグ位置に依存しない。正当用途の損失が小さい |
| `Bash(git branch -D:*)` | `-D` 直後のみ | `Bash(git branch *-D *)` + `Bash(git branch *-D)` へ**拡大** | 結合フラグは覆えない（フックに残す） |
| `Bash(rm -rf:*)` | 結合順1種のみ | `Bash(rm *-rf *)` `*-fr *` `*-Rf *` `*-fR *` を**追加** | 主要な表記ゆれを第2層でも拾う |
| `Bash(git checkout .)` | 無し | **追加** | 現状 `git checkout -- *` のみ |
| `Bash(git push:*)` | あり | **変更なし** | push 全体 deny で足りている |
| Read 31件 | あり | **変更なし** | ツール経路の遮断。bash 経路とは別物 |
| `Edit(...)` 14件（`_base`） | あり | **変更なし** | ADR-009 ロックは維持（ADR-012 注意事項） |

### 4-3. 検査(6)・検査(7)への影響

- **検査(6) は「root ↔ `_base` の permissions が、共通所有ロック `Edit(...)` を差し引いて同値」を要求する。**
  Bash deny を足すときは **root と `_base` の両方に同じものを足さないと即赤**になる。
  さらに `profiles/*/files/.claude/settings.json` は「`ask` 以外は `_base` と完全一致」が要求されるため、
  **実質4ファイル同時更新**になる（ADR-013 の Dockerfile 4本と同じ構造）。
- **検査(6) の正規化は配列の値だけをソートする実装に直っている**（ADR-013 実装時の是正）。
  deny 配列を増やす分にはこの穴は再発しない。
- **検査(7)① は `_base` の `Edit(...)` deny が、フックの `COMMON_OWNED` 正規表現に必ず掛かることを要求する。**
  → **フックから検査C を削除すると、`sed -n "s/^\s*COMMON_OWNED='\(.*\)'$/\1/p"` の抽出が空になり、
  検査(7)が「抽出できません」で赤になる。** 検査C は残す判定なので実害は無いが、
  **フックを縮小する際に `COMMON_OWNED` の定義形式（1行のシングルクォート代入）を崩すと監査が壊れる**。
  フェーズ2で触る場合は検査(7)の抽出方法も同時に見ること。
- 検査(3) は `profiles/_base/.claude/{settings.json,scripts/guard-dangerous.sh}` の**配布行の実在**を見る。
  ファイルを消さない限り影響なし。
- 検査(8) は Makefile と CI ジョブのみ。影響なし。
- 検査(13) は Dockerfile / compose / `defaultMode` と `ask` の `mcp__*`。影響なし。

### 5-1. シムが塞いでいた穴は、廃止後どうなるか（重要）

シムの目的は「`CLAUDE_PROJECT_DIR` が起動ディレクトリを指すため、サブディレクトリから
`claude` を起動するとフックが見つからず**無警告で素通しする**（fail-open）」を止めることだった。

**この穴は ADR-013 のマウント設計で構造的に解けている。**

- 共通の `.claude` を **ユーザースコープ（`/home/node/.claude`）へマウント**する形になった。
- 基盤 root の `settings.json` のフックコマンドは **絶対パス** `bash /home/node/.claude/scripts/guard-dangerous.sh`。
- ユーザースコープの設定は**起動ディレクトリに関係なく効く**ため、`CLAUDE_PROJECT_DIR` に依存しない。

一方、**配布側（`_base` / プロファイル）のフックコマンドは今も
`bash "$CLAUDE_PROJECT_DIR/.claude/scripts/guard-dangerous.sh"`** であり、
シムを消すだけだと**シムが塞いでいた fail-open がそのまま戻る**。

→ **フェーズ2の判断事項**: 配布側のフックコマンドを絶対パス（ユーザースコープ）へ寄せるか、
プロジェクト同梱の `.claude/scripts/` を残したまま `$CLAUDE_PROJECT_DIR` を使い続けるか。
前者ならシム廃止と同時に穴も消える。後者なら穴が残るので、シム廃止は**穴を1つ開ける変更**になる。

## 9. フェーズ2に持ち越す判断事項・実測項目

**判断が要る点（フェーズ2の冒頭で確認したい）**

1. **移管＝フックからの削除にするか、二重化として残すか。** 3. のとおり、A系を文字どおり
   フックから消すと絶対パス経由が両層から抜ける。**残すことを推奨**（移管の目的は
   「第2層でも拾えるようにする」であって、第3層を薄くすることではない）。
2. **配布側フックの委譲先をユーザースコープの絶対パスへ寄せるか**（5-1）。
   寄せないままシムを消すと fail-open が戻る。
3. **`find . -delete` を塞ぐか、第1層に委ねるか**（3. の回避経路2）。現状どちらの層も見ていない。
4. **deny ルールの検証をどう担保するか**（8.）。bats では検証できないため、
   「deny に書いてある」ことの静的検査（監査の新しい検査層）を足すかどうか。

**実測が要る項目（推測で進めない）**

- deny ルールが**サブコマンド単位で照合されるか**（0.#2 は allow 文脈の記述）。
- `Bash(rm *-rf *)` のような**中間ワイルドカードの実挙動**。
- `Bash(git clean *)` を deny に入れたとき、**`git clean -n`（ドライラン）も止まるか**。
- 組み込み読み取り専用コマンド（`cat` 等）に対する deny が、**bypassPermissions 下でも発火するか**。

**やらないこと（フェーズ1の制約どおり）**: 実装・差分の提示・テストの再編。すべてフェーズ2で行う。
