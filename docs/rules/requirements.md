# 要件の永続資産化とトレーサビリティ（共通）

要件は「タスクごとにLLMが再導出する派生物」ではなく、**人間が批准する永続・バージョン管理された
一意ID付きの一次成果物**とする。CIが緑でも要件が未達なら不合格、を機械的に判定できる土台を定める。

> この枠組みはサービス非依存。何が要件かの**中身**（ドメイン固有の受け入れ基準・禁止事項・機微パターン）は
> 各サービスが `docs/requirements/` と `SERVICE.md` に自分のドメイン語で書く。本ファイルは**枠**だけを定める。

---

## 1. 配置と採番

- 要件は `docs/requirements/` に **1要件 = 1ファイル**で置く（`R-<連番>-<スラッグ>.md`）。
- **一意ID `R-<連番>`**（例 `R-101`）を各要件に振る。
  - **不変**：一度振ったIDの意味を変えない。
  - **欠番許容・再利用禁止**：要件を廃止してもその番号を別要件に再利用しない（トレースの取り違え防止）。
- 要件は Tier（`docs/rules/tiers.md`）を持ち、Tierが検証の厳格度を決める。

## 2. front-matter スキーマ

```yaml
---
id: R-101                    # 一意・不変・再利用禁止
title: <要件の一行表題>
tier: <S|A|B|C>              # 人間批准フィールド（tiers.md）。自己申告で下げられないよう deny 保護下に置く
status: <draft|ratified>     # draft→ratified は人間の commit のみ（LLMは要件ディレクトリを書けない）
ratified_by: <批准した人間>   # 要件そのものの批准者（status: ratified 時に必須）
tests_ratified_by: <人間>    # S/A 必須（B1）: 要件↔テストの「妥当性」を人間が確認した証跡
tests_ratified_sha: <SHA>    # S/A 必須（F1）: 批准時点のテスト資産群の正規化ハッシュ
paths:                       # この要件が統べる機微コードの glob（Tierトリップワイヤの照合キー）
  - "<この要件が統べる機微コードのglob>"
test_assets:                 # F1/F3: ハッシュ対象に含めるテスト/フィクスチャの glob
  - "<ハッシュ対象に含めるテスト/フィクスチャのglob>"
negative_space:              # 起きてはいけないこと（S/A 必須）。抽象語でなく自サービスの具体語で
  - "<このTierで起きてはならないことを1件ずつ列挙>"
---
## 受け入れ基準
- <入力条件 → 期待結果を、テストで検証可能な粒度で列挙>
```

## 3. 批准（自己申告を信頼しない）

- `status: ratified` と `tier`・`tests_ratified_by`・`tests_ratified_sha` は**人間の commit でのみ**成立する。
- 要件ディレクトリ `docs/requirements/` は機械的に書き込み拒否される（`settings.json` deny ＋ フック。
  LLM は要件を生成・改変できない）。LLM は下書きを保護外のスクラッチに出し、人間が中身を確認して
  `docs/requirements/` へ移し批准する（動線は要件抽出スキル側に定義）。

## 4. 要件↔テストの紐づけと妥当性（B1）

- テストは要件IDのマーカーで紐づける（マーカー規約の詳細: `docs/rules/testing.md`）。
- **マーカーは「紐づけの主張」であって「検証の妥当性」ではない**。実装LLMはハッピーパスしか見ない
  テストにもマーカーを貼れてしまう。そこで **Tier S/A は `tests_ratified_by`（人間の妥当性批准）を必須**とし、
  マーカーの存在だけでは緑にしない。

## 5. negative space（起きてはいけないこと）

- 禁止事象の類型はサービス固有であり、**本ファイルに具体例として焼き込まない**。
  各サービスが `docs/requirements/` の要件と `INVARIANTS` テンプレに自分の具体語で書く。
- negative space は Tier S/A で必須。これは `docs/rules/consistency.md` の「モデル/設定から**導かれる
  派生的不変条件**」とは**別物**であり、**設計から再生成させない人間確定の固定資産**として置く。
- adversarial テストで検証する。

## 6. adversarial テストの生成規約（B1）

- adversarial テストは**実装LLMに生成・マーカー付与させない**。次のいずれかに限る：
  1. **人間が執筆**したもの。
  2. **実装とは別コンテキストのモデル**が要件文面から逆生成し、**人間レビューを経た**もの。
- 実装者（実装LLM）が自分の実装に合わせて骨抜きの adversarial テストを書く経路を断つ。

## 7. 批准後のテスト改変検知（F1）— tests_ratified_sha

一度 ratify した後にテストを骨抜きに書き換えても緑が続く「時間軸の穴」を塞ぐ。
S/A 要件は批准時点のテスト内容ハッシュを持ち、現在値と照合する（不一致＝要再批准で赤）。

**ハッシュの算出（決定論・再現可能）**：

本仕様は一貫して**ファイル単位**で扱う（関数/ブロックの抽出をしない）。言語依存の抽出を排して
決定論性を最大化し、批准時に人間が算出する値と CI 再計算値のズレを防ぐため。過剰発火（対象ファイル内の
無関係な編集でも再批准を要する）は fail-safe 側なので許容する。

1. **対象** = 当該要件IDの req/adversarial マーカーを含むテスト**ファイル** ∪ front-matter `test_assets` の
   全ファイル（重複排除）。マーカーは行内に含まれていればそのファイルを対象にする（関数/ブロック抽出はしない）。
2. **正規化**（各対象ファイルに適用）：
   - ① CRLF→LF
   - ② 行末空白の除去
   - ③ 空行の除去
   - ④ **行頭が**コメント記法（`SERVICE.md` で定義）**で始まる行のみ**除去する。行末コメント・複数行
     コメントブロックは正規化対象外（そのまま残す）。コメント記法が `SERVICE.md` に**未定義**のサービスでは
     ④ を**スキップ**し ①②③ のみ適用する（未定義で暗黙に何かを消さない＝挙動を一意化）。
     コメント改変でハッシュが変わるのは過剰発火side＝fail-safe で許容する。
3. **直列化**：対象ファイルを**ファイルパスの昇順**で連結する（開始行ソート・スパン連結はしない）。
4. **ハッシュ**：直列化した内容を sha256。
5. **再批准**＝人間が新しい `tests_ratified_sha` を書いて commit した時のみ成立。**自動更新は禁止**。

**制約（決定論のため）**：ハッシュ対象ファイルのパスに**空白（スペース・タブ・改行）を含めない**。
含まれると単語分割で別ファイル扱いになりハッシュが非決定化するため、照合スクリプトは空白を含む対象パスを
検出した時点で **exit 2（fail-closed）**で止める（silent な F1 誤発火を防ぐ）。

## 8. 機微 fixture の骨抜き対策（F3）

- 機微な test・fixture（アクセス制御のテストデータ等、サービス固有）は、該当 S/A 要件の `test_assets` に
  含める。これにより fixture の弱体化改変は §7 のハッシュ不一致で検知され、警告ではなく**再批准要求（赤）**になる。
- ドキュメントのみの変更は従来どおり軽微扱い。

---

## まとめ（原則）

- 要件は**永続・一意ID・人間批准**の一次成果物。LLM が要件ループを自己完結させない。
- マーカー・Tier・ベースライン・ハッシュのいずれも、**人間批准かコード実態からの裏取り**で閉じる
  （自己申告を単独で信頼するゲートを作らない）。
