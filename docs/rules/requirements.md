# 要件の永続資産化とトレーサビリティ（共通）

要件は「タスクごとにLLMが再導出する派生物」ではなく、**永続・バージョン管理された一意ID付きの
一次成果物**とする。CIが緑でも要件が未達なら不合格、を機械的に判定できる土台を定める。

> この枠組みはサービス非依存。何が要件かの**中身**（ドメイン固有の受け入れ基準・禁止事項・機微パターン）は
> 各サービスが `docs/requirements/` と `SERVICE.md` に自分のドメイン語で書く。本ファイルは**枠**だけを定める。

> **2026-07-24 批准レス化（ADR-008）**: 人間批准を要する仕組み（LLM編集封鎖・`tests_ratified_by`・
> `tests_ratified_sha`・Tier の人間批准・CODEOWNERS レビュー必須化）は、solo 運用での対応待ちが
> 作業効率を損なうため廃止した。担保は「要件の永続ファイル化」と「機械ゲート（req-coverage /
> tier-tripwire）」に一本化する。

---

## 1. 配置と採番

- 要件は `docs/requirements/` に **1要件 = 1ファイル**で置く（`R-<連番>-<スラッグ>.md`）。
- **`R-000-template.md` は配布テンプレであり要件ではない**（`status: draft`・`tier` はプレースホルダ）。
  新規要件はこれを複製して次の連番で作る。この固定名は `check-requirements-coverage.sh` の
  **検証対象外**（唯一の除外。他の名前・場所で tier がプレースホルダ/不正なら exit 2＝fail-closed のまま）。
- **一意ID `R-<連番>`**（例 `R-101`）を各要件に振る。
  - **不変**：一度振ったIDの意味を変えない。
  - **欠番許容・再利用禁止**：要件を廃止してもその番号を別要件に再利用しない（トレースの取り違え防止）。
- 要件は Tier（`docs/rules/tiers.md`）を持ち、Tierが検証の厳格度を決める。

## 2. front-matter スキーマ

```yaml
---
id: R-101                    # 一意・不変・再利用禁止
title: <要件の一行表題>
tier: <S|A|B|C>              # tiers.md の4軸で判定。過小申告はトリップワイヤがコード実態から裏取りする
status: <draft|ratified>     # ratified の要件のみゲート対象。draft のままだと紐づくテストは dangling＝赤
ratified_by: <確定させた主体> # 任意の証跡
paths:                       # この要件が統べる機微コードの glob（Tierトリップワイヤの照合キー）
  - "<この要件が統べる機微コードのglob>"
negative_space:              # 起きてはいけないこと（S/A 必須）。抽象語でなく自サービスの具体語で
  - "<このTierで起きてはならないことを1件ずつ列挙>"
---
## 受け入れ基準
- <入力条件 → 期待結果を、テストで検証可能な粒度で列挙>
```

## 3. 要件の編集と有効化（批准レス運用）

- 要件は LLM も直接生成・編集できる（旧「LLM編集封鎖」は廃止。ADR-008）。
- `status: ratified` にした要件だけが req-coverage / tier-tripwire のゲート対象になる。
  内容が確定したら ratified に更新すること（draft 放置は dangling で赤になる）。
- **要件を実装の都合で書き換えない（自己完結ループの防止）**。既存要件の意味変更・緩和・削除は
  ユーザーの了解を得てから行い、変更理由をコミットメッセージに残す。テストを緑にする目的で
  要件側を動かすことは、理由の如何によらず禁止。

## 4. 要件↔テストの紐づけ

- テストは要件IDのマーカーで紐づける（マーカー規約の詳細: `docs/rules/testing.md`）。
- 未カバー要件（Tier S/A は即赤・B/C はベースライン猶予可）と dangling マーカーは
  `check-requirements-coverage.sh` が機械検出する。

## 5. negative space（起きてはいけないこと）

- 禁止事象の類型はサービス固有であり、**本ファイルに具体例として焼き込まない**。
  各サービスが `docs/requirements/` の要件と `INVARIANTS` テンプレに自分の具体語で書く。
- negative space は Tier S/A で必須。これは `docs/rules/consistency.md` の「モデル/設定から**導かれる
  派生的不変条件**」とは**別物**であり、**設計から再生成させない固定資産**として置く。
- adversarial テストで検証する（S/A で negative_space があるのに adversarial テストが無ければ赤。G4）。

## 6. adversarial テストの生成規約

- adversarial テストは、実装した同一コンテキストが自分の実装に合わせて書くと骨抜きになりやすい。
  **要件文面だけを入力にした別コンテキスト（別セッション・サブエージェント等）での生成を推奨**する
  （必須の人間レビューは課さない。ADR-008）。

## 7.〜8.（廃止）

- 旧 §7「批准後のテスト改変検知（F1）— tests_ratified_sha」・旧 §8「機微 fixture の骨抜き対策（F3）」は
  2026-07-24 の批准レス化（ADR-008）で廃止した。ハッシュ再批准のたびに人間の commit を要する運用が
  待ちを生むため。テストの弱体化に対する防波堤は、カバレッジ・フロア（一方向ラチェット）・
  adversarial 必須（G4）・tier-tripwire（機微 test/fixture にも S 要件を要求）で維持する。

---

## まとめ（原則）

- 要件は**永続・一意ID**の一次成果物。LLM が要件をタスクごとに再導出して自己完結させない。
- 要件↔テストの照合（未カバー・dangling・G4・B3）は**機械ゲート**で閉じ、人間の対応待ちは作らない。
- 要件の意味変更はユーザー了解＋コミット記録。実装の都合で要件を動かさない。
