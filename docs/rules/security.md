# セキュリティガイドライン（共通）

本ファイルは全サービス共通の原則のみを扱う。**秘密情報管理の具体的な仕組み**（設定ライブラリ・設定ファイルの場所）、**アップロード許可形式**、**脆弱性スキャンツール名**など、スタック・サービス固有の具体は各サービスの `PROJECT.md` に定義する。

## 秘密情報の管理
- APIキー・パスワード・トークンをコードに直書き禁止
- 環境変数は`.env`で管理し、`.env.example`にキー名のみ記載する
- `.env`は必ず`.gitignore`に追加する
- シークレットのローテーションは定期的に実施する
- 環境変数のスキーマ検証（必須キーの未設定・型不一致をアプリ起動時に検出）を行う。具体的な仕組みは `PROJECT.md` に定義する

## 入力バリデーション
- ユーザー入力は必ずバリデーション・サニタイズを行う
- SQLはパラメータバインドを使用し、文字列結合禁止
- ファイルアップロードは拡張子・MIMEタイプ・サイズを検証する（許可形式・上限は `PROJECT.md` に定義）

## 出力
- ログに個人情報・秘密情報を出力しない
- エラーメッセージに内部実装の詳細を含めない（本番環境）
- レスポンスに不要なフィールドを含めない

## 依存パッケージ
- 依存パッケージの脆弱性チェックを定期的に実施する（使用するツールは `PROJECT.md` に定義）
- 重大な脆弱性は即時対応する
- 不要なパッケージは削除する

## AIエージェントのガードレール
- 破壊的操作・秘密ファイル読み取りは、プロンプト任せにせず `.claude/settings.json` の `permissions.deny` と
  PreToolUse フック `.claude/scripts/guard-dangerous.sh` で機械的に遮断する（プロジェクト単位で配布済み）。
- **組織全体で強制したい制御は managed-settings（管理者スコープ）で設定する**。プロジェクトの `settings.json` には
  置けない管理者専用キー（`disableBypassPermissionsMode`＝`--dangerously-skip-permissions` の抑止、
  `allowManagedPermissionRulesOnly` / `allowManagedHooksOnly` / `allowManagedMcpServersOnly`）は、
  IT管理者が managed-settings に定義する。プロジェクト設定に書いても無効、または自リポのフック/権限を壊すため注意。
  （出典: Claude Code 公式 settings ドキュメント）

「書いてあること」は監査が、「実際に発火すること」は手動チェックリストが受け持つ。
チェックリストには**通ることの確認（`cat .env.example` / `git clean -n`）を必ず含める**——
止まることだけを見るチェックは、全部止める設定でも緑になるため。

## 静的検査の防御ライン

`guard-dangerous.sh` は正規表現によるコマンド文字列の静的検査であり、**守れる範囲には原理的な上限がある**。
この節はその上限を明文化する。ここを曖昧にすると「ガードがあるから安全」という誤った前提が積み上がるため。
（2026-07-25 明文化。サービス側 devcontainer への python / node 導入で「インタプリタが存在しない」前提が
消え、インタプリタ経由の読み取りをガード対象に加えた際に、同時に限界も固定した）

### 脅威モデル（2026-08-03・ADR-012 で更新）

想定するのは **「実行時に生成され、実行前にレビューも信頼もできない任意のコード」** である。
旧前提（「LLM の不注意な選択と人間の操作ミス。悪意ある実行者は想定しない」）は破棄した。
**プロンプトインジェクションで生成されたコードは不注意ではなく敵対的**であり、
AI エージェント環境では旧前提が成立しないため。

**ただし、この層（静的検査）がその脅威に耐えるという意味ではない。** 防御は3層に分かれ、
敵対的コードに耐えるのは第1層だけである。

| 層 | 位置づけ | 何に耐えるか | 失敗の仕方 |
|---|---|---|---|
| 第1層 コンテナ隔離（ADR-013） | **唯一の本物の境界** | 敵対的コード。爆発半径を決める | マウント・ネットワーク規則の誤り |
| 第2層 `permissions.deny` | 事故防止 | 不注意 | **例外を書けずに失敗する**（広い deny は正当な操作を止め、狭い deny は覆えない） |
| 第3層 PreToolUse フック | 事故防止 | 不注意 | **見つからずに失敗する**（設定・マウントが欠けると無警告で素通し） |

**第2層・第3層を撤去はしない。位置づけを「防御」から「事故防止」へ変えるだけである。**
両層で重複して判定するのは、上表のとおり**失敗の仕方が独立している**ためで、
片側だけが消える退化は `audit-consistency.sh` の検査(14)が機械検出する（ADR-012 決定4）。

以下はその第2層・第3層——静的検査——の防御ラインである。

### 守れること

- 秘密パス（`.env`・`*.pem`・`id_rsa`・`.ssh/`・`.aws/` **配下全体**・`secrets/`・`.netrc`・
  `.git-credentials`・`.kube/`・`.docker/config.json` 等）が**平文でコマンド文字列に現れる読み取り**を止める。
- 読み取り手段は `cat` 等の外部コマンドに限らず、インタプリタ（`python`・`node`・`perl`・`ruby`・
  `php`・`deno`・`bun`・`tsx`・`ts-node`）のインラインコード（`-c` / `-e` / `-p` / `--eval` / `-m`）、
  ヒアドキュメント、パイプ経由の流し込みを含む。
- `uv run` / `poetry run` のようなラッパ経由でも、**インラインペイロードならコマンド文字列に現れるため捕捉される**
  （`uv run python -c "print(open('.env').read())"` は deny）。捕捉できないのはペイロードが別ファイルにある場合。

### 守れないこと（対象外と明示する）

- **難読化**: 文字列分割（`'.e'+'nv'`）・`chr()`・`Buffer.from(...,'base64')` などでパスを組み立てる書き方。
  インタプリタの引数はチューリング完全な言語であり、正規表現でファイル読み取り意図を判定することは**不可能**。
- **ファイル実行**: `python script.py` / `node script.js`。ファイルの中身はフックから見えない。
  塞ぐには「全てのスクリプト実行の禁止」が必要になり、開発が成立しない。
- **間接実行**: `npm run` / `npx` / `node_modules/.bin/*`、および `uv run` / `poetry run` で
  **ペイロードを別ファイルに置いた場合**（`uv run scripts/dump_env.py`）。実行内容は package.json や
  スクリプトファイルにあり、フックからは追えない。
  ※ `uv run` / `poetry run` でもインラインペイロード（`-c` / `-e`）なら捕捉される（上記「守れること」参照）。
- **ライブラリ経由**: `require('dotenv').config()` のようにパス文字列がコマンドに現れない読み込み。
- **環境変数経由の漏洩**: `env | grep` 等。ファイル読み取りではなく、このガードの責務外。
- **`find` 経由の削除**: `find . -delete` / `find . -exec rm …`。**第2層・第3層のどちらも見ていない**
  （deny の prefix ルールは `-exec` / `-delete` 形を覆わず、フックにも `find` の判定は無い）。
  2026-08-04 に明文化。第1層が受ける。
- **コンテナ外での起動**: フックもルールも devcontainer のマウント経由で配られるため、
  コンテナ外で `claude` を起動すると**どちらも無い状態**になる。`CLAUDE.md` も `docs/rules/` も
  同様に見えないため、ガードだけが特別に脆いわけではない。第1層が前提である。

これらが「塞げていないこと」は `tests/guard-dangerous.bats` の「既知の限界」節で
**通過することをテストとして固定**している。バグではなく仕様である。

### 想定する脅威にどの層で対処するか

上の脅威モデルのとおり、敵対的コードは**既定で想定する**（「想定する場合」という条件付きではない）。
静的検査（第2層・第3層）の拡張では解決しない。次のいずれかで対処すること。

- **ファイル権限**: 秘密ファイルをエージェント実行ユーザーから読めない所有者・パーミッションにする
- **秘密の非ファイル化**: シークレットマネージャ経由の取得に切り替え、ファイルとして置かない
- **ネットワーク遮断**: 読めても持ち出せないよう、コンテナの外向き通信を制限する
  （ADR-013 で実装した。下記「開発コンテナの隔離境界」を参照）

## 開発コンテナの隔離境界（ADR-013）

秘密を読めても**持ち出せない**ようにするのがこの層である。上の静的検査とは別物で、
静的検査が原理的に守れない範囲（難読化・ファイル実行・`npm run` 経由）をここで受ける。

### 構成

| 項目 | 設定 |
|---|---|
| 外向きネットワーク | 既定拒否 + 許可リスト（`init-firewall.sh`） |
| 実行ユーザー | 非 root。`sudo` は `init-firewall.sh` 1本のみ（`sudo` グループからも外す） |
| ホームディレクトリ・SSH 秘密鍵・Docker ソケット | マウントしない |
| 兄弟プロジェクト | マウントしない |
| 権限モード | `permissions.defaultMode: bypassPermissions` |
| MCP | `ask` の `mcp__*`。bypass は明示的な `ask` だけは素通りしないため、これが実行時の歯止めになる |

### 触ってはいけない前提

- **ファイアウォールはイメージ内の root 所有コピー（`/usr/local/bin/init-firewall.sh`）を実行する。**
  マウントされたワークスペース側のファイルを sudo 実行する構成にすると、書き換えてから sudo する経路が
  そのまま root 昇格になる。許可ドメインの追加分（`extra-allowed-domains.txt`）を
  ビルド時に焼き込むのも同じ理由——実行時にワークスペースから読ませない。
- **スクリプトは引数を解釈しない。** sudoers は引数まで固定できないため、`--disable` のような
  無効化オプションを持たせるとコンテナ内から遮断を解除できてしまう。

### 効いているかの確認（Rebuild のたび）

```bash
bash scripts/verify-isolation.sh
```

適用スタンプ（`/var/log/init-firewall.status`）と実際の通信の両方で判定する。
**iptables のルールは読まない**——`sudo` を1本に絞った以上、非 root ではルールを読めず、
読めるようにすることは消せるようにすることでもあるため。「ルールがこう書いてある」ではなく
「実際にこう振る舞う」で見る。`postStartCommand` が黙って失敗したときが最悪の壊れ方
（見た目は正常なまま全開放）であり、それを検出するのがこのスクリプトの主目的である。

### 遮断で詰まったときの回復手順

**回復はすべてホスト側で行う。コンテナ内から解除する手段は用意しない**——回復経路をコンテナの外に
置くこと自体が境界の意味だからである（ADR-012 決定5「fail-closed とし、回復手順を必須にする」は、
手順が文書化され実行可能であることを求めており、コンテナ内から実行できることは求めていない）。

| 症状 | 回復方法 |
|---|---|
| ビルドが失敗してコンテナが起動しない | ホストのターミナルで退避しておいた `devcontainer.json` / `Dockerfile` を書き戻し、Rebuild |
| 起動するが必要な通信が通らない | ホストで `devcontainer.json` の `postStartCommand` 行を一時的に削除 → Rebuild（遮断なしで起動）→ 許可リストを直す → 行を戻す |
| 許可済みのドメインに繋がらなくなった | CDN の IP ローテーションの可能性。コンテナを再起動すれば名前解決からやり直す |
| コンテナに入れない | ワークスペースはホスト上の実ファイルなので、ホストのエディタで直接編集できる |

**切替前に必ず `devcontainer.json` と `Dockerfile` をホスト側でコピーして退避すること。**
未コミットの状態で壊すと git から戻せないため、この退避が唯一の即時復旧手段になる。

### 許可ドメインを増やすとき

1. `init-firewall.sh` の `BASE_DOMAINS`（全プロジェクト共通）か、
   プロジェクト固有なら `.devcontainer/extra-allowed-domains.txt` に1行足す
2. Rebuild する（実行時に反映する経路は無い。これは仕様）
3. **推測で足さない。** 実際に失敗したツールのエラーメッセージから宛先を特定してから足す

**許可宛先の集合は要件 R-003 の管理下にある**（基盤リポの `docs/requirements/`）。ここは設定値ではなく
境界そのもの——外へ出られる宛先の集合が爆発半径を決める——ため、1行足すことは境界を広げることと
同じである。上記のファイルを変更すると `make tier-tripwire` が R-003 との対応を要求し、複製4本の
一致は監査の検査(10)が diff で強制する。**黙って広げられない状態を保つのが要件化の目的**である。

### 過剰ブロックとの釣り合い

- **ガードが正当な操作を妨げると、回避策が常用されてガード自体が形骸化する**。過剰側に倒すのは原則だが、
  日常操作を止めるほど倒してはいけない。この釣り合いを崩した具体例が `.env.*` の Read deny だった。
- そのため **bash 側と `Read` deny 側で書き方を意図的に非対称にしている**。bash 側は
  `\.env(\.[a-zA-Z0-9_]+)*` で全サフィックスを覆い、`Read` deny 側は `.env.production` /
  `.staging` / `.development` / `.test` を明示列挙する。`Read(.env.*)` と書くと `.env.example` に
  一致し、deny は allow より優先され否定も書けないため、テンプレートが読めなくなるからである。
- 列挙から漏れたサフィックス（例 `.env.qa`）は `Read` ツールで読めるが、**bash 側のワイルドカードが
  残るため多層防御は維持される**。これが漏れを許容する根拠。
- **`.env.example` が読める状態は意図的**であり、穴ではない。`.env.example` / `.sample` / `.template` /
  `.dist` は bash 側でもサニタイズで対象外にしている。

- `process.env` / `import.meta.env` は**言語の構文であってファイルパスではない**ため、`.env` 判定から除外する。
  この除外を外すと `node -e "console.log(process.env.NODE_ENV)"` のような正当なワンライナーが軒並み止まる。
- 逆に共通所有ファイル（ADR-009）については、読み取り／書き込みを静的に区別できないため、
  インタプリタとの共起は読み取り目的でも deny する（読むだけなら Read ツールで足りるため実害が小さい）。
- `.key` / `.pem` / `.p12` / `.pfx` は**言語のプロパティアクセスと字面が同じ**（`row.key`）。
  拡張子の直後が引用符・空白・行末のときだけ秘密ファイルとみなす。この判定に引用符を使うため、
  ここだけクォート除去前のコマンドを見る。受け入れた偽陰性は `cat a.key|base64`（空白なしパイプ）で、
  許容集合に `|` を足すと JS の `o.key || x` を巻き込むため入れない。
- **`secrets/` は巻き添えを承知で広く取っている**。`git diff secrets/` や `grep -rn TODO secrets/` も deny になる。
  sops / git-crypt / SealedSecrets で暗号化済みの `secrets/` を運用するリポジトリでは日常操作が止まるため、
  **実運用で作業が阻害されるなら除外を再検討する**（現時点では秘密が素で置かれる想定を優先し、fail-safe 側に倒している）。
