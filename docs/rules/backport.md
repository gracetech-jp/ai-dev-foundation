# 共通基盤の逆輸入と順輸入（サービス ⇄ 共通リポ）

共通基盤は一方通行ではない。共通リポの `new-service.sh` でサービスを作った後、
そのサービス内で共通ルール・仕組みが育つ。育った改善を**共通リポへ還流（逆輸入）**し、
還流された改善・共通リポで生まれた新ルールを**既存の各サービスが取り込む（順輸入）**。
この双方向ループを標準プロセスとして各サービスに備える。

```
共通リポ ──(new-service.sh で雛形展開)──▶ サービス
   ▲│                                       │▲
   │└──(sync-from-common.sh で取込)─────────┘│
   └───(backport-to-common.sh で還流)◀───────┘
```

---

## 仕組み

- **`.backport-manifest`**：このサービスが持つファイルのうち「共通所有（全サービス共通の基盤・ルール）」を列挙。
- **`scripts/backport-to-common.sh`**：マニフェストに載ったファイルだけを共通リポへ上書き同期する（更新のみ・削除なし・自動バックアップ・dry-run 付き）。
- **`scripts/sync-from-common.sh`**：逆方向（共通 → このサービス）。**共通リポ側**のマニフェストを正として共通所有ファイルを取り込む（新規追加あり・削除なし・自動バックアップ・dry-run 付き。設計理由: ADR-005）。
- **両スクリプトはマニフェストに載っており自己ホスティング**。＝ツール自身の改善も還流・取込で全サービスへ伝播する。
- 一方**マニフェスト（`.backport-manifest`）自身は還流対象に含めない**。マニフェストはリポごとのローカル設定であり、
  あるサービスのローカル改変を全サービスへ勝手に伝播させないため。共通側マニフェストの変更は共通リポで直接（PRで）行う。

### 安全機構（誤操作・事故を機械的に防ぐ）
- **新規ファイルは既定で追加しない**：共通リポに既に存在するファイルの**更新のみ**を行う。共通に無いファイル（＝サービス固有物が紛れ込んだ疑い）は
  スキップし、意図的な新規追加は `--allow-new` を明示したときだけ許可する（＝レビューの合図）。
- **dirty な共通リポには適用しない**：`--apply` 前に共通リポの対象ファイルに未コミット変更があれば中断する（`--force` で回避可）。
  共通側の未コミット作業を盲目的な上書きで潰さないため。上書き分は `.backport-backup-*/` に自動退避する。
- **profiles/ 由来の骨格は機械還流の対象外**（サービス側の配置とパスが 1:1 対応せず `.backport-manifest` に
  載せられないため。`.backport-manifest` 注1参照）。運用は下記チェックリストの1行で足りる：
  - [ ] **還流・順輸入の実行時**：profiles 骨格（`.claude/` 配下・`.devcontainer/`・`.github/workflows/`・`Makefile`・監査雛形等）を
        どちらか一方で変更していたら、共通リポ側は `profiles/` 配下の対応ファイル、既存サービス側は同パスへ**手でコピーして揃える**
        （基盤→サービス方向の変更でも同様。root↔`profiles/_base` の複製ずれは監査 check(7) が機械検出する）。

## 最重要の規律：マニフェスト対象はスタック中立に保つ
機械同期は中身を抽象化しない。だから**共通所有ファイルには最初からサービス固有物を書かない**。

- ✅ 共通所有に置く：枠組み・原則・言語非依存の運用ルール（例：品質ゲートの原則、整合性監査の"型"、破壊的操作の禁止、git運用）。
- ❌ 共通所有に置かない：特定の言語/FW/ORM/決済/インフラ、具体的な `lint`/`test` コマンド、ドメイン固有の識別子やチェック。
  → これらは `SERVICE.md`、または `docs/rules/` ではなく別ディレクトリ（例：`docs/service-rules/`）へ分離する。

固有物が共通所有ファイルに混ざりそうになったら、それは「ファイルを分割せよ」の合図。
共通の枠組み部分だけをマニフェスト対象に残す。

## 使い方

```bash
# 1) プレビュー（差分表示のみ）
./scripts/backport-to-common.sh <共通リポのパス>

# 2) 問題なければ既存ファイルの更新を適用（共通リポ内 .backport-backup-*/ に元ファイルを自動退避）
./scripts/backport-to-common.sh <共通リポのパス> --apply

# 2') 共通リポにまだ無いファイルを意図的に新規追加する場合のみ
./scripts/backport-to-common.sh <共通リポのパス> --apply --allow-new

# 3) 共通リポ側で差分を確認し、レビューを経てコミット/PR
cd <共通リポのパス> && git status && git diff
```

- 実行は「共通リポが見える環境」で行う（サービスと共通リポが別コンテナなら、両方が見える WSL 側など）。
- **共通リポへの反映は必ずレビュー/PRを通す**。逆輸入は上書きなので、他サービス由来の改善を消していないか差分で確認する。
- マニフェストは各サービスが編集してよい（ローカル設定であり共通へは伝播しない）。追加するファイルはスタック中立に限る。
- **後片付け**：`--apply` のたびに共通リポへ `.backport-backup-<日時>/` が生成される（`.gitignore` 済み）。
  差分をコミット/PR 化して確認が済んだら、不要なバックアップは適宜削除してよい。

## 順輸入（共通 → サービス）の使い方

```bash
# 1) プレビュー（差分表示のみ。共通リポ側マニフェスト由来の対象一覧と diff を確認）
./scripts/sync-from-common.sh <共通リポのパス>

# 2) 問題なければ適用（上書き分は .sync-backup-*/ に自動退避。新規の共通ルールは追加される）
./scripts/sync-from-common.sh <共通リポのパス> --apply

# 3) サービス側で差分を確認してコミット
git status && git diff
```

- 対象の解決は**共通リポ側の `.backport-manifest` が正**（サービス側ローカルの改変で取込範囲が歪まないように）。
- 逆輸入と違い**新規ファイルも既定で追加する**。順方向の新規＝共通リポで生まれた新ルールであり、配布がこのツールの目的そのものだから（逆方向は固有物の漏出リスクがあるため `--allow-new` を要求する。非対称は意図的）。
- サービス側の対象ファイルが dirty なら中断する。共通へ還流すべき改善が混ざっているなら、**先に `backport-to-common.sh` で還流してから**取り込む（取込→還流の順だと改善が上書きで消える）。

## いつ逆輸入・順輸入するか
- **逆輸入**：共通所有ファイル（`.backport-manifest` 記載）を改善したとき。定期監査（`audit-ai-rules` skill 等。**基盤リポで一括実施**し、各サービスへは配布しない）で「この改善は他サービスにも効く」と判断したとき。
- **順輸入**：共通リポに他サービス由来の改善・新ルールが入ったと知ったとき。目安として**作業の区切りで dry-run を流し**、差分があれば取り込む（solo 運用では定期スケジュールを課さない。2026-07-23 に週次目安を撤去）。
- サービス固有に閉じる変更は還流しない（マニフェストに載せない）。
