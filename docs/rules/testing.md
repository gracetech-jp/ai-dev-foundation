# テストガイドライン（共通・言語非依存）

本ファイルは全サービス共通の原則のみを扱う。**フレームワーク名・テスト用DB・CIジョブ名・現状のカバレッジ数値・モック対象の外部サービス**など、スタック固有の具体は各サービスの `PROJECT.md` に定義する。

## 基本ルール
- 新機能の実装時は必ずテストを同時に作成する
- バグ修正時は再現テストを先に書いてから修正する
- テストなしのコードはマージ不可

## カバレッジ目標
| 対象 | 目標 |
|---|---|
| ビジネスロジック | 80%以上 |
| APIエンドポイント | 100%（正常系・異常系） |
| ユーティリティ関数 | 100% |

- 上記は目標値。これとは別に「現状値からの低下を防ぐフロア」をCIで機械強制し、テストを追加しながら段階的に引き上げる。フロアの現在値・実行コマンド・CIジョブ名は `PROJECT.md` に定義する

## テスト名
- 正常系・異常系が名前から判別でき、入力条件と期待結果が読み取れる命名にする
  （例：「正常系: 〜が存在する場合、〜を返す」「異常系: 〜が存在しない場合、404を返す」）

## 方針
- 単体テストを優先し、結合テストは最小限に抑える
- テストは独立して実行可能にする（他テストの結果に依存しない）
- モックは外部依存（DB・外部API）に限定し、内部ロジックはモックしない
- テストデータはファクトリー関数で生成し、ハードコードしない
- 使用するテストフレームワーク・テスト用DB・モック対象の外部サービスは `PROJECT.md` に定義する

## 要件トレーサビリティ（要件↔テストの紐づけ）

要件（`docs/requirements/`）とテストをマーカーで紐づける。詳細な要件の形式は
`docs/rules/requirements.md` を正とする。ここではテスト側のマーカー規約のみを定める。

- **マーカー記法**：テストに要件IDのマーカーを付す。
  - 通常の受け入れ基準の検証：`@pytest.mark.req("R-xxx")`
  - 「起きてはいけないこと」の検証（adversarial）：`@pytest.mark.adversarial("R-xxx")`
- **マーカー文字列はスタック依存**（言語・フレームワークで表記が異なる）。
  実際に走査する grep 正規表現（`REQ_MARKER_RE` / `ADV_MARKER_RE`）とテスト探索パス（`REQ_TEST_PATHS`）は
  **`PROJECT.md` で定義**する（共通リポは中立＝既定の記法を強制しない。例: bats のサービスは
  `# @req: R-xxx` のようなコメントマーカーを用いる）。
- **マーカーは「紐づけの主張」であって「検証の妥当性」ではない**。実装者はハッピーパスしか見ない
  テストにもマーカーを貼れてしまう。妥当性は adversarial テスト（S/A の negative_space に必須。G4）で
  補強する（旧 `tests_ratified_by` の人間批准は 2026-07-24 の批准レス化（ADR-008）で廃止）。
- **adversarial テストは、実装した同一コンテキストで生成しない**ことを推奨する（要件文面だけを入力に
  した別コンテキストで逆生成する。骨抜き防止。`docs/rules/requirements.md` §6）。
- 未カバー要件・dangling マーカーは `scripts/check-requirements-coverage.sh` が
  CI と push 前で機械検出する（`make req-coverage`）。
