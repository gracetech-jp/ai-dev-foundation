# 整合性チェックガイドライン（共通テンプレ）

変更のたびにその場だけ修正して終わりにせず、プロジェクト全体への影響を確認する。

> このファイルは**枠組み**を定める共通テンプレート。各サービスは、自分のアーキテクチャに合わせて
> 「層の名前」「マイグレーション/スキーマ検査の具体コマンド」「監査スクリプトの中身」を
> `PROJECT.md`・監査スクリプト側で肉付けする。ここにスタック固有名（特定ORM・特定FW・特定関数名）を書かない。

---

## 変更後に必ず確認するチェックリスト

### 1. 同一ドメインの層間チェック（縦断）
1つのファイルを変更したら、同じドメインの**関連する全レイヤー**に反映されているか確認する。
（例：データモデル → 入出力スキーマ → ビジネスロジック → 公開インターフェース。層の呼称は各サービスで定義）

- モデルのフィールド追加・変更・削除 → スキーマ・ロジック・公開I/Fに反映されているか
- 型の変更 → 送受信の両側・バリデーションと一致しているか
- 関数/サービスの戻り値変更 → 呼び出し側の期待と整合しているか

### 2. データモデルとマイグレーション（スキーマ）の同期
- モデルのカラム追加・変更・削除が発生したら、必ず対応するマイグレーションを作成する
- 前進（upgrade）・後退（downgrade/rollback）の両方が正しいか確認する
- **モデル↔マイグレーションの drift 検出**をCIとpush前で自動実行する（具体コマンドは各サービス）

### 3. サーバ ↔ クライアント（API契約）の型一致
- レスポンスのフィールド名・型がクライアント側の型定義と一致しているか
- フィールド名のリネームは、参照している全箇所（クライアント含む）を**同時に**更新する
- null許容 / 任意項目の扱いが両側で一致しているか

### 4. シード・テストデータの追従
- モデル変更後、シードデータが新スキーマで動作するか
- テスト用フィクスチャが古いフィールドを参照していないか

### 5. 既存テストの通過確認
変更後は必ずテストを実行し、壊れていないことを確認する（実行コマンドは各サービスの`PROJECT.md`）。
壊れたテストは修正してから完了とする。修正困難なら必ずユーザーに報告する。

### 6. `PROJECT.md` の棚卸し
`PROJECT.md`は実装の要約であり、ズレるとAIが誤った前提で判断する。以下を変更したら同時に更新する。
- 依存パッケージを追加した → 技術スタック表に追記したか
- モジュール/ディレクトリを追加・削除した → 構成一覧に反映したか
- 環境変数を追加した → 環境変数表に追記したか

### 7. 設計ドキュメントのハルシネーションチェック
AIが設計書に書いた内容が実装を正しく反映しているとは限らない。大きめの変更後・監査時に確認する。
- **UIモック・フロー図が実装と食い違っていないか**（文言・配置・遷移順。作り直した初版が残っていないか）
- **コード例・関数シグネチャが実在するか**（疑似コードが実際の引数・型と一致するか。grepで裏取り）
- **未実装を実装済みのように書いていないか**（構想段階は「【未実装・要検討】」と明記）
- **リネーム・削除済みの識別子を参照していないか**

チェック方法：具体的な主張（関数名・フィールド名・UI挙動）を1つずつgrep/コード読解で裏取りする。
裏取りできない主張は「未確認」「要検証」と明記するか、確認してから記載する。

## 監査スクリプトの3層構成（枠組み）
個々のチェック内容はサービス固有だが、**監査の型は共通**。`make audit-all` 相当で束ねて実行できるようにする。

| 層 | 目的 | 性質 |
|---|---|---|
| (1) 軽量grep整合性 | 過去不具合の再発防止・層間の対応漏れ検出 | 依存なし・どこでも実行可 |
| (2) 構造的不変条件 | モデル/設定から導かれる「常に成り立つべき条件」の検証（設計から**再生成される派生物**） | コード解析ベース |
| (3) スキーマdrift | 実データモデルとマイグレーションのズレ検証 | 実環境が必要 |

> **(2) 構造的不変条件と、要件の negative space（固定資産）は別物**。(2) は設計・設定から
> **導かれる派生物**であり「設計に追従して整合が崩れていないか」を検査する。一方、要件の
> **negative space（起きてはいけないこと）は、設計から再生成させない確定済みの固定資産**であり、
> 「何があっても踏み越えてはならない一線」を adversarial テストで検証する（詳細:
> `docs/rules/requirements.md` §5・`INVARIANTS` テンプレ）。両者を混同しない。前者はここ(2)で扱い、
> 後者の具体は各サービスが `docs/requirements/` に自分のドメイン語で書く（本ファイルには焼き込まない）。

**再利用性の高いパターン**（各サービスで実装推奨）：
- **リネーム残渣の全域スキャン（データ駆動）**：`旧名→新名`の配列を1箇所に持ち、旧名の残存をリポ全域grepで検出。新リネームは配列に1行追加するだけ。
- **必須設定の二重記載チェック**：必須の環境変数などが、ドキュメントと設定例（`.env.example`等）の両方に載っているか。
- **登録漏れ検出**：中央レジストリ（マイグレーションのモデルimport一覧、横断ポリシーの対象一覧等）への登録漏れを機械検出。

> 過去バグ用の個別grepを無闇に増やさない。一般化できる不変条件は (2) か「リネーム残渣スキャン」に寄せる。

## 実行タイミング（二重化）

| タイミング | 方法 | 位置づけ |
|---|---|---|
| **CI必須ゲート** | CIジョブ（整合性・スキーマdrift 等） | 毎push実行。build/deployの前提に含め、フック未導入や`--no-verify`素通りを防ぐ最終防波堤 |
| **push前ローカル** | git pre-pushフック（`make audit-all`＋`make test`相当） | 手元で早期検出。CIを待たず気付ける |
| **手動** | `make audit-all` / `make test` 相当 | 疑いがあるとき・大きな変更後に任意で |

毎ファイル変更後の実行は不要。CIとpush前の二重で担保する（詳細: `docs/rules/quality-gates.md`）。

## 作業完了の定義
以下をすべて満たして初めて「完了」とする。
- [ ] 変更の直接対象が意図通り動作する
- [ ] 関連する他層に不整合がない
- [ ] マイグレーションがモデルと同期している
- [ ] クライアントの型がサーバのスキーマと一致している
- [ ] 既存テストが通過している
- [ ] シードデータが動作する
- [ ] `PROJECT.md`が実装（依存・構成・環境変数）と一致している
- [ ] 設計ドキュメントに新規記載・更新した内容が実装と裏取りできている（推測・記憶で書いていない）
