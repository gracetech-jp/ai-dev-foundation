## 背景

ADR-012 で「本物の境界はコンテナ隔離だけ」と決めた。`permissions.deny` も PreToolUse フックも
迂回経路が実証されており、敵対的コードに対する防御としては数えない。したがって**爆発半径を
実際に決めているのは、コンテナから外へ出られる宛先の集合**＝許可ドメインリストである。

この集合は「設定値」ではなく境界そのものなので、変更が監査対象になっていなければならない
（ADR-013 結果節「許可ドメインリストを要件として管理する（変更時に監査対象とする）」）。

## 受け入れ基準

### 許可リストの決め方

- `BASE_DOMAINS`（全プロジェクト共通）は、**公式の Network access requirements に挙がる必須ホスト**と
  **実コンテナで観測した宛先**の積のみで構成する。参照実装に載っているだけの宛先は入れない。
- 追加するときは**実測の根拠**（失敗したツールのエラーメッセージ、または DNS 観測の記録）を伴う。
  推測で足さない。まとめて広げない（1件ずつ足して都度確認する）。
- プロジェクト固有の追加は `extra-allowed-domains.txt` に置き、**ビルド時にイメージへ焼き込む**。
- **不要になった宛先は外す。** 許可リストは増える一方にしない——外へ出られる宛先の集合が
  そのまま爆発半径だから、使わなくなった1行を残すことは境界を無償で広げたままにすることと同じ。
  2026-08-04 に通知サービス1件を、機能（通知フック）の廃止にあわせて外した実績がある。
- **爆発半径を広げる追加は、広がる範囲を明記してから行う。** 到達先が「読むだけの宛先」か
  「書き込める宛先」かで意味が違う。後者を足すときは、実際に何ができるかを決めるのは
  許可リストではなく**そこへ渡す資格情報のスコープ**であることを記録する（下記 GitHub の例）。

### スクリプトが満たすこと（`init-firewall.sh`）

- **引数を一切受け付けない**。sudoers は引数まで固定できないため、`--disable` のような口を持つと
  コンテナ内から遮断を解除できてしまう。
- **root 以外では実行できない**（`postStartCommand` から sudo 経由で呼ばれる前提）。
- 許可ドメインの**名前解決に失敗したら異常終了する**。黙って飛ばして「その宛先だけ通らない
  ファイアウォール」を作らない。
- `extra-allowed-domains.txt` の行は**ドメイン書式を検査**し、不正な行があれば異常終了する。
  壊れた行を黙って無視しない。
- **異常終了時は fail-closed**。許可リストの構築途中で落ちても `OUTPUT` を DROP に落としてから
  終わり、`status=failed` を記録し、回復手順を標準エラーへ出す。
- **正常終了時は既定ポリシーが DROP** であり、かつ「遮断側に到達できないこと」と
  「許可側に到達できること」の**両方を実測してから** `status=ok` を記録する。
  片側だけの検証では「全部塞いだ」状態も緑になってしまう。

| **`github.com`** | **git over HTTPS（fetch / pull / push）** | **同上** |

**GitHub 追加による爆発半径の変化（2026-08-04）**

- コンテナから**リポジトリへ書き込める**ようになる（`git push`・API 経由の設定変更）。
  これは意図した変更であり、CI 結果の確認という用途のために受け入れる。
- **境界の実効範囲を決めるのは、この許可リストではなく渡すトークンのスコープになった。**
  許可リストは「どのホストへ出られるか」しか決めない。GitHub 上で何ができるかは資格情報が決める。
  したがって**トークンは用途に必要な最小の権限・最小のリポジトリに限定する**こと。
- `permissions.deny` の `Bash(git push:*)`（第2層）は**別の層**であり、この変更では触っていない。
  第2層は事故防止であって境界ではない（ADR-012）。境界側が開いた事実は第2層では打ち消せない。

**GitHub へ渡す資格情報のスコープ（2026-08-04 確定）**

| 項目 | 値 | 根拠 |
|---|---|---|
| 種別 | **fine-grained PAT**（GitHub App のインストールトークンは採用しない） | 下記 |
| 対象リポジトリ | 3本のみ（共通基盤・既存2プロジェクト） | 用途がこの範囲に閉じる |
| 権限 | **Actions: Read + Contents: Read and write + Workflows: Read and write**（2026-08-06 拡大） | 下記 |
| 有効期限 | 90日 | |
| 渡し方 | `devcontainer.json` の `containerEnv` からホスト環境変数 `GH_TOKEN` を参照 | 秘密の住所をホスト側に置いたままにする（ワークスペースにも git にもイメージにも入れない） |

**App のインストールトークン（1時間で失効）を採らなかった理由**: 短命であることの利点は
**トークンをコンテナの外で発行して注入する場合にのみ**成立する。コンテナ内で自動更新するには
**App の RSA 秘密鍵をコンテナへ置く**ことになり、PAT より強力かつ長命な秘密を抱えることになる。
1時間ごとに人が発行し直す運用は「極力人間に手を使わない」前提に反する。
**短命トークンという語に引かれて、より強い秘密を置き換えで持ち込まないこと。**

**書き込みへ広げた（2026-08-06）**: 当初は `Contents: Read` のみで、
`git push` は**ネットワーク的には可能だが認証が通らない**状態にしてあった。
コンテナから push できるようにするため `Contents` を Read and write へ広げ、
**ワークフローファイル（`.github/workflows/`）の変更には別途 `Workflows` 権限が要る**ため
これも Read and write で追加した。

**爆発半径の変化を隠さずに書く**——広がったのは次のとおり:

| | 変更前（2026-08-04） | 変更後（2026-08-06） |
|---|---|---|
| 読み取り | 3リポジトリ | 3リポジトリ（変わらず） |
| 書き込み | **無し** | **3リポジトリの内容を改変・push できる** |
| ワークフロー | 変更不可 | **`.github/workflows/` を改変できる＝ CI で任意のコードを走らせられる** |

とくに 3 行目は、**CI 実行環境（GitHub Actions ランナー）まで爆発半径が伸びる**ことを意味する。
コンテナ隔離の外側にある実行環境を、コンテナの中から書き換えられる。
`git push` を止めているものは、もはやトークンのスコープではなく
**第2層の `permissions.deny`（`Bash(git push:*)`）と運用規律（CLAUDE.md）だけ**になった。
第2層は事故防止であって境界ではない（ADR-012）——**この構成では「Claude が push しない」ことは
機械的には保証されていない**。渡した以上、その前提で扱うこと。

**渡していないもの**: `Administration`（ブランチ保護などリポジトリ設定の変更）は付与しない。
設定変更は画面から人が行う。

**スコープの確認**: `scripts/verify-isolation.sh` の 5/6 が実測する
（(a) 許可側の Actions が読めること・(b) 到達できるリポジトリ集合・
(c) **記録どおり書き込めること**・(d) **Administration が無いこと**）。
判定は**スコープを広げたら結果が変わるもの**でなければならない。2026-08-04 の実測で、
次の2つは条件を満たさないと分かった——`gh api /user` は Metadata: Read-only の範囲で
公開プロフィールを返すため**全開放でも 200**。「許可外リポジトリが 404」も、
許可外の**公開**リポジトリは 200 で読めるうえ（fine-grained PAT は選択外でも公開データに届く）、
存在しないリポジトリ名なら**全開放でも 404**のままになる。
書き込みの可否は 2026-08-06 の権限拡大で「拒否されること」を測れなくなったため、
**上限を測る役目は (d) へ移した**（Administration 未付与なら 403、付与すれば 200/404 に変わる）。
(c) は実効性ではなく**記録と実態の一致**を見る検査として残す（読み取り専用へ戻したのに
本ファイルが書き込み可のままなら、記録のほうが嘘になる）。

**足していない候補**（用途が確定していないため。必要になったら失敗したコマンドのエラーを根拠に足す）:
`codeload.github.com`（アーカイブ取得）/ `uploads.github.com`（アップロード）。

**`objects.githubusercontent.com` は足していないが到達する。**
`raw.githubusercontent.com` と同じ4つの IP に解決されるため、ipset では区別できない（2026-08-04 実測）。
下記「対象外」の「同一 IP への相乗り」が実際に現れた例であり、**許可リストの粒度がホスト単位ではなく
IP 単位であること**を示す具体例として記録する。

### 変更したときに走るゲート

- 上記 `paths` のいずれかを変更すると `make tier-tripwire` が本要件との対応を要求する
  （Makefile の `TIER_TRIPWIRE_PATHS` に同じ集合を登録済み）。
- 複製4本（`common/docker/` 正本 ↔ `profiles/_base/` ↔ `service-templates/` ↔ 基盤 `.devcontainer/`）の
  一致は `audit-consistency.sh` 検査(10)が diff で強制する。1本だけ足すと赤になる。
- 境界を成す Dockerfile 側の要素（sudo の1本絞り・`COPY` によるイメージ内実行）は
  検査(13)が実在を要求する。

## 対象外（この要件が要求しないこと）

- **ホストの Docker ソケットを渡す構成では本要件は成立しない。** ソケットが使える時点で
  コンテナの設定を任意に上書きして起動できるため、許可リストごと迂回される（ADR-013「未解決」）。
- **許可ドメインと同一 IP に相乗りする別ホストへの通信**。ipset は IP 単位で許可するため、
  共有 CDN 上の別サイトは区別できない。
- **DNS 経由の持ち出し**。名前解決を通すため udp/53 は常時許可しており、クエリ名に情報を載せる
  経路は塞いでいない。
- **ビルド時（`docker build`）の通信**。ファイアウォールは `postStartCommand` で適用されるため、
  イメージビルド中の `RUN` 行は遮断対象外である。

## 検証

`tests/init-firewall.bats`（`make test` から bats で実行）。実際の iptables を触らずに検証するため、
`iptables` / `ipset` / `dig` / `ip` / `curl` / `id` をスタブに差し替え、状態ファイルと
`extra-allowed-domains.txt` の位置をサンドボックスへ向けた複製に対して実行する。
遮断を解除しようとする側（引数・非 root・不正な追加行）と、fail-closed の成立を adversarial として置く。

実コンテナでの実測は `scripts/verify-isolation.sh`（Rebuild 後に1本流す）が担う。
静的検査（設定がそう書いてあること）とは別に、**実際にそう振る舞うこと**を確認するのが目的である。
