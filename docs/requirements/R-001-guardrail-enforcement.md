## 位置づけ（2026-08-03・ADR-012）

本要件が統べるのは**ガードレールの第2層・第3層**であり、これらは「不注意による事故を減らす」層である。
敵対的コードに耐える境界は第1層（コンテナ隔離。ADR-013 / R-003）だけであり、
**本要件は「防御」ではなく「事故防止」を約束する**。

旧題は「破壊的操作・秘密読取の**機械的遮断**」だった。ADR-012 で第2層・第3層の位置づけを
「防御」から「事故防止」へ変えたため、要件の主語も変えた（2026-08-04・ユーザー承認済み）。
**要件が実態より強いことを主張し続けるほうが危険**であるため、範囲を実態に合わせた。

## 受け入れ基準（EARS 記法）

記法: `While〈前提条件〉, when〈トリガー〉, the〈システム名〉shall〈システム応答〉`

### 第3層（PreToolUse フック）が満たすこと

**R-001-1**
When Bash ツールの呼び出しが発生したとき、
**第3層は**、次を含むコマンドを **deny しなければならない**。

- 再帰かつ強制の削除（`rm -rf` / `-fr` / `-Rf` / 分離・混在・パス先行の表記ゆれを含む）
- 履歴・ブランチの破壊（`git reset --hard` / `git clean` の force 形 / `git branch -D`）
- force push（`git push --force` / `-f` / `--force-with-lease`）
- `git checkout` によるパス指定の変更破棄（`-- <パス>` および `.`）

**R-001-2**
When Bash ツールの呼び出しが発生したとき、
**第3層は**、秘密ファイルのパスが平文で現れる読み取りを **deny しなければならない**。
対象の手段は外部コマンド、インタプリタのインラインコード（`-c` / `-e` / `-p` / `--eval` / `-m`）、
ヒアドキュメント、パイプ経由の流し込みを含む。

**R-001-3**
While 対象リポジトリが基盤リポジトリでない間（プロジェクトルートに `profiles/_base/` が無い間）、
when 共通所有ファイルへの書き込みを伴う Bash 呼び出しが発生したとき、
**第3層は**、その呼び出しを **deny しなければならない**。

**R-001-7**
If 判定に必要な前提（`jq` の実在）を満たさない場合、
then **第3層は**、Bash の実行自体を **exit 2 でブロックしなければならない**（fail-closed）。

### 第2層（`permissions.deny`）が満たすこと

**R-001-4**
`git push --force` 系・`git reset --hard`・`git clean` の force 形・`git checkout` による変更破棄について、
**第2層は**、第3層と**独立に**当該コマンドを拒否するルールを **保持しなければならない**（ADR-012 決定4の二重化）。

### 例外（deny へ移管できない理由そのもの）

**R-001-5**
When `.env.example` / `.env.sample` / `.env.template` / `.env.dist` の読み取り、
言語の環境変数構文（`process.env` / `import.meta.env` / `Bun.env` / `Deno.env`）、
公開鍵（`id_*.pub`）、プロパティアクセス（`row.key` 等）、
または `git clean` のドライラン（`-n` / `--dry-run`）を含む Bash 呼び出しが発生したとき、
**第3層は**、その呼び出しを **deny してはならない**。

**R-001-6**
While 対象リポジトリが基盤リポジトリでない間、
when 第1引数が `profiles/_base/` で始まる `cp` / `rsync` / `install`（骨格同期）が発生したとき、
**第3層は**、その呼び出しを **deny してはならない**。

### 退化の検出

**R-001-8**
When 第2層または第3層のいずれか一方から R-001-4 の判定が失われたとき、
**整合性監査は**、非ゼロ終了で **失敗しなければならない**。

## 対象外（この要件が要求しないこと）

- **難読化**によるパス生成（`'.e'+'nv'` / `chr()` / base64 デコード）
- **ファイル実行**（`python script.py`）、**間接実行**（`npm run` / `npx` / `uv run` のファイル実行形）
- **ライブラリ経由**の暗黙読み込み（`require('dotenv').config()`）
- **`find` 経由の削除**（`find . -delete` / `find . -exec rm …`）。**第2層・第3層のどちらも見ていない**
  （2026-08-04 明文化）
- **コンテナ外での起動**。フックもルールもマウント経由で配られるため、コンテナ外では両方とも無い

いずれも正規表現による静的検査では原理的に到達できないか、層の外にある
（根拠: `docs/rules/security.md` §静的検査の防御ライン）。これらは第1層（ADR-013 / R-003）が受ける。
通過することは `tests/guard-dangerous.bats`「既知の限界」節で**テストとして固定**している。

## 検証

| 対象 | 手段 | 頻度 |
|---|---|---|
| 第3層の振る舞い（R-001-1/2/3/5/6/7） | `tests/guard-dangerous.bats`（`make test`） | 常時 |
| 両層に判定が実在すること（R-001-4/8） | `scripts/audit-consistency.sh` 検査(14)（`make audit-all`） | 常時 |
| 第2層が実際に発火すること | `scripts/verify-guardrails.md` の手動チェックリスト | deny 変更時・Rebuild 時 |

第2層は Claude Code 本体が評価するため **bats からは検証できない**。
「書いてあること」は検査(14)、「実際に発火すること」は手動チェックリストが受け持つ。

## 改訂の記録

> **2026-08-04 ADR-012 フェーズ2**: 記法を EARS へ変更し、層ごとに主語を分けた。
> `title` を「機械的遮断」→「事故防止」に変更（**要件の意味の変更**。ユーザー承認済み）。
> `negative_space` の1件目を「破壊的コマンドが表記ゆれを用いても実行できてはならない」から
> 「双方の層から同時に判定が失われてはならない」へ差し替えた。旧文言は `find . -delete`・
> 結合フラグ・コンテナ外起動で成立してしまう**達成不能な絶対要求**であり、
> 満たしていないものを満たしていると主張し続ける状態だったため。
> 3件目（正当な操作を止めてはならない）は新規追加で、誤遮断が2度（2026-07-25 の `process.env`、
> 07-26 の `ls /home/node/.ssh/`）実際に起きたことに基づく。

> 2026-07-24 批准レス化（ADR-008）: 旧 `tests_ratified_by` / `tests_ratified_sha` / `test_assets` は
> スキーマごと廃止したため本要件からも除去した。要件内容（受け入れ基準・negative_space）は不変。

> **2026-07-26 paths の拡大（保護範囲の拡大・ユーザー承認済み）**: 参照方式への移行フェーズ0で、
> `new-service.sh` が配る初期値の正本を `service-templates/` へ移した。移行後はこちらが
> ガードと deny の配布元になるが、Tier トリップワイヤの機微パスに入っておらず**保護対象外**だった。
> `service-templates/claude/scripts/guard-dangerous.sh` と `service-templates/claude/settings.json` を
> paths に追加し、Makefile の `TIER_TRIPWIRE_PATHS` にも同じ2件を加えて実効化した。
> **これは保護範囲の拡大であり緩和ではない**（受け入れ基準・negative_space は不変）。
> なお `service-templates/` 配下でディレクトリ名を `.claude` ではなく `claude` にしているのは、
> `.claude/skills/` が作業ディレクトリ配下にあると Claude Code がスコープ付きスキルとして
> オンデマンドに読み込むため（実測）。配布前の雛形が基盤セッションに混ざるのを構造的に防ぐ。

> **2026-07-25 negative_space の緩和（ユーザー了解のうえ実施）**: 旧文言
> 「秘密情報ファイルが bash 経由（読取コマンドとの共起・パイプ跨ぎ）で読み取れてはならない」は、
> 達成不能な絶対要求だった。`guard-dangerous.sh` は正規表現による静的検査であり、難読化・
> ファイル実行・間接実行には原理的に到達できない。旧文言のままでは「要件を満たしている」と
> 誤認したまま穴が放置されるため、実際に守れる範囲（パスが平文で現れる読み取り）へ限定した。
> **これは要件の緩和であり、防御範囲は狭まっている**。敵対的コードを想定する場合は
> フックの拡張では解決せず、ファイル権限・秘密の非ファイル化・ネットワーク遮断で対処する
> （2026-08-03・ADR-012 で脅威モデルを更新し、これを既定の想定とした）。
